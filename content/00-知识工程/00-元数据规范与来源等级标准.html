知识条目元数据规范与来源等级标准

概述

每一个知识条目文件在创建时，必须包含一份 YAML frontmatter 作为结构化元数据。这份元数据承担了三个核心职责：(1) 使知识条目可被程序化检索和聚合；(2) 标注知识来源的可信度等级，为读者提供信息可靠性判断依据；(3) 通过关系字段建立知识图谱的边，使知识库从平面文件集合升级为可遍历的知识网络。

本文件定义了所有元数据字段的语义、约束和用法，以及七级来源等级标准（L0-L6），供知识条目作者和审核人使用。

核心内容

一、YAML Frontmatter 字段详解

1.1 domain（必填）

知识条目所属的知识域编号与名称，格式为 "XX-domain-name"。该字段用于将知识条目归属到 KNOWLEDGE_TAXONOMY.md 中定义的 19 个知识域之一。

约束：

  • 必须与目录路径一致。例如，放在 knowledge/01-计算机基础/ 目录下的文件，domain 必须为 "01-计算机基础"。
  • 编号使用两位数字，与知识域总览表对齐。

示例：

yaml
domain: "01-计算机基础"
domain: "02-Java平台"
domain: "12-Agent工程"

1.2 title（必填）

知识条目的中文标题。应简洁、准确、完整，通常控制在 20 字以内。标题定义了本条目最主要的讨论对象，也是构建知识关系时的主要引用标识。

最佳实践：

  • 使用名词短语而非句子
  • 尽量避免过于宽泛的词（如"知识"、"技术"）
  • 优先级：准确性 > 简洁性 > 吸引力

反例： "一些关于Java的东西"（不准确） → 正例： "JVM 内存模型与 G1 GC 原理"

1.3 status（必填）

知识条目的生产就绪状态。四个可选值：

值 含义 触发条件
draft 草稿，内容不完整或未经验证 新建条目默认值；L6 来源自动设为 draft
verified 已审核，内容可靠 通过质量检查清单的全部项目
outdated 已过时，但保留供历史参考 技术版本更新导致原内容不再适用
archived 已归档，不再维护 知识域被重构或知识点被合并到其他条目

状态转换规则：

draft ──（通过质量检查清单）──> verified
verified ──（技术升级/版本落后）──> outdated
outdated ──（完成更新）──> verified
draft/outdated/verified ──（合并/重构）──> archived

每次修改状态需同步更新 updated 字段。

1.4 level（必填）

知识条目的难度级别，与目标读者（具备 Java 后端经验的工程师）的预期理解水平对齐。

级别 含义 判断标准
beginner 入门级 只需域外前置知识即可理解；无本域经验也可阅读
intermediate 中级 需要本域的基础概念；适合有 1-2 年相关经验的读者
advanced 高级 涉及深层原理、源码分析、性能调优；需要扎实的域内基础
reference 参考级 速查表、命令清单、配置模板等；内容侧重索引而非讲解

示例：

  • Java 基础语法 → beginner
  • HashMap 源码分析 → advanced
  • Docker 常用命令速查 → reference

1.5 sources（必填）

来源列表，每条来源包含三个字段：level（L0-L6）、url（可选）、description（必填）。

Array of objects 结构：

yaml
sources:
  - level: "L1"
    url: "https://docs.oracle.com/en/java/javase/25/"
    description: "Oracle JDK 25 官方文档"
  - level: "L2"
    url: "https://github.com/openjdk/jdk/tree/jdk-25"
    description: "OpenJDK 25 源码仓库 — HashMap 实现分析"
  - level: "L3"
    description: "《Java并发编程实战》第5章 — 同步容器与并发容器"

约束规则：

  1. 至少包含一个 L0-L3 级别的来源（verified 条目的硬性要求）。
  2. L6 来源强制 status: draft。
  3. URL 若有，应为可公开访问的标准 URL；内部 Wiki 或无法公开访问的链接应只保留描述。
  4. 来源按可信度从高到低排列。

1.6 relations（必填）

知识条目与其他条目的关系。六种关系类型（详见 00-知识关系类型详解.md）：

yaml
relations:
  prerequisite: ["01-数据结构与算法"]   # 前置知识
  related: ["02-garbage-collection-in-depth"]            # 相关知识
  derived: []                                            # 派生关系
  contrast: []                                           # 对比关系
  version-of: []                                         # 版本关系
  replaces: []                                           # 替代关系

取值规则：

  • 值为该知识域内的文件名（不含 .md 扩展名）。跨域引用加域前缀，如 02-Java平台/02-virtual-threads-in-depth。
  • 空数组表示该关系类型无关联条目，不可省略该字段。
  • 建议在创建条目时先填写 prerequisite 和 related，其他关系在后续整理中补充。

1.7 tags（必填）

扁平的关键词标签数组，用于跨域搜索和语义归类。标签应是 小写英文 单词或短语（连字符连接），避免使用中文标签（保留给未来 i18n 支持）。

标签命名规则：

  • 使用单数形式（thread 而非 threads）
  • 使用全称而非缩写（garbage-collection 而非 gc，除非缩写是业界通用标准如 jvm、jdk）
  • 每个条目建议 3-8 个标签
  • 标签体现：技术栈名、概念领域、应用场景

示例：

yaml
tags: ["jvm", "garbage-collection", "g1", "memory-management", "performance-tuning"]

标签体系会随着知识库增长而演进；新增标签时应检查是否已有同义标签存在。

1.8 created 和 updated（必填）

日期格式统一为 YYYY-MM-DD（ISO 8601 日期格式）。

  • created：条目首次创建的日期，不可修改。
  • updated：最近一次内容实质性修改的日期。修正拼写错误不视为实质性修改；更新代码示例、补充新章节、修改结论视为实质性修改。

版本矩阵检查： 当 updated 距当前日期超过 90 天时，应触发时效性复核。

二、来源等级标准 (L0-L6)

来源等级是知识可信度的尺度。同一知识点的多级来源存在冲突时，优先采信高等级来源。

2.1 L0 — 官方规范与标准

最高可信度。包括但不限于：

类型 示例
Java 语言规范 JLS (Java Language Specification)
JDK Enhancement Proposals JEP 444 (Virtual Threads)
IETF 标准 RFC 7230 (HTTP/1.1)、RFC 8446 (TLS 1.3)
国际/行业标准 OWASP Top 10、ISO 27001
W3C 规范 HTML、CSS、Web API 标准
数据库 SQL 标准 SQL:2016

判断标准： 内容由正式的标准委员会或权威组织发布，具有规范性质的约束力，实现者必须遵循。

使用指南： L0 来源用于确认"标准怎么说"。例如，HashMap 的 hash() 方法行为应以 JLS 和 JEP 为准，而不是某篇博客的解读。

2.2 L1 — 官方文档

由技术开发方或维护方撰写的正式文档，是日常开发中最常用的权威来源。

类型 示例
语言/平台文档 Oracle JDK 文档、Go 语言规范
框架官方手册 Spring Framework Reference、Spring AI 文档
数据库官方文档 PostgreSQL Manual、Redis Documentation
云服务文档 AWS 官方文档、Kubernetes 官方文档
API Reference OpenAI API Reference、Anthropic API Docs

判断标准： 文档发布方 = 技术开发方；内容为官方维护而非社区贡献。

边界情况：

  • GitHub 仓库中的 README.md 若为主要文档入口，视为 L1。
  • GitHub 仓库中的 Wiki（社区可编辑），应降级为 L4。
  • Stack Overflow 上的官方团队回答（有"Staff"标签），可视情况升级为 L1。

2.3 L2 — 源码

直接阅读和解析源代码获得的理解。这是验证 L1 文档准确性、理解未文档化行为的终极手段。

类型 示例
OpenJDK 源码 java.util.HashMap 实现
Spring Framework 源码 @Transactional AOP 拦截逻辑
Linux 内核源码 epoll 实现
PostgreSQL 源码 MVCC 实现

判断标准： 内容来自对源代码的直接解读分析，而非第三方转述。

使用指南： L2 来源通常配合代码引用（指定文件路径和行号或关键方法名）。源码分析时务必标注分析的版本（commit hash 或 tag），因为源码行为可能随版本变化。

标记示例：

yaml
- level: "L2"
  url: "https://github.com/openjdk/jdk/blob/jdk-25-ga/src/java.base/share/classes/java/util/HashMap.java"
  description: "OpenJDK 25 HashMap 源码 — resize() 方法 L668-L740"

2.4 L3 — 权威书籍

由领域专家撰写、出版社正式出版的书籍，经过同行评审和编辑审核。

类型 示例
并发编程 《Java并发编程实战》(Brian Goetz)
分布式系统 《Designing Data-Intensive Applications》(Martin Kleppmann)
JVM 《深入理解Java虚拟机》(周志明)
算法 《算法导论》(CLRS)

判断标准：

  1. 正式出版（ISBN 存在）。
  2. 作者是该领域公认的专家。
  3. 内容经过编辑或同行评审。

排除项：

  • 自出版电子书（除非作者是该技术的核心贡献者）。
  • 仅在线发布的文档（除非满足 L1 条件）。
  • 翻译版以其原版的权威性为准。

2.5 L4 — 技术博客与学术论文

类型 示例
官方技术博客 Spring Blog、Netflix Tech Blog、AWS Architecture Blog
学术界论文 经同行评审的会议/期刊论文（如 SIGMOD、VLDB、OSDI）
知名技术博客 美团技术团队、阿里中间件博客
个人技术博客 经多方交叉验证的深度技术文章

判断标准：

  • 博客：作者可追踪、内容有数据或实验支撑、非纯观点。
  • 论文：经同行评审（arXiv 预印本降低一个可信度子级）。
  • 博客无官方背书 → 不能升级为 L1。

2.6 L5 — 社区与经验

类型 示例
Stack Overflow 高票答案（score > 50）
GitHub Issues/Discussions 官方仓库的讨论
技术论坛 Reddit r/java、V2EX
个人实践经验 经多项目验证的经验总结

判断标准： 社区共识或经过多人验证的个体经验。单个 L5 来源不足以支撑核心结论，建议至少 2-3 个独立 L5 来源交叉验证。

2.7 L6 — AI 生成

由大语言模型（Claude、GPT 等）生成的知识总结。

强制约束：

  1. 任何以 L6 为主要来源的条目，status 必须为 draft。
  2. 必须在 description 中显式标注："AI 生成，未经人工验证"。
  3. 人工审核验证后，移除 L6 来源标记，添加对应的 L0-L5 来源。
  4. L6 可作为补充来源（次要来源）存在于 verified 条目中，但不能是唯一来源。

典型用法： L6 用于知识条目的初稿生成（提升效率），后续由人类专家对照 L0-L3 来源进行事实核查和改写。

三、版本矩阵维护流程

KNOWLEDGE_TAXONOMY.md 第五节定义了版本矩阵，记录所有关键技术的当前版本。维护流程如下：

3.1 定期复核（每季度）

复核触发条件：
- 到达季度复核日期（1月、4月、7月、10月第一个工作日）
- JDK/Spring/Spring AI 大版本发布
- PostgreSQL/Redis/Kafka 等核心基础设施大版本发布

复核步骤：
1. 逐项检查版本矩阵中的"当前版本"列
2. 对每个技术，访问其官方网站确认最新稳定版本
3. 更新"当前版本"和"备注"列
4. 在 TECHNLOGY_RADAR.md 中评估是否需要调整象限
5. 在维护日志中记录变更

3.2 事件驱动更新

事件 行动
JDK 新 LTS 发布 一周内更新版本矩阵，评估是否需要创建新的知识条目
Spring Boot 大版本 三天内更新，检查所有代码示例的兼容性
Spring AI 大版本 三天内更新，优先核查 API 变更
技术雷达象限变动 同步更新版本矩阵"备注"

3.3 知识条目版本同步

当版本矩阵中的技术版本更新后，需要扫描所有引用该技术的知识条目：

  • 如果新版本导致代码示例无法编译 → 更新代码且将 status 改为 verified（如需大幅改写则先改为 draft）
  • 如果新版本只增加特性，不影响现有内容 → 在条目中添加新版本说明，保持 status: verified

四、完整示例

以下是一个符合所有规范的知识条目 frontmatter 完整示例：

yaml
---
domain: "02-Java平台"
title: "Virtual Threads 深度解析"
status: "verified"
level: "advanced"
sources:
  - level: "L0"
    url: "https://openjdk.org/jeps/444"
    description: "JEP 444: Virtual Threads 正式规范"
  - level: "L1"
    url: "https://docs.oracle.com/en/java/javase/25/core/virtual-threads.html"
    description: "Oracle JDK 25 Virtual Threads 官方文档"
  - level: "L2"
    url: "https://github.com/openjdk/jdk/tree/jdk-25-ga/src/java.base/share/classes/java/lang"
    description: "OpenJDK 25 源码 — VirtualThread、Continuation 实现"
  - level: "L3"
    description: "《Java并发编程实战》第3版 第9章 — Project Loom与Virtual Threads"
  - level: "L4"
    url: "https://inside.java/2023/11/15/virtual-threads-deep-dive/"
    description: "Oracle 内部博客 — Virtual Threads 调度与性能分析"
relations:
  prerequisite:
    - "02-java-thread-model"
    - "02-jmm-basics"
  related:
    - "02-structured-concurrency"
    - "02-scoped-values"
    - "02-reactor-vs-virtual-threads"
  derived: []
  contrast:
    - "02-reactor-vs-virtual-threads"
  version-of: []
  replaces:
    - "02-reactor-fundamentals"
tags:
  - "virtual-threads"
  - "project-loom"
  - "concurrency"
  - "jdk25"
  - "jep444"
  - "continuation"

updated: "2026-07-17"

常见问题

Q1: 如果一本书同时有中英文版本，来源等级如何标注？

以原版（通常是英文版）的权威性为准。翻译版可能在技术术语上存在偏差，建议引用的同时标注原版信息。

Q2: 官方团队博客（如 Spring Blog）属于 L1 还是 L4？

正式的框架参考文档（Reference Documentation）属于 L1。官方团队博客中带有"engineering deep dive"性质的文章属于 L4——它们通常解释实现细节而非定义 API 契约。

Q3: 一个知识点在 L1 文档中描述模糊但在 L2 源码中有明确行为，应该标注什么？

L1 + L2 同时标注。在正文中明确指出："官方文档（L1）对 X 行为的描述为……，但源码（L2, commit abc123）中实际实现为……"。

Q4: 版本矩阵中的技术版本与本地环境不一致怎么办？

版本矩阵记录的是知识库的"规范版本"（即代码示例和技术论述的基准版本）。如果本地环境版本不同，应在理解兼容性的前提下，以矩阵版本为准编写示例。

Q5: status: draft 的条目可以被引用为 prerequisite 吗？

可以，但不推荐。如果一个 draft 条目作为其他条目的前置知识，应当在依赖条目中明确指出这一风险，并说明读者可以暂时跳过该前置条件或寻找替代学习资源。
