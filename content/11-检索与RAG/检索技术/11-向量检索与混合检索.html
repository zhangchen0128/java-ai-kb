向量检索与混合检索：从HNSW到RRF融合

概述

检索是RAG系统的核心环节。现代检索系统通常结合两种范式：稠密向量检索（语义匹配）和稀疏关键词检索（精确匹配）。本文从向量检索的底层索引结构（HNSW、IVFFlat）出发，推导BM25的数学原理，最终构建完整的混合检索+RRF融合方案，并提供在PostgreSQL pgvector和Elasticsearch上的完整Java实现。

一、向量检索原理

1.1 ANN vs KNN

KNN (K-Nearest Neighbors)：

  • 精确检索：扫描所有向量，计算距离，返回Top-K
  • 复杂度：O(N×D)，N为向量数量，D为维度
  • 百万级向量 → 秒级延迟 → 不可接受

ANN (Approximate Nearest Neighbors)：

  • 近似检索：牺牲少量精度换取数量级的速度提升
  • 典型精度损失：<1%（召回率99%+）
  • 百万级向量 → 毫秒级延迟

1.2 pgvector支持的索引类型对比

特性 IVFFlat HNSW
构建时间 快 较慢
查询速度 较慢 快
内存占用 低 高（需要存储图结构）
召回率 95-99% 99%+
构建参数 lists m, ef_construction

增量更新 需要重建 支持
适用规模 100K-10M 10K-100M

二、HNSW索引深入

2.1 图结构

HNSW (Hierarchical Navigable Small World) 构建一个多层图：

Layer 2:  ●──────●        （最顶层，节点最少，长距离连接）
         /        \
Layer 1: ●──●──●──●──●    （中间层）
        / \/ \/ \/ \/ \
Layer 0: ●─●─●─●─●─●─●─●  （底层，所有节点，短距离连接）

关键参数：

  • M (max_connections)：每个节点每层的最大连接数。典型值16-64。更大的M → 更高召回率 + 更多内存。
  • ef_construction：构建索引时的动态候选列表大小。典型值128-512。更大的值 → 更高质量的图 + 更长的构建时间。
  • ef_search：搜索时的动态候选列表大小。典型值64-256。更大的值 → 更高召回率 + 更多搜索延迟。

2.2 插入算法

function INSERT(new_element, HNSW_graph):
    L = random_level()  // 随机选择层级（指数衰减分布）
    entry_point = get_entry_point()
    
    for lc from max_level down to L+1:
        // 在高层找到最近的入口点
        entry_point = greedy_search(new_element, entry_point, 1, lc)
    
    for lc from min(L, max_level) down to 0:
        // 在当前层搜索ef_construction个最近邻
        candidates = search_layer(new_element, entry_point, ef_construction, lc)
        // 启发式邻居选择：挑选多样化的邻居
        neighbors = select_neighbors_heuristic(new_element, candidates, M, lc)
        // 添加双向连接
        for neighbor in neighbors:
            connect(new_element, neighbor)
            // 裁剪：如果neighbor的连接数超过M，剪掉最远的
            if |neighbor.connections(lc)| > M:
                prune_neighbors(neighbor, lc)

2.3 搜索算法

function SEARCH(query, k, ef_search):
    entry_point = get_entry_point()
    
    // 从顶层开始，逐层下降
    for lc from max_level down to 1:
        entry_point = greedy_search(query, entry_point, 1, lc)
    
    // 在底层做精细搜索
    candidates = search_layer(query, entry_point, ef_search, 0)
    
    // 从candidates中取前k个作为结果
    return top_k(candidates, k)

三、IVFFlat索引

3.1 工作原理

IVFFlat (Inverted File with Flat compression) 将向量空间划分为K个聚类区域：

  1. 训练阶段：对数据集的子集运行K-means聚类，得到K个聚类中心
  2. 索引阶段：将每个向量分配到最近的聚类中心，构建倒排列表
  3. 查询阶段：找到距离查询向量最近的nprobe个聚类中心，只在这些聚类中搜索
向量空间划分：
    Cluster 1: [v11, v12, v13, ...]  ← 倒排列表 1
    Cluster 2: [v21, v22, ...]       ← 倒排列表 2
    ...
    Cluster K: [vK1, vK2, ...]       ← 倒排列表 K

查询过程：
    query → 计算与K个聚类中心的距离
         → 选最近的nprobe个聚类
         → 在这nprobe个聚类的所有向量中精确搜索

3.2 pgvector IVFFlat配置

sql
-- 创建IVFFlat索引（需要先有数据用于训练）

数据量 < 100K + 需要频繁增量更新 → HNSW
数据量 > 10M + 内存受限 → IVFFlat
召回率要求 > 99% → HNSW
构建时间敏感 → IVFFlat

四、BM25稀疏检索

4.1 从TF-IDF到BM25的演变

TF-IDF的缺陷：

  1. 词频线性增长：一个词出现10次的文档权重是出现1次的10倍，不符合实际
  2. 无文档长度归一化：长文档天然有更高的匹配机会
  3. 参数不可调：无法针对场景优化

BM25的改进：引入词频饱和函数和文档长度归一化参数。

4.2 BM25公式分解

$$BM25(D, Q) = \sum_{i=1}^{n} IDF(q_i) \times \frac{f(q_i, D) \times (k_1 + 1)}{f(q_i, D) + k_1 \times (1 - b + b \times \frac{|D|}{avgdl})}$$

其中：

  • $IDF(q_i)$：逆文档频率，衡量词$q_i$的稀有度
  • $f(q_i, D)$：词$q_i$在文档$D$中的频率
  • $|D|$：文档长度
  • $avgdl$：所有文档的平均长度
  • $k_1$：词频饱和参数（典型值1.2-2.0）。$k_1=0$时退化为二值（出现/不出现）
  • $b$：文档长度归一化参数（典型值0.75）。$b=0$时不归一化，$b=1$时完全归一化

IDF的具体公式（Lucene/ES使用）： $$IDF(q_i) = \ln\left(1 + \frac{N - n(q_i) + 0.5}{n(q_i) + 0.5}\right)$$

其中$N$为文档总数，$n(q_i)$为包含词$q_i$的文档数。

import co.elastic.clients.elasticsearch.ElasticsearchClient;
import co.elastic.clients.elasticsearch.core.SearchResponse;
import co.elastic.clients.elasticsearch.core.search.Hit;
import co.elastic.clients.json.jackson.JacksonJsonpMapper;
import co.elastic.clients.transport.rest_client.RestClientTransport;
import org.elasticsearch.client.RestClient;

public class ElasticsearchBm25Search {

    private final ElasticsearchClient esClient;

    public ElasticsearchBm25Search(String esUrl) {
        var restClient = RestClient.builder(
            java.net.http.HttpClient.newHttpClient()  // 简化示例
        );
        // 实际项目中使用RestClient.builder(HttpHost.create(esUrl)).build()
        this.esClient = null; // 实际初始化
    }

    /**
     * BM25检索
     */
    public record SearchResult(String chunkId, String content,
                                double score, Map<String, Object> highlights) {}

    public List<SearchResult> bm25Search(String query, String indexName, int size) throws Exception {
        var response = esClient.search(s -> s
            .index(indexName)
            .query(q -> q
                .match(m -> m
                    .field("content")
                    .query(query)
                )
            )
            .size(size)
            .highlight(h -> h
                .fields("content", hf -> hf
                    .fragmentSize(150)
                    .numberOfFragments(3)
                )
            )
            .explain(true), // 开启explain查看BM25计算细节
            Map.class
        );

        return response.hits().hits().stream()
            .map(hit -> new SearchResult(
                (String) hit.source().get("chunk_id"),
                (String) hit.source().get("content"),
                hit.score() != null ? hit.score() : 0.0,
                hit.highlight() != null ? hit.highlight() : Map.of()
            ))
            .toList();
    }

    /**
     * 使用explain API查看BM25打分细节（调试用）
     */
    public String explainScore(String query, String documentId, String indexName) throws Exception {
        var response = esClient.explain(e -> e
            .index(indexName)
            .id(documentId)
            .query(q -> q.match(m -> m.field("content").query(query)))
        );
        return response.explanation().toString();
    }
}

五、混合检索与RRF融合

5.1 稠密+稀疏的互补性

特性 稠密检索（向量） 稀疏检索（BM25）
匹配方式 语义相似度 关键词精确匹配
优势 同义词、改写、语义理解 专有名词、代码、术语精确匹配
劣势 对罕见词不敏感 对语义改写不敏感
适合Query类型 自然语言问句 关键词搜索、实体查询

核心洞察：两种检索方式的错误模式不同，融合后可以互补。

5.2 RRF (Reciprocal Rank Fusion)

RRF是当前最常用的融合策略，不依赖分数的绝对值（向量相似度与BM25分数的量纲不同）。

$$RRF(d) = \sum_{r \in R} \frac{1}{k + rank_r(d)}$$

其中：

  • $R$：参与融合的排序列表集合
  • $rank_r(d)$：文档$d$在排序列表$r$中的排名（从1开始）
  • $k$：平滑参数，经典默认值60。$k \to 0$时排名差距越大权重差异越大

RRF计算示例：

文档A: 向量检索排名1, BM25排名3
  RRF(A) = 1/(60+1) + 1/(60+3) = 0.01639 + 0.01587 = 0.03226

文档B: 向量检索排名2, BM25排名1
  RRF(B) = 1/(60+2) + 1/(60+1) = 0.01613 + 0.01639 = 0.03252

B排在A前面，虽然A的向量排名更高

5.3 Java实现 — RRF融合算法

java
import java.util.*;
import java.util.stream.Collectors;

public class HybridSearchService {

    /**
     * 混合检索结果
     */
    public record HybridSearchResult(
        String chunkId,
        String content,
        double rrfScore,
        double vectorScore,    // 原始向量相似度
        double bm25Score,      // 原始BM25分数
        int vectorRank,
        int bm25Rank,
        Map<String, Object> metadata
    ) {}

    /**
     * 执行混合检索 + RRF融合
     */
    public List<HybridSearchResult> hybridSearch(
            String query, float[] queryEmbedding,
            String tenantId, List<String> accessLevels,
            int topK) {

        // 1. 向量检索（pgvector）
        var vectorResults = vectorSearch(queryEmbedding, tenantId, accessLevels, topK * 2);

        // 2. BM25检索（Elasticsearch或PostgreSQL ts_rank）
        var bm25Results = bm25Search(query, tenantId, accessLevels, topK * 2);

        // 3. RRF融合
        return rrfFusion(vectorResults, bm25Results, 60, topK);
    }

    /**
     * RRF融合核心算法
     * @param k RRF平滑参数，默认60
     */
    public List<HybridSearchResult> rrfFusion(
            List<RankedResult> vectorResults,
            List<RankedResult> bm25Results,
            int k, int topK) {

        // 构建 chunkId → RRF累积分数 的映射
        var rrfScores = new HashMap<String, RrfAccumulator>();

        // 处理向量检索结果
        for (int i = 0; i < vectorResults.size(); i++) {
            var r = vectorResults.get(i);
            var acc = rrfScores.computeIfAbsent(r.chunkId(), id -> new RrfAccumulator());
            acc.addVectorScore(r.score(), i + 1, k);
        }

        // 处理BM25检索结果
        for (int i = 0; i < bm25Results.size(); i++) {
            var r = bm25Results.get(i);
            var acc = rrfScores.computeIfAbsent(r.chunkId(), id -> new RrfAccumulator());
            acc.addBm25Score(r.score(), i + 1, k);
        }

        // 按RRF分数排序，取Top-K
        return rrfScores.entrySet().stream()
            .map(e -> {
                var acc = e.getValue();
                return new HybridSearchResult(
                    e.getKey(),
                    getContent(e.getKey()),
                    acc.getRrfScore(),
                    acc.vectorScore,
                    acc.bm25Score,
                    acc.vectorRank,
                    acc.bm25Rank,
                    getMetadata(e.getKey())
                );
            })
            .sorted((a, b) -> Double.compare(b.rrfScore(), a.rrfScore()))
            .limit(topK)
            .toList();
    }

    /**
     * 加权分数融合（Weighted Sum）— RRF的替代方案
     * 需要对向量相似度和BM25分数做归一化（Min-Max或Softmax）
     */
    public List<HybridSearchResult> weightedFusion(
            List<RankedResult> vectorResults,
            List<RankedResult> bm25Results,
            double vectorWeight, // 典型值0.7
            double bm25Weight,   // 典型值0.3
            int topK) {

        // Min-Max归一化
        if (vectorResults.isEmpty() || bm25Results.isEmpty()) {
            return List.of();
        }

        var vMax = vectorResults.getFirst().score();
        var vMin = vectorResults.getLast().score();
        var bMax = bm25Results.getFirst().score();
        var bMin = bm25Results.getLast().score();

        var scores = new HashMap<String, Double>();

        for (var r : vectorResults) {
            var normalized = vMax == vMin ? 1.0
                : (r.score() - vMin) / (vMax - vMin);
            scores.merge(r.chunkId(), normalized * vectorWeight, Double::sum);
        }

        for (var r : bm25Results) {
            var normalized = bMax == bMin ? 1.0
                : (r.score() - bMin) / (bMax - bMin);
            scores.merge(r.chunkId(), normalized * bm25Weight, Double::sum);
        }

        return scores.entrySet().stream()
            .sorted(Map.Entry.<String, Double>comparingByValue().reversed())
            .limit(topK)
            .map(e -> new HybridSearchResult(
                e.getKey(), getContent(e.getKey()),
                e.getValue(), 0, 0, 0, 0, getMetadata(e.getKey())
            ))
            .toList();
    }

    // --- 辅助类型 ---
    public record RankedResult(String chunkId, double score) {}

    private static class RrfAccumulator {
        double vectorScore = 0;
        double bm25Score = 0;
        int vectorRank = -1;
        int bm25Rank = -1;

        void addVectorScore(double score, int rank, int k) {
            this.vectorScore = score;
            this.vectorRank = rank;
        }

        void addBm25Score(double score, int rank, int k) {
            this.bm25Score = score;
            this.bm25Rank = rank;
        }

        double getRrfScore() {
            double sum = 0;
            if (vectorRank > 0) sum += 1.0 / (60 + vectorRank);
            if (bm25Rank > 0) sum += 1.0 / (60 + bm25Rank);
            return sum;
        }
    }

    // --- 占位方法 ---
    private List<RankedResult> vectorSearch(float[] embedding, String tenantId,
                                             List<String> accessLevels, int limit) {
        // 调用pgvector进行向量检索
        return List.of();
    }

    private List<RankedResult> bm25Search(String query, String tenantId,
                                           List<String> accessLevels, int limit) {
        // 调用Elasticsearch进行BM25检索
        return List.of();
    }

    private String getContent(String chunkId) { return ""; }
    private Map<String, Object> getMetadata(String chunkId) { return Map.of(); }
}

/**
 * Elasticsearch原生混合检索 — BM25 + kNN + RRF
 */
public List<SearchResult> esHybridSearch(
        ElasticsearchClient esClient,
        String query, float[] queryEmbedding,
        String indexName, int topK) throws Exception {

    var response = esClient.search(s -> s
        .index(indexName)
        .size(topK)
        // BM25子查询
        .query(q -> q.bool(b -> b
            .should(sq -> sq.match(m -> m
                .field("content")
                .query(query)
                .boost(1.0f)
            ))
        ))
        // kNN子查询
        .knn(k -> k
            .field("embedding")
            .queryVector(Arrays.stream(queryEmbedding)
                .boxed().toList())
            .k(topK * 2)
            .numCandidates(topK * 4)
        )
        // RRF融合
        .rank(r -> r.rrf(rrf -> rrf
            .windowSize(topK * 2)
            .rankConstant(60)
        )),
        Map.class
    );

    return response.hits().hits().stream()
        .map(hit -> new SearchResult(
            (String) hit.source().get("chunk_id"),
            (String) hit.source().get("content"),
            hit.score() != null ? hit.score() : 0.0,
            Map.of()
        ))
        .toList();
}

5.5 PostgreSQL混合检索（ts_rank + pgvector + RRF）

sql
-- PostgreSQL混合检索完整SQL
WITH vector_results AS (
    SELECT c.chunk_id, c.content,
           1 - (e.embedding <=> :query_vector::vector) AS vector_score,
           ROW_NUMBER() OVER (ORDER BY e.embedding <=> :query_vector::vector) AS vector_rank
    FROM chunk_embeddings e
    JOIN chunks c ON e.chunk_id = c.chunk_id
    WHERE c.status = 'active'
      AND c.tenant_id = :tenant_id
    ORDER BY e.embedding <=> :query_vector::vector
    LIMIT :limit
),
bm25_results AS (
    SELECT c.chunk_id, c.content,
           ts_rank(to_tsvector('chinese', c.content),
                   plainto_tsquery('chinese', :query_text)) AS bm25_score,
           ROW_NUMBER() OVER (ORDER BY
               ts_rank(to_tsvector('chinese', c.content),
                       plainto_tsquery('chinese', :query_text)) DESC
           ) AS bm25_rank
    FROM chunks c
    WHERE to_tsvector('chinese', c.content) @@ plainto_tsquery('chinese', :query_text)
      AND c.status = 'active'
      AND c.tenant_id = :tenant_id
    ORDER BY bm25_score DESC
    LIMIT :limit
),
combined AS (
    SELECT
        COALESCE(v.chunk_id, b.chunk_id) AS chunk_id,
        COALESCE(v.content, b.content) AS content,
        COALESCE(v.vector_score, 0) AS vector_score,
        COALESCE(b.bm25_score, 0) AS bm25_score,
        COALESCE(v.vector_rank, :fallback_rank) AS vector_rank,
        COALESCE(b.bm25_rank, :fallback_rank) AS bm25_rank
    FROM vector_results v
    FULL OUTER JOIN bm25_results b ON v.chunk_id = b.chunk_id
)
SELECT chunk_id, content, vector_score, bm25_score,
       (1.0 / (60 + vector_rank) + 1.0 / (60 + bm25_rank)) AS rrf_score
FROM combined
ORDER BY rrf_score DESC
LIMIT :top_k;

-- pgvector: WHERE子句在ORDER BY之前执行
SELECT c.chunk_id, c.content,
       1 - (e.embedding <=> :query_vector) AS similarity
FROM chunk_embeddings e
JOIN chunks c ON e.chunk_id = c.chunk_id
WHERE c.tenant_id = :tenant_id           -- 过滤
  AND c.access_level IN (:access_levels)  -- 过滤
  AND c.created_at > :since               -- 过滤
ORDER BY e.embedding <=> :query_vector
LIMIT 10;
  • 优点：精确控制返回数量
  • 缺点：可能排除了语义相关但不满足过滤条件的文档（更安全的选择）

Post-filtering（先检索再过滤）：

sql
-- 先检索更多，再在应用层过滤
SELECT ... LIMIT 50  -- 取更多
-- 然后在Java代码中过滤
  • 优点：不会因过滤条件漏掉潜在相关文档
  • 缺点：返回数量不可控

最佳实践：Pre-filtering + 适当扩大检索范围（limit * 1.5 ~ 2）。

public class FilteredSearchService {

    /**
     * Pre-filtering策略：在SQL/ES层面完成过滤
     */
    public List<HybridSearchResult> searchWithFilters(
            float[] queryEmbedding, String query,
            FilterCriteria criteria, int topK) {

        var expandedLimit = (int) (topK * 2.0); // 扩大检索范围

        var vectorResults = vectorSearchWithFilters(
            queryEmbedding, criteria, expandedLimit
        );
        var bm25Results = bm25SearchWithFilters(
            query, criteria, expandedLimit
        );

        var fused = rrfFusion(vectorResults, bm25Results, 60, topK);

        // 后置检查（双保险）
        return fused.stream()
            .filter(r -> criteria.matches(r.metadata()))
            .limit(topK)
            .toList();
    }

    public record FilterCriteria(
        String tenantId,
        List<String> accessLevels,
        String category,
        List<String> tags,
        java.time.Instant since,
        java.time.Instant until
    ) {
        public boolean matches(Map<String, Object> metadata) {
            if (tenantId != null && !tenantId.equals(metadata.get("tenant_id"))) return false;
            if (!accessLevels.isEmpty() && !accessLevels.contains(metadata.get("access_level"))) return false;
            // ... 更多条件
            return true;
        }
    }
}

八、最佳实践

  1. 默认使用HNSW：召回率和速度综合最优
  2. 混合检索作为标配：BM25 + 向量 + RRF
  3. 平滑参数k=60：经典默认值，大多数场景无需调整
  4. 扩大检索范围 + Pre-filtering：先取limit×2，数据库层过滤
  5. Metadat过滤下推到数据库：SQL WHERE / ES filter context
  6. 定期ANALYZE向量索引：索引膨胀后需要维护

九、反模式

  • 仅用向量检索：丢失精确匹配能力
  • 混合检索不融合直接拼接：向量Top-10 + BM25 Top-10 = 20个结果缺乏统一排序
  • 在应用层做元数据过滤：检索后只剩3条，用户看不到完整结果
  • 盲目增大ef_search追求召回率：ef_search=500时延迟可能是100的5倍
