幂等设计与分布式锁

概述

在分布式系统中，网络重试、消息重复投递、用户重复点击都会导致同一操作被执行多次。幂等设计确保重复执行的结果与单次执行一致。分布式锁则提供跨节点的互斥访问能力。两者是构建可靠分布式系统的基石。

本文覆盖幂等性的五种实现策略、三种分布式锁方案的深度对比、Redisson 源码级分析，以及支付、消息消费、定时任务三个实际案例。

一、幂等设计

1.1 什么是幂等

数学定义：f(f(x)) = f(x)。在分布式系统中：同一操作的任意次执行，产生的结果与执行一次相同。

幂等分两类：

  • 天然幂等： UPDATE account SET balance = 100 WHERE id = 1（设置绝对值）
  • 需设计幂等： UPDATE account SET balance = balance - 10 WHERE id = 1（相对操作）

1.2 策略一：Token 机制

流程：

  1. 客户端请求 Token → 服务端生成唯一 Token 返回 → 同时存入 Redis（TTL 5 分钟）
  2. 客户端提交请求时携带 Token
  3. 服务端检查 Token 是否存在
  4. 存在 → 删除 Token + 执行业务（原子操作）
  5. 不存在 → 拒绝（重复请求）
java
@RestController
@RequestMapping("/api/orders")
public class OrderController {

    private final StringRedisTemplate redis;

    // 1. 获取 Token
    @PostMapping("/token")
    public Map<String, String> getToken(@RequestParam String userId) {
        var token = UUID.randomUUID().toString();
        redis.opsForValue().set("idempotent:token:" + token, userId,
                Duration.ofMinutes(5));
        return Map.of("token", token);
    }

    // 2. 带 Token 提交
    @PostMapping
    public ResponseEntity<?> createOrder(@RequestHeader("X-Idempotent-Token") String token,
                                         @RequestBody CreateOrderRequest request) {
        // 原子删除 Token（Lua 脚本）
        var script = """
            if redis.call('get', KEYS[1]) == ARGV[1] then
                return redis.call('del', KEYS[1])
            else
                return 0
            end
            """;

        var deleted = redis.execute(
                new DefaultRedisScript<>(script, Long.class),
                List.of("idempotent:token:" + token),
                request.userId());

        if (deleted == null || deleted == 0) {
            return ResponseEntity.status(409).body(Map.of("error", "重复请求"));
        }

        // 执行业务逻辑
        var order = orderService.create(request);
        return ResponseEntity.ok(order);
    }
}

优点： 通用性强，不依赖业务数据。 缺点： 需要额外一次 Token 获取请求；Token 删了但业务失败需要补偿机制。

1.3 策略二：唯一索引

利用数据库唯一约束 + 业务键：

sql
CREATE TABLE orders (
    id BIGSERIAL PRIMARY KEY,
    order_no VARCHAR(32) NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'CREATED',
    -- ...
    CONSTRAINT uk_order_no UNIQUE (order_no)
);
java
@Service
@Transactional
public class OrderService {

    public Order createOrder(OrderRequest request) {
        try {
            var order = new Order(request.getOrderNo(), "CREATED", ...);
            return orderRepo.save(order);
        } catch (DataIntegrityViolationException e) {
            // 唯一键冲突 → 返回已有订单（幂等）
            return orderRepo.findByOrderNo(request.getOrderNo())
                    .orElseThrow(() -> new IllegalStateException("订单已存在但无法查询"));
        }
    }
}

适用条件：

  • 业务键天然唯一（如订单号、流水号）
  • 请求携带的业务键全局唯一（客户端生成或雪花ID）

状态机 + 唯一索引： 更复杂的幂等需要结合状态机。

java
@Service
@Transactional
public class PaymentService {

    public Payment processPayment(String transactionId, PaymentRequest req) {
        var existing = paymentRepo.findById(transactionId);
        if (existing.isPresent()) {
            var payment = existing.get();
            if (payment.getStatus() == PaymentStatus.SUCCESS) {
                return payment; // 幂等：已完成
            }
            if (payment.getStatus() == PaymentStatus.PROCESSING) {
                // 当前正在处理 → 等待或返回处理中
                return payment;
            }
        }
        // 插入初始状态 + 处理
        var payment = paymentRepo.save(new Payment(transactionId, PaymentStatus.PROCESSING));
        executePayment(payment, req);
        payment.setStatus(PaymentStatus.SUCCESS);
        return paymentRepo.save(payment);
    }
}

1.5 策略四：数据库去重表

sql
CREATE TABLE request_dedup (
    request_id VARCHAR(64) PRIMARY KEY,
    handler_class VARCHAR(200),
    result JSONB,
    status VARCHAR(20) DEFAULT 'PROCESSING',
    created_at TIMESTAMPTZ DEFAULT NOW(),
    completed_at TIMESTAMPTZ
);
java
@Service
public class DedupService {

    private final JdbcTemplate jdbc;

    public <T> T executeOnce(String requestId, Supplier<T> handler) {
        // 1. 尝试插入去重记录
        try {
            jdbc.update(
                "INSERT INTO request_dedup (request_id, status) VALUES (?, 'PROCESSING')",
                requestId);
        } catch (DuplicateKeyException e) {
            // 2. 已存在 → 等待结果
            return waitForResult(requestId);
        }

        // 3. 执行业务
        try {
            var result = handler.get();
            jdbc.update(
                "UPDATE request_dedup SET result = ?::jsonb, status = 'COMPLETED', completed_at = NOW() WHERE request_id = ?",
                toJson(result), requestId);
            return result;
        } catch (Exception e) {
            jdbc.update(
                "UPDATE request_dedup SET status = 'FAILED' WHERE request_id = ?",
                requestId);
            throw e;
        }
    }

    private <T> T waitForResult(String requestId) {
        // 轮询等待处理完成（生产环境建议用 Redis pub/sub 通知）
        for (int i = 0; i < 30; i++) {
            var row = jdbc.queryForMap(
                "SELECT result, status FROM request_dedup WHERE request_id = ?",
                requestId);
            if ("COMPLETED".equals(row.get("status"))) {
                return fromJson((String) row.get("result"));
            }
            Thread.sleep(100);
        }
        throw new ProcessingTimeoutException("处理超时: " + requestId);
    }
}

1.6 策略五：Redis 计数器 + TTL

java
public boolean isDuplicate(String idempotentKey, Duration window) {
    var key = "dedup:" + idempotentKey;
    var count = redis.opsForValue().increment(key);
    if (count == 1) {
        redis.expire(key, window); // 仅首次设置过期
        return false;
    }
    return true; // count > 1 → 重复请求
}

二、分布式锁

2.1 Redis 实现

基础 SET NX PX + Lua 释放：

java
public class RedisDistributedLock {

    private final StringRedisTemplate redis;
    private static final String LOCK_PREFIX = "distributed_lock:";
    private static final String RELEASE_SCRIPT = """
        if redis.call('get', KEYS[1]) == ARGV[1] then
            return redis.call('del', KEYS[1])
        else
            return 0
        end
        """;

    public boolean tryLock(String key, String value, long expireMs) {
        return Boolean.TRUE.equals(
                redis.opsForValue().setIfAbsent(LOCK_PREFIX + key, value,
                        Duration.ofMillis(expireMs)));
    }

    public boolean release(String key, String value) {
        var result = redis.execute(
                new DefaultRedisScript<>(RELEASE_SCRIPT, Long.class),
                List.of(LOCK_PREFIX + key), value);
        return result != null && result == 1;
    }
}

Redisson 看门狗深入：

java
// Redisson RLock 自动续期
var config = new Config();
config.useSingleServer().setAddress("redis://localhost:6379");
var redisson = (RedissonClient) Redisson.create(config);

var lock = redisson.getLock("order:123");

// lock() 看门狗行为：
// - 默认 leaseTime = 30s（internalLockLeaseTime）
// - 每 internalLockLeaseTime/3 = 10s 续期一次
// - 看门狗在当前线程存活期间持续续期
// - 调用 unlock() 时取消看门狗
lock.lock();

try {
    // 可能执行 >30s 的业务逻辑，看门狗自动续期
    doLongRunningTask();
} finally {
    lock.unlock();
}

// 也可指定 leaseTime（不使用看门狗，到时自动释放）
lock.lock(10, TimeUnit.SECONDS);

红锁（RedLock）争议讨论：

RedLock 算法（Antirez 提出）：
1. 获取当前时间
2. 依次向 N 个 Redis 实例获取锁（SET NX PX）
3. 如果获取到多数锁（N/2+1）且总耗时 < 锁有效期 → 成功
4. 失败则释放所有已获取的锁

Kleppmann 的质疑：
1. 锁用于"互斥"和"正确性"两种不同目的
2. 如果只用于"效率"（避免重复工作），单实例 + 看门狗足够
3. 如果用于"正确性"（只能有一个写入者），RedLock 依赖时钟同步，不可靠
4. 正确性场景应使用 Fencing Token 或支持一致性的系统（ZooKeeper/etcd）

生产建议：

目的 推荐方案
效率（避免并发重复执行） 单 Redis + Redisson 看门狗
简单互斥（可容忍极低概率出错） 单 Redis + Redisson + 短 TTL
正确性（严格互斥，如金融） ZooKeeper / etcd / DB 锁
正确性 + 高可用 Fencing Token + Consensus 锁

2.2 ZooKeeper 实现

临时顺序节点 + Watch 机制：

java
public class ZkDistributedLock {

    private final CuratorFramework client;
    private final String lockPath;
    private String currentNodePath;

    public ZkDistributedLock(CuratorFramework client, String lockName) {
        this.client = client;
        this.lockPath = "/locks/" + lockName;
    }

    public void lock() throws Exception {
        // 1. 创建临时顺序节点
        currentNodePath = client.create()
                .creatingParentsIfNeeded()
                .withMode(CreateMode.EPHEMERAL_SEQUENTIAL)
                .forPath(lockPath + "/lock-");

        while (true) {
            // 2. 获取所有子节点，按序号排序
            var children = client.getChildren().forPath(lockPath)
                    .stream().sorted().toList();

            var currentNodeName = currentNodePath.substring(lockPath.length() + 1);
            var index = children.indexOf(currentNodeName);

            if (index == 0) {
                // 3. 最小序号 → 获取锁
                return;
            } else {
                // 4. Watch 前一个节点
                var prevNodePath = lockPath + "/" + children.get(index - 1);
                var latch = new CountDownLatch(1);

                if (client.checkExists().forPath(prevNodePath) != null) {
                    client.getData().usingWatcher((Watcher) event -> {
                        if (event.getType() == Watcher.Event.EventType.NodeDeleted) {
                            latch.countDown();
                        }
                    }).forPath(prevNodePath);
                } else {
                    continue; // 前一个节点已删除，重新检查
                }

                latch.await();
            }
        }
    }

    public void unlock() throws Exception {
        if (currentNodePath != null) {
            client.delete().forPath(currentNodePath);
        }
    }
}

ZK 锁机制优势：

  • 客户端断开 → 临时节点自动删除 → 锁自动释放
  • Watch 机制 → 准实时通知，无轮询
  • 顺序节点 → 公平锁（先到先得）

三、实际案例

3.1 支付防重

java
@Service
public class PaymentDedupService {

    private final PaymentRepo paymentRepo;
    private final RedissonClient redisson;

    @Transactional
    public PaymentResult pay(String transactionId, PayRequest request) {
        // 1. 分布式锁（按交易ID）
        var lock = redisson.getLock("pay:" + transactionId);
        try {
            if (!lock.tryLock(5, 30, TimeUnit.SECONDS)) {
                throw new ConcurrentPaymentException("支付处理中");
            }

            // 2. 检查是否已支付（唯一索引 + 状态机）
            var existing = paymentRepo.findByTransactionId(transactionId);
            if (existing.isPresent()) {
                var payment = existing.get();
                if (payment.getStatus() == PaymentStatus.SUCCESS) {
                    return new PaymentResult(true, payment, "已支付");
                }
                if (payment.getStatus() == PaymentStatus.PROCESSING) {
                    return new PaymentResult(false, payment, "处理中");
                }
            }

            // 3. 创建支付单 + 处理
            var payment = paymentRepo.save(
                    new Payment(transactionId, PaymentStatus.PROCESSING));

            return doPay(payment, request);
        } finally {
            lock.unlock();
        }
    }
}

3.2 消息重复消费

java
@Component
public class IdempotentMessageConsumer {

    private final StringRedisTemplate redis;

    @KafkaListener(topics = "orders")
    public void onMessage(ConsumerRecord<String, OrderEvent> record, Acknowledgment ack) {
        var msgKey = record.key();
        var msgOffset = record.offset();

        // Kafka offset + partition 作为幂等键
        var idempotentKey = STR."msg:\{record.topic()}:\{record.partition()}:\{msgOffset}";

        // Redis SET NX + TTL 去重
        var success = redis.opsForValue()
                .setIfAbsent(idempotentKey, "processed", Duration.ofHours(24));

        if (Boolean.FALSE.equals(success)) {
            // 已处理过，直接 ACK
            ack.acknowledge();
            return;
        }

        try {
            processOrder(record.value());
            ack.acknowledge();
        } catch (Exception e) {
            // 处理失败，删除标记允许重试
            redis.delete(idempotentKey);
            throw e;
        }
    }
}

3.3 定时任务防重

java
@Component
public class DistributedScheduledTask {

    private final RedissonClient redisson;

    @Scheduled(cron = "0 0 2 * * ?") // 每天凌晨2点
    public void nightlyReindex() {
        var lock = redisson.getLock("scheduled:nightly-reindex");
        if (!lock.tryLock()) {
            log.info("Reindex already running on another instance, skipping");
            return;
        }

        try {
            log.info("Starting nightly reindex...");
            // 可能运行很长时间，看门狗自动续期
            reindexAllDocuments();
            log.info("Nightly reindex completed");
        } finally {
            lock.unlock();
        }
    }
}

常见问题

Q: 幂等 key 应该包含哪些信息？ A: 业务唯一标识（订单号/流水号）+ 操作类型。例如 pay:order:12345:alipay 和 pay:order:12345:wechat 是不同的幂等键。

Q: Redisson 看门狗适合所有场景吗？ A: 不。如果业务逻辑可能死锁或无限循环，看门狗会导致锁永不释放。此时应使用固定 TTL 而非看门狗。

Q: 分布式锁超时了但业务还没执行完怎么办？ A: 使用看门狗（自动续期）或设计分阶段锁（子任务各自加锁，减少单次持锁时间）。

Q: ZK 锁和 Redis 锁的性能差距有多大？ A: Redis（微秒级）比 ZK（毫秒级）快约 10-100 倍。但在多数业务场景这个差距可忽略，选型应以可靠性需求为主。
