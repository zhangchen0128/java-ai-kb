分布式一致性与事务方案

概述

分布式事务是微服务架构中最具挑战性的问题之一。在 AI 应用中，Agent 工具调用涉及多个外部系统、向量索引更新跨多个数据库、异步推理结果需要可靠投递——这些场景都需要合适的分布式事务或一致性保障机制。

本文从一致性模型出发，系统对比 2PC/XA、Saga、TCC、本地消息表、Outbox Pattern 和 Seata 六大方案，提供决策树和 Spring 实现代码。

一、一致性模型回顾

模型 定义 实现复杂度 延迟
强一致性 所有节点看到相同的已提交数据，更新后立即可见 高 高
最终一致性 如果不再更新，最终所有副本收敛到相同值 中 低
因果一致性 有因果关系的写入按顺序被看到 中 中
读己之写 用户总是能看到自己提交的更新 低 低
单调读 不会看到比已读数据的更旧版本 低 低

分布式系统的真实约束（PACELC）：

  • 存在网络分区（P）时，选择可用性（A）还是一致性（C）
  • 无分区（Else）时，选择延迟（L）还是一致性（C）

二、分布式事务方案对比

2.1 2PC / XA

原理：

              Coordinator
              (TM)
          /       |       \
         /        |        \
   Participant  Participant  Participant
      (RM1)       (RM2)        (RM3)

Phase 1 — Prepare（投票）：
  1. TM → all RM: "准备提交"
  2. RM 执行事务但不提交，写 Undo/Redo 日志
  3. RM → TM: "Ready" 或 "Abort"

Phase 2 — Commit/Abort（决策）：
  1a. 所有 RM Ready → TM → all RM: "提交" → 各 RM 提交
  1b. 任一 RM Abort → TM → all RM: "回滚" → 各 RM 回滚

故障分析：

故障点 影响 处理
Participant Prepare 前宕机 TM 超时，Abort 安全
Participant Prepare 后宕机 TM 无法决定 阻塞（最严重问题）
TM Prepare 后宕机 所有 Participant 锁定 需要 TM 恢复后决策
网络分区 可能出现不一致 启发式决策

2PC 评价： 强一致性保证，但性能差（同步阻塞）、单点故障风险（协调者）、锁定时间长。现代微服务架构很少使用。

2.2 Saga

Saga 将一个长事务拆分为多个本地事务序列，每个本地事务有对应的补偿操作。

编排式 (Choreography) vs 协调式 (Orchestration)：

Choreography（去中心化，事件驱动）：
Service A → 事件 → Service B → 事件 → Service C
          ← 补偿事件 ←         ← 补偿事件 ←
优点：松耦合，简单
缺点：流程不可见，循环依赖风险

Orchestration（中心化，协调者驱动）：
Saga Orchestrator
  ├▶ Service A (success)
  ├▶ Service B (success)
  ├▶ Service C (failed!)
  ├▶ Service B (compensate)
  └▶ Service A (compensate)
优点：流程可见，集中控制
缺点：协调者成为单点

核心问题与解决：

问题 描述 解决
正向补偿 后续步骤失败需要回退 每步定义补偿操作
反向补偿 补偿操作本身失败 重试 + 人工干预
空回滚 未成功执行的步骤收到补偿请求 状态机判断（未执行则跳过）
悬挂 补偿先于正向操作到达 幂等 + 唯一键防悬挂
java
// Saga Orchestration 实现
@Service
public class CreateOrderSagaOrchestrator {

    private final OrderService orderService;
    private final InventoryService inventoryService;
    private final PaymentService paymentService;

    public record SagaContext(Long orderId, Long inventoryId, Long paymentId) {}
    public record SagaStepResult(boolean success, String service, String error) {}

    public SagaContext execute(CreateOrderRequest request) {
        var context = new SagaContext(null, null, null);

        try {
            // Step 1: 创建订单
            var order = orderService.createOrder(request);
            context = new SagaContext(order.id(), null, null);

            // Step 2: 锁定库存
            var inventory = inventoryService.reserve(
                    request.productId(), request.quantity(), order.id());
            context = new SagaContext(order.id(), inventory.reservationId(), null);

            // Step 3: 处理支付
            var payment = paymentService.charge(
                    order.id(), request.amount());
            context = new SagaContext(order.id(), inventory.reservationId(), payment.id());

            // Step 4: 确认订单（所有步骤成功）
            orderService.confirmOrder(order.id());
            return context;

        } catch (InsufficientInventoryException e) {
            // 库存不足，补偿已完成的步骤
            if (context.orderId() != null) {
                orderService.cancelOrder(context.orderId());  // 补偿订单
            }
            throw new SagaFailedException("Insufficient inventory", e);

        } catch (PaymentFailedException e) {
            // 支付失败，补偿订单和库存
            if (context.inventoryId() != null) {
                inventoryService.releaseReservation(context.inventoryId());  // 补偿库存
            }
            if (context.orderId() != null) {
                orderService.cancelOrder(context.orderId());  // 补偿订单
            }
            throw new SagaFailedException("Payment failed", e);
        }
    }
}

@Component
public class OrderEventsSaga {

    @EventListener
    public void onOrderCreated(OrderCreatedEvent event) {
        try {
            inventoryService.reserve(event.productId(), event.quantity(), event.orderId());
            eventPublisher.publish(new InventoryReservedEvent(event.orderId(), event.productId()));
        } catch (InsufficientInventoryException e) {

            orderService.cancelOrder(event.orderId());
            eventPublisher.publish(new OrderCancelledEvent(event.orderId(), "INSUFFICIENT_INVENTORY"));
        }
    }

    @EventListener
    public void onInventoryReserved(InventoryReservedEvent event) {
        try {
            paymentService.charge(event.orderId());
            eventPublisher.publish(new PaymentCompletedEvent(event.orderId()));
        } catch (PaymentFailedException e) {
            // 支付失败 → 释放库存 + 取消订单
            inventoryService.releaseReservation(event.reservationId());
            orderService.cancelOrder(event.orderId());
            eventPublisher.publish(new OrderCancelledEvent(event.orderId(), "PAYMENT_FAILED"));
        }
    }
}

2.3 TCC (Try-Confirm-Cancel)

TCC 是 Saga 的变体，每个操作分为三个阶段：

Try（预留资源）:
  - 冻结库存 10 件 → 可用库存 -10，冻结库存 +10
  - 冻结金额 100 元 → 可用余额 -100，冻结金额 +100

Confirm（确认执行）:
  - 扣减冻结库存 → 冻结库存 -10
  - 扣减冻结金额 → 冻结金额 -100

Cancel（取消释放）:
  - 解冻库存 → 冻结库存 -10，可用库存 +10
  - 解冻金额 → 冻结金额 -100，可用余额 +100
java
// TCC 实现（简化版本）
@Service
public class TccTransferService {

    // Try 阶段：冻结资源
    @Transactional
    public void tryTransfer(Long fromAccount, Long toAccount, BigDecimal amount) {
        accountRepo.freezeAmount(fromAccount, amount);  // 冻结转出金额
        accountRepo.freezeAmount(toAccount, BigDecimal.ZERO); // 标记转入准备
        tccLogRepo.insert(fromAccount, toAccount, amount, "TRY");
    }

    // Confirm 阶段：实际扣减
    @Transactional
    public void confirmTransfer(Long tccId) {
        var log = tccLogRepo.findById(tccId);
        accountRepo.deductFrozen(log.fromAccount(), log.amount());
        accountRepo.addBalance(log.toAccount(), log.amount());
        tccLogRepo.updateStatus(tccId, "CONFIRMED");
    }

    // Cancel 阶段：解冻资源
    @Transactional
    public void cancelTransfer(Long tccId) {
        var log = tccLogRepo.findById(tccId);
        accountRepo.unfreeze(log.fromAccount(), log.amount());
        tccLogRepo.updateStatus(tccId, "CANCELLED");
    }
}

TCC vs Saga 对比：

维度 TCC Saga
资源预留 显式预留（Try 阶段） 隐式（直接扣减 + 回退补偿）
隔离性 Try 阶段提供部分隔离 无隔离（其他事务可见中间状态）
实现复杂度 高（每个服务需实现三接口） 中（仅需正向 + 补偿）
适用场景 金融、库存等需严格资源控制 通用业务流程

2.4 本地消息表

原理：在同一数据库事务中将业务操作和消息记录原子写入，然后异步轮询发送消息。

sql
-- 本地消息表
CREATE TABLE event_outbox (
    id BIGSERIAL PRIMARY KEY,
    aggregate_type VARCHAR(100) NOT NULL,
    aggregate_id VARCHAR(100) NOT NULL,
    event_type VARCHAR(200) NOT NULL,
    payload JSONB NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    retry_count INT DEFAULT 0,
    created_at TIMESTAMPTZ DEFAULT NOW(),
    processed_at TIMESTAMPTZ
);

CREATE INDEX idx_outbox_status ON event_outbox(status, created_at);
java
@Service
public class LocalMessageTableService {

    private final OrderRepository orderRepo;
    private final JdbcTemplate jdbc;

    // 原子写入：业务表 + 消息表
    @Transactional
    public void createOrder(Order order) {
        // 1. 写入业务表
        orderRepo.save(order);

        // 2. 写入消息表（同一事务）
        var sql = """
            INSERT INTO event_outbox (aggregate_type, aggregate_id, event_type, payload)
            VALUES (?, ?, ?, ?::jsonb)
            """;
        jdbc.update(sql, "Order", order.getId(), "OrderCreated",
                toJson(order));
    }

    // 定时轮询发送（@Scheduled）
    @Scheduled(fixedDelay = 1000)
    public void pollAndPublish() {
        var events = jdbc.query(
                "SELECT * FROM event_outbox WHERE status = 'PENDING' ORDER BY id LIMIT 100",
                new BeanPropertyRowMapper<>(OutboxEvent.class));

        for (var event : events) {
            try {
                kafkaTemplate.send("orders", event.getAggregateId(),
                        event.getPayload()).get(5, TimeUnit.SECONDS);

                jdbc.update("UPDATE event_outbox SET status = 'SENT', processed_at = NOW() WHERE id = ?",
                        event.getId());
            } catch (Exception e) {
                jdbc.update("""
                    UPDATE event_outbox
                    SET retry_count = retry_count + 1,
                        status = CASE WHEN retry_count >= 10 THEN 'DEAD' ELSE 'PENDING' END
                    WHERE id = ?
                    """, event.getId());
            }
        }
    }
}

2.6 Seata

Seata 提供四种事务模式，满足不同场景：

模式 一致性 性能 侵入性 适用场景
AT 最终一致 高 低（注解即可） 关系数据库 + ACID 要求
TCC 最终一致 高 高（需实现三接口） 金融/库存等严格场景
Saga 最终一致 高 中（补偿接口） 长事务/跨服务
XA 强一致 低 中 需要跨数据库强一致
java
// Seata AT 模式（最常用，完全无侵入）
@Service
public class SeataOrderService {

    @GlobalTransactional(timeoutMills = 300000, name = "create-order-saga")
    public void createOrder(OrderRequest request) {
        // AT 模式自动代理 SQL，解析 UNDO_LOG
        orderRepo.save(request.toOrder());        // 本地事务 1
        inventoryClient.deduct(request.items());  // 远程 RPC → 本地事务 2
        paymentClient.charge(request.amount());   // 远程 RPC → 本地事务 3
    }
}

@Entity
@Table(name = "saga_instance")
public class SagaInstance {
    @Id
    private String sagaId;
    private String sagaType;
    private String status;       // RUNNING, COMPLETED, COMPENSATING, FAILED
    private int currentStep;

    @OneToMany(mappedBy = "saga", cascade = ALL)
    @OrderBy("stepOrder ASC")
    private List<SagaStep> steps;

    public boolean isCompensatable() { /* ... */ }
}

@Entity
@Table(name = "saga_step")
public class SagaStep {
    @Id
    private String stepId;
    private String stepName;
    private int stepOrder;
    private String status; // PENDING, SUCCEEDED, FAILED, COMPENSATED
    private String serviceName;
    private String compensatable;

    @ManyToOne
    @JoinColumn(name = "saga_id")
    private SagaInstance saga;
}

@Service
public class PersistentSagaOrchestrator {

    private final SagaInstanceRepo sagaRepo;
    private final Map<String, SagaStepHandler> handlers;

    public void startSaga(String sagaId, SagaStepHandler... steps) {
        var saga = new SagaInstance(sagaId, "create-order", "RUNNING", 0);
        sagaRepo.save(saga);

        try {
            for (var handler : steps) {
                var stepResult = handler.execute(saga);
                saga.advanceStep(stepResult);
                sagaRepo.save(saga);
            }
            saga.markCompleted();
            sagaRepo.save(saga);
        } catch (Exception e) {
            // 触发补偿
            compensate(saga);
            throw e;
        }
    }

    public void compensate(SagaInstance saga) {
        saga.markCompensating();
        sagaRepo.save(saga);

        // 逆序补偿已完成的步骤
        var completedSteps = saga.getCompletedStepsInReverse();
        for (var step : completedSteps) {
            try {
                var handler = handlers.get(step.getStepName());
                handler.compensate(step);
                step.setStatus("COMPENSATED");
            } catch (Exception e) {
                // 补偿失败，标记需要人工介入
                step.markCompensationFailed(e);
                saga.markFailed();
                sagaRepo.save(saga);
                alertService.sendAlert("Saga compensation failed: " + saga.getSagaId());
                return;
            }
        }
        sagaRepo.save(saga);
    }
}

常见问题

Q: 为什么不用 2PC？ A: 2PC 的同步阻塞、单点故障和长锁定问题使其不适合现代微服务。仅在数据库支持 XA 且对强一致性有硬性要求时使用。

Q: Saga 的补偿事务失败怎么办？ A: 重试机制 + 最终人工干预。补偿操作必须设计为幂等。可配合持久化 Sagastate + 告警。

Q: Outbox Pattern 和本地消息表选哪个？ A: 已部署 Debezium+Kafka 基础设施的团队首选 Outbox（CDC）；精简运维要求的团队用本地消息表+轮询。

Q: 如何保证消息不丢失？ A: Producer 端：本地消息表/Outbox。Broker 端：acks=all + min.insync.replicas >= 2。Consumer 端：手动 ACK + 幂等。

五、Seata 分布式事务实战

5.1 Seata 架构

Seata（Simple Extensible Autonomous Transaction Architecture）是阿里巴巴开源的分布式事务中间件，核心定位是为微服务架构提供高性能、易接入的分布式事务能力。Seata 架构由三个核心角色构成：TC (Transaction Coordinator) 是事务协调器，作为独立进程部署（Seata Server），负责维护全局事务和分支事务的状态，驱动全局提交或全局回滚；TM (Transaction Manager) 是事务管理器，嵌入业务应用，负责定义全局事务的边界——即发起、提交或回滚一个全局事务；RM (Resource Manager) 是资源管理器，同样嵌入业务应用，管理分支事务处理的资源，向 TC 注册分支事务、报告状态，并响应 TC 的提交/回滚指令。

AT（Automatic Transaction）模式是 Seata 使用最广泛、侵入性最低的模式。其核心原理建立在三个关键机制之上。第一是全局锁：在分支事务提交本地事务前，Seata 会向 TC 申请该行数据的全局锁，确保在全局事务存续期间，其他全局事务无法修改同一行——这是一种跨服务的行级锁机制，提供了隔离性保障。第二是 undo_log 表：Seata 通过代理 JDBC 数据源，在每次 DML 操作时自动解析 SQL 语句，生成前镜像（修改前的行数据）和后镜像（修改后的行数据），以 JSON 格式持久化到每个业务数据库的 undo_log 表中。第三是两阶段提交：阶段一（Prepare），各 RM 执行本地事务并提交——注意 AT 模式在阶段一就提交本地事务，释放本地锁，因此对本地数据库连接持有时间极短，性能远优于传统 2PC/XA；阶段二（Commit/Abort），TM 通知 TC 决策，TC 驱动各 RM 异步执行全局提交或全局回滚。如果是全局提交，RM 只需异步删除 undo_log 记录；如果是全局回滚，RM 从 undo_log 中解析前镜像，生成反向 SQL 将数据恢复至修改前状态。undo_log 的清理由 Seata 后台线程周期性完成，不会长期残留。

TCC 模式与 AT 模式在设计哲学上有本质区别。AT 模式依赖 Seata 自动拦截 SQL、管理 undo_log，对业务代码零侵入——开发者只需添加 @GlobalTransactional 注解；而 TCC 模式要求开发者手动实现 try、confirm、cancel 三个接口，资源控制粒度更细、隔离性更强，适用于对金额/库存有严格并发控制要求的金融场景。从隔离性角度看，AT 模式依赖全局锁提供写隔离，但可能出现脏读（因为阶段一已提交本地事务）；TCC 模式通过 Try 阶段的资源预留，天然避免脏读问题。从性能角度看，AT 模式在绝大多数 OLTP 场景下性能优于 TCC，因为 TCC 的 Try 阶段需要进行显式的冻结操作，涉及更多 SQL 交互。选择原则是：一般业务优先 AT 模式降本增效；资金账户、库存扣减等需要严格资源隔离的场景使用 TCC 模式。

@GlobalTransactional 注解是 Seata 对业务代码的唯一侵入点，标注在发起全局事务的方法上。该注解支持以下核心属性：timeoutMills 控制全局事务超时（默认 60s，长事务建议适当放大）；name 为全局事务命名，便于在 Seata Dashboard 中追踪和排查；rollbackFor 和 noRollbackFor 控制哪些异常触发回滚，默认为任何未捕获异常都回滚。需要注意：@GlobalTransactional 标注的方法内部，每个远程 RPC 调用或跨数据库操作会开启一个分支事务，分支事务在本地数据库层面上各自提交，最终由 TC 协调全局决策。如果全局事务超时，TC 会向所有已注册的分支事务发送回滚指令。

全局锁冲突是 AT 模式在生产中最常见的问题。当两个全局事务同时修改同一行数据时，第二个事务的分支提交阶段会发现全局锁已被第一个事务持有，此时 Seata 会进入锁等待模式。默认锁等待时间是 10 秒（可通过 seata.client.rm.lock.lock-retry-interval 和 lock-retry-times 调整），超时后抛出 LockConflictException。处理全局锁冲突的最佳实践包括：（1）尽量减少全局事务持有锁的时间，将被锁操作放在分支事务末尾；（2）在设计层面通过业务分区避免热点行竞争，比如按用户 ID 或订单 ID 分片；（3）对于无法避免的热点场景，使用 TCC 模式替代 AT 模式，因为 TCC 的 Try 阶段就可以通过资源冻结判断冲突并快速失败，避免长期等待。

java
// 全局事务入口 + 锁冲突处理
@Service
public class OrderGlobalTxService {

    private final OrderRepo orderRepo;
    private final InventoryClient inventoryClient;
    private final AccountClient accountClient;

    @GlobalTransactional(
            timeoutMills = 120_000,
            name = "order-create-global-tx",
            rollbackFor = {Exception.class},
            noRollbackFor = {IllegalArgumentException.class})
    public OrderResult createOrder(OrderRequest request) {
        // 分支事务 1：写入订单表（本地数据库）
        var order = orderRepo.save(request.toOrder());

        try {
            // 分支事务 2：远程调用库存服务扣减库存
            inventoryClient.deduct(
                    request.productId(), request.quantity(), order.getId());
        } catch (LockConflictException e) {
            // 全局锁冲突：库存热点行被占用
            // 策略：重试或降级提示用户
            throw new RetryableException("库存暂时繁忙，请稍后重试", e);
        }

        try {
            // 分支事务 3：远程调用账户服务扣款
            accountClient.debit(
                    request.userId(), request.totalAmount(), order.getId());
        } catch (Exception e) {
            // 账户扣款失败 → Seata 自动回滚分支 1 和 2
            // 无需手动补偿，AT 模式自动执行 undo_log 回滚
            throw e;
        }

        return new OrderResult(order.getId(), "SUCCESS");
    }
}

5.3 实际案例：订单-库存-账户 Saga 编排

以下是一个完整的电商下单案例，展示如何使用 Seata 的 Saga 模式编排订单服务、库存服务和账户服务，每个步骤都定义了正向操作和补偿操作。在 JDK 25 + Spring Boot 4.x 技术栈下，利用 Seata Saga 的状态机 DSL（基于 JSON 或 YAML 定义流程）或 Java 注解式 @Compensable 均可实现，本案例采用注解式实现以保持代码在单文件内可读。

java
// ==================== 订单服务 ====================
@Service
public class OrderSagaService {

    // 步骤1 正向：创建订单（状态 PENDING）
    @Compensable(compensateMethod = "cancelOrder")
    public Order createOrder(OrderRequest request) {
        var order = new Order();
        order.setUserId(request.userId());
        order.setProductId(request.productId());
        order.setQuantity(request.quantity());
        order.setAmount(request.amount());
        order.setStatus("PENDING");
        return orderRepo.save(order);
    }

    // 步骤1 补偿：取消订单
    public void cancelOrder(OrderRequest request) {
        var order = orderRepo.findByRequestId(request.requestId());
        if (order == null) return;                                    // 空回滚防护
        if ("CANCELLED".equals(order.getStatus())) return;            // 幂等防护
        order.setStatus("CANCELLED");
        orderRepo.save(order);
    }
}

// ==================== 库存服务 ====================
@Service
public class InventorySagaService {

    // 步骤2 正向：冻结库存
    @Compensable(compensateMethod = "releaseInventory")
    public void freezeInventory(Long productId, Integer quantity, String sagaId) {
        var rows = inventoryRepo.freeze(productId, quantity, sagaId);
        if (rows == 0) {
            throw new InsufficientInventoryException("库存不足: productId=" + productId);
        }
    }

    // 步骤2 补偿：释放冻结库存
    public void releaseInventory(Long productId, Integer quantity, String sagaId) {
        inventoryRepo.unfreeze(productId, quantity, sagaId);
    }
}

// ==================== 账户服务 ====================
@Service
public class AccountSagaService {

    // 步骤3 正向：扣减余额
    @Compensable(compensateMethod = "refundAccount")
    public void debitAccount(Long userId, BigDecimal amount, String sagaId) {
        var rows = accountRepo.debit(userId, amount, sagaId);
        if (rows == 0) {
            throw new InsufficientBalanceException("余额不足: userId=" + userId);
        }
    }

    // 步骤3 补偿：退回金额
    public void refundAccount(Long userId, BigDecimal amount, String sagaId) {
        accountRepo.credit(userId, amount, sagaId);
    }

    // 防悬挂检查：如果 Cancel 先于 Try 到达（网络延迟等极端情况）
    public boolean isCompensationAhead(String sagaId) {
        return sagaLogRepo.existsBySagaIdAndStatus(sagaId, "COMPENSATED");
    }
}

// ==================== Saga 编排入口 ====================
@Service
public class CreateOrderSagaOrchestrator {

    private final OrderSagaService orderSagaService;
    private final InventorySagaService inventorySagaService;
    private final AccountSagaService accountSagaService;

    @GlobalTransactional(timeoutMills = 300_000, name = "create-order-saga")
    public SagaResult execute(OrderRequest request) {
        var sagaId = UUID.randomUUID().toString();

        // Step 1: 创建订单
        var order = orderSagaService.createOrder(request);

        // Step 2: 冻结库存（失败 → Seata 自动补偿 Step 1）
        inventorySagaService.freezeInventory(
                request.productId(), request.quantity(), sagaId);

        // Step 3: 扣减账户余额（失败 → Seata 自动补偿 Step 2 → Step 1）
        accountSagaService.debitAccount(
                request.userId(), request.amount(), sagaId);

        // 全部分支成功 → TC 驱动全局提交
        log.info("Saga completed successfully: sagaId={}, orderId={}", sagaId, order.getId());
        return new SagaResult(sagaId, order.getId(), "SUCCESS");
    }
}

该案例的关键设计点包括：（1）每个 @Compensable 注解标注的方法都有对应的 compensateMethod，Seata 在全局回滚时会按逆序调用这些补偿方法；（2）补偿方法内部需要实现空回滚（对未执行的正向步骤，补偿方法直接返回）和幂等防护（重复的补偿请求不会重复操作）——这是 Seata Saga 模式的硬性要求；（3）sagaId 贯穿所有步骤，每个步骤的数据库操作使用 sagaId 作为业务幂等键，防止极端网络延迟导致的正向/补偿乱序问题（防悬挂）；（4）异常抛出即触发全局回滚，开发者无需在业务代码中手动编排补偿链，Seata TC 统一调度。在生产环境中，建议配合 Seata Dashboard 监控全局事务的执行链路，并设置告警规则：全局回滚率超过 5%、全局事务平均耗时超过阈值等指标需要及时响应。

六、选型决策实战

6.1 实战决策矩阵

在企业级 Java 微服务架构中，分布式事务方案的选择是一个多维决策问题，不能仅凭"强一致"或"最终一致"的单一维度做判断。以下决策矩阵覆盖了实际项目中最常见的五种场景，结合业务特性、基础设施现状和团队能力给出推荐方案及理由。

场景 推荐方案 原因
同数据库多表 Spring @Transactional 单数据库内的 ACID 事务由数据库本身保证，无需引入任何分布式事务框架。同一个 DataSource 下的多表操作天然在同一个本地事务中，性能最优、复杂度最低。即使应用拆分为多个微服务，只要它们共享同一个数据库实例，就仍然可以用本地事务。
同步RPC+强一致要求 Seata AT 当业务需要通过同步 RPC（REST/gRPC/Dubbo）调用多个服务、且要求整体提交或整体回滚时，Seata AT 是平衡一致性和侵入性的最优解。AT 模式对业务代码仅需一个 @GlobalTransactional 注解，自动拦截 JDBC SQL 并管理 undo_log，无需开发者手写补偿逻辑。相比 2PC/XA，AT 在阶段一即提交本地事务，连接持有时间短、吞吐量高；相比 TCC，AT 的接入成本低一个数量级。
异步解耦+最终一致 Saga + Outbox 当业务使用消息队列（Kafka/RabbitMQ）做异步解耦、且对延迟不敏感时，Saga + Outbox 组合是最稳妥的选择。Outbox 模式确保业务操作和消息发布的原子性（同一数据库事务），Debezium CDC 以毫秒级延迟将 Outbox 事件推送至 Kafka；Saga 编排器消费事件后驱动流程。该方案的优势是全异步、高可用——即使某个消费者临时故障，消息不会丢失，Saga 流程可从中断点恢复。代价是架构复杂度较高，需要维护 CDC Connector 和 Kafka 集群。
高性能+弱依赖 TCC 当全局事务的性能是最高优先级的考量维度、且各个服务之间的依赖相对独立时，TCC 模式通过资源预留（Try 阶段）实现了细粒度的并发控制。与 AT 模式的全局锁等待不同，TCC 在 Try 阶段就能快速判断资源是否可满足——比如冻结库存、冻结资金——如果资源不足则立即失败，不会持有数据库行锁等待。这种"先检查、再操作"的模式大幅降低了锁冲突概率，适用于高并发秒杀、抢购等场景。代价是每个服务需实现 Try/Confirm/Cancel 三个接口，开发成本显著高于 AT 模式。
已有Kafka基础设施 Outbox + Debezium 如果团队已有成熟的 Kafka 集群和完善的 CDC 基础设施（如 Debezium + Kafka Connect），那么 Outbox + Debezium 是运维成本最低的扩展方案。不需要引入新的中间件（如 Seata Server），不需要修改业务服务的部署架构，只需在现有数据库中添加 Outbox 表并在业务代码中原子写入、然后配置 Debezium Connector 监听该表的变更——即可获得可靠的跨服务事件驱动能力。该方案的局限在于只适用于最终一致性场景，且要求所有参与服务都能消费 Kafka 事件。

补充一个决策速记口诀，帮助在技术评审时快速对齐团队认知："能本地不分布，能异步不同步，能 AT 不 TCC，能 Outbox 不手写消息。" 这四句话分别对应：优先审视是否能通过业务重构消除分布式事务需求；如果可以接受最终一致就不要用同步阻塞方案；在需要同步分布式事务时优先用 AT 而非手写 TCC 接口；在需要异步可靠投递时优先用 CDC 驱动的 Outbox 而非自行实现消息表轮询。

6.2 反模式警告

在分布式事务的实践中，以下三种反模式是导致线上事故和架构腐化的高频原因，开发者必须警惕。

反模式一：用分布式事务解决所有一致性问题。 分布式事务是一个"重型武器"，不应该成为默认选项。许多看似需要分布式事务的场景，实际上可以通过业务建模层面的优化来规避。例如：将原本分布在两个微服务中的"扣库存"和"发积分"合并到同一个服务中操作同一个数据库；或者通过幂等设计允许重复调用而非依赖全局事务的回滚。每引入一个分布式事务框架（Seata 或 Saga 编排器），都意味着增加一个新的故障域——TC 宕机、全局锁超时、补偿失败等都需要配套监控和应急预案。因此，在决定使用分布式事务之前，必须先回答一个问题："能否通过调整服务边界或数据库分片策略消除跨数据库的场景？" 只有在确认无法规避时，才引入分布式事务。

反模式二：在循环中开启全局事务。 这是一个性能杀手，常见于批量操作场景——比如批量导入订单、批量发放优惠券时，开发者在 for 循环内部为每一行数据启动一个全局事务。每个全局事务至少涉及：TM 向 TC 注册全局事务 → 各 RM 注册分支事务 → 各 RM 执行本地事务并申请全局锁 → TM 通知 TC 提交 → TC 通知所有 RM 提交并释放全局锁。这个过程涉及多次网络往返，在循环中执行会导致数据库连接池耗尽、TC 压力过大、整体吞吐量骤降。正确的做法是将循环中的操作聚合为一个全局事务（如果业务允许批量提交），或者使用 TCC 模式在 Try 阶段完成批量资源冻结后统一 Confirm。

反模式三：让补偿操作依赖外部不可靠服务。 Saga 和 TCC 的补偿操作是事务一致性的最后一道防线，必须保证高可靠性。常见的错误是将补偿操作设计为依赖外部不可靠的 HTTP API（如通知第三方支付网关退款），一旦该外部服务不可用，补偿失败直接导致数据不一致。补偿操作的依赖链应遵循以下原则：（1）补偿操作只操作本地数据库，尽最大可能消除外部依赖；（2）如果必须调用外部服务进行补偿（如退款），应采用异步重试 + 死信队列机制，确保补偿最终成功而不是一次调用失败即放弃；（3）补偿操作必须有完整的可观测性：记录补偿日志、发出告警、支持人工介入。生产环境的经验法则是：补偿操作的可用性要求必须大于等于正向操作的可用性要求，否则 Saga 的整体一致性底线就会由补偿操作的可用性决定。如果团队无法保证补偿操作的高可用，那么该场景不适合使用 Saga 或 TCC 模式，应回归到 Outbox + 异步重试的最终一致性方案。
