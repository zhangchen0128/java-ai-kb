一、Pre-training（预训练）

预训练是 LLM 的第一阶段：在海量无标注文本上，通过自监督学习让模型掌握语言的统计规律、世界知识和推理能力。预训练决定了模型的"智商天花板"。

1.1 自监督学习 (Self-Supervised Learning)

预训练不需要人工标注，而是从文本本身构造监督信号。三种核心范式：

MLM（掩码语言模型 / Masked Language Model）

BERT 系列使用的训练目标。随机 mask 掉输入中 15% 的 token，让模型预测被 mask 的 token。

输入:  "The [MASK] sat on the [MASK]"
目标:  预测 "cat"        预测 "mat"

关键设计（BERT 的 80/10/10 规则）：
  - 80% 替换为 [MASK]     → 训练模型学会"填空"
  - 10% 保持原 token       → 防止训练-推理 mismatch
  - 10% 替换为随机 token   → 防止模型只依赖 [MASK] 标记

MLM 的核心优势是双向上下文：每个 token 可以同时看到左边和右边的信息。这使它特别适合理解类任务（分类、NER、问答），但不适合自回归生成。

CLM（因果语言模型 / Causal Language Model）

GPT 系列的标准训练目标。给定前 N 个 token，预测第 N+1 个。模型只能看到"左边"的上下文（单向），通过自回归逐个生成 token。

$$\mathcal{L}{\text{CLM}} = -\sum{t=1}^{T} \log P(x_t | x_{<t}; \theta)$$

CLM 是当今 LLM 的主流范式。原因：

  1. 统一性：任何 NLP 任务都可以表达为"给定前缀预测下一个 token"
  2. 生成能力：天然支持自回归文本生成
  3. 扩展性：GPT-3 证明 CLM 在足够大时涌现出 in-context learning

对比学习 (Contrastive Learning)

Embedding 模型训练的核心范式。核心思想：拉近正样本对（语义相似的文本），推远负样本对（语义不相似的文本）。

对比学习示意图：
  ┌─────────┐         ┌─────────┐
  │  Query  │────────►│  Pos    │  拉近（相似）
  └─────────┘         └─────────┘
       │
       │    ┌─────────┐
       └───►│  Neg₁   │  推远（不相似）
            └─────────┘
            ┌─────────┐
            └─────────┘← Neg₂ → 推远

典型损失函数（InfoNCE）：
  L = -log( exp(sim(q, pos)/τ) / Σ exp(sim(q, all)/τ) )

对比学习的关键设计选择：

  • 正样本构造：同文档的不同片段、同一段落的两个句子、query-answer 对
  • 负样本选择：in-batch negatives（同一 batch 中的其他样本）、hard negatives（相似但无关的样本）
  • 温度 τ：控制分布的尖锐程度，τ 越小对正负样本区分越"严格"

这对 Java 开发者的启示：当你在 SaaS 应用中切换 Embedding 模型时，新模型的对比学习策略决定了它在你的数据上的表现是否一致。

1.2 数据规模与质量

预训练数据的质量直接影响下游表现。以下是数据工程的关键维度：

数据混合策略：

典型预训练数据的组成（以 LLaMA 2 为例）：
┌──────────────────────────────────────────────┐
│  高质量数据（书籍、论文、Wikipedia）  ~15%    │  ← 知识密度最高
│  中等质量数据（网页、论坛、新闻）    ~70%    │  ← 多样性来源
│  代码数据（GitHub、StackOverflow）   ~10%    │  ← 推理能力来源
│  多语言数据                          ~5%     │  ← 多语言能力
└──────────────────────────────────────────────┘

去重（Deduplication）：

重复数据会导致模型"记忆"而非"泛化"。三个层级：

层级 方法 目的
文档级去重 MinHash / SimHash 删除完全或近似重复的文档
段落级去重 N-gram 重叠 + 阈值过滤 删除大段重复内容（模板生成）
跨语言去重 翻译后去重 防止多语言版本的相同内容

毒性过滤（Toxicity Filtering）：

  • 分类器筛选有害内容（仇恨言论、暴力、色情）
  • 关键词黑名单 + 上下文语义分析
  • 人工审核高风险样本

数据质量 > 数据数量：

Chinchilla Scaling Law（见下一节）的核心结论：对于给定的计算预算，更多高质量数据比更大模型更划算。这改变了"堆参数"的惯性思维。

1.3 Scaling Law（缩放定律）

Scaling Law 是预训练阶段最重要的理论发现之一，它揭示了模型性能与参数量、数据量、计算量之间的数学关系。

Kaplan (OpenAI, 2020)

最早系统研究 LLM 缩放规律的论文。核心发现：

$$\text{Loss} \propto \left(\frac{1}{N}\right)^{\alpha_N} + \left(\frac{1}{D}\right)^{\alpha_D} + \text{irreducible}$$

其中 N 是参数量，D 是数据量，α 是各维度的幂律指数。

Kaplan 的结论倾向于：给定计算预算，应优先增加参数量而非数据量。

Chinchilla (DeepMind, 2022)

对 Kaplan 结论的重要修正。通过训练超过 400 个不同规模的模型（从 70M 到 16B 参数），发现：

最优参数/数据比例约为 1:20（每个参数配 20 个 token）。

Chinchilla 的工程意义：

假设你有 1e24 FLOPs 的计算预算：
  - Kaplan 建议：训练 500B 参数的模型，用 200B token
  - Chinchilla 建议：训练 70B 参数的模型，用 1.4T token
  - 结果：70B 模型表现更好！

Chinchilla 的另一个重要发现：大多数大模型都是 Undertrained（训练不足）。
例如 GPT-3 (175B) 在 300B token 上训练，按照 Chinchilla 最优比例
应该在 3.5T token 上训练——差了近 10 倍。

对 Java 开发者的应用层启示：

  1. 模型选择时：不要只看参数量。一个充分训练的 7B 模型可能比训练不足的 13B 模型更好
  2. 关注"训练 token 数"：查看模型卡上的训练数据量，判断模型是否训练充分
  3. 小模型 + 多数据 > 大模型 + 少数据：这对成本敏感的应用场景是利好

二、SFT（监督微调 / Supervised Fine-Tuning）

预训练后的模型是一个"什么都懂但不太会聊天"的基座。SFT 通过高质量的指令-回答对，让模型学会遵循指令、保持对话格式、输出符合人类期望的内容。

2.1 指令数据构建

SFT 数据的标准格式是 (Instruction, Input, Output) 三元组：

json
// 典型 SFT 数据格式
{
  "instruction": "将以下文本翻译成英文",
  "input": "人工智能正在改变世界",
  "output": "Artificial intelligence is changing the world"
}

// 多轮对话格式（Chat Template）
{
  "messages": [
    {"role": "system", "content": "你是一个专业的编程助手"},
    {"role": "user", "content": "用 Java 写一个二分查找"},
    {"role": "assistant", "content": "public static int binarySearch..."},
    {"role": "user", "content": "加上输入校验"},
    {"role": "assistant", "content": "加上边界检查后..."}
  ]
}

数据来源的三条路径：

路径 成本 质量 规模 适用场景
人工标注 极高 最高 小 关键任务/合规场景
模型生成 + 人工筛选 中等 中高 中 Self-Instruct 范式
强模型蒸馏 低 取决于 teacher 大 通用能力提升

Self-Instruct 范式（2022）：

Self-Instruct 的迭代流程：
┌─────────────────────────────────────────────────────┐
│  1. Seed Tasks（种子任务，如 175 个人工编写的指令）   │
│           ↓                                          │
│  2. GPT-4 根据 Seed 生成更多多样化指令               │
│           ↓                                          │
│  3. GPT-4 为每个指令生成回答（输入+输出）            │
│           ↓                                          │
│  4. 人工筛选：去除低质量、重复、错误数据              │
│           ↓                                          │
│  5. 将筛选后的数据加入训练集 → 微调小模型            │
│           ↓                                          │
│  6. 评估效果 → 如不够好 → 回到步骤 2               │
└─────────────────────────────────────────────────────┘

2.2 数据质量 > 数据数量

LIMA 论文（2023）的惊人发现： 仅用 1000 条精心挑选的高质量指令微调 LLaMA 65B，即可达到接近 GPT-4 的水平。这证明了精选数据 >> 海量数据。

数据质量的三条筛选标准：

  1. 多样性：覆盖不同任务类型（翻译、摘要、推理、代码、创意写作），避免同质化
  2. 复杂性：包含多步推理任务，而非简单的单步回答
  3. 正确性：答案准确无误。错误答案的毒害远大于"不回答"

对 Java 开发者的启示： 如果你需要为特定业务场景微调模型（如保险条款解读），把精力放在打磨 500-1000 条高质量的 instruction-output 对上，而不是收集 10 万条低质量数据。

2.3 格式遵循训练

SFT 阶段的关键输出是让模型学会遵循特定的对话格式。这涉及两个方面：

Chat Template：

不同的模型使用不同的特殊 token 来标记对话角色：

LLaMA 3 Chat Template:
<|begin_of_text|><|start_header_id|>system<|end_header_id|>
你是一个有用的助手<|eot_id|>
<|start_header_id|>user<|end_header_id|>

<|start_header_id|>assistant<|end_header_id|>

训练和推理使用同一 template 至关重要。不一致的 template 会导致模型行为异常——这在 Java 应用端通过 HTTP 调用推理服务时，由推理服务（vLLM/Ollama）的 Chat Template 配置决定。

         "name": "get_weather",

三、RLHF（人类反馈强化学习）

RLHF 是让模型输出"符合人类偏好"的关键阶段。预训练让模型"知道很多"，SFT 让模型"会回答问题"，RLHF 让模型"回答得让人喜欢"。

3.1 完整流程

RLHF 的三个阶段：
┌─────────────────────────────────────────────────────────┐
│  Stage 1: SFT（已在第二章介绍）                         │
│    基座模型 → 指令微调 → Policy Model                  │
│                                                         │
│  Stage 2: Reward Model 训练                             │
│    同一 prompt → Policy Model 生成多个回答               │
│    → 人工标注排序（A > B > C > D）                      │
│    → 训练 Reward Model 学习"什么回答更好"               │
│                                                         │
│  Stage 3: PPO 强化学习优化                              │
│    Policy Model 生成回答 → Reward Model 打分            │
│    → PPO 算法更新 Policy（约束不偏离 SFT 太远）         │
└─────────────────────────────────────────────────────────┘

3.2 Reward Model 训练

Reward Model 是一个"打分器"：输入一个 prompt + response，输出一个标量奖励值（越高越好）。

偏好数据的构造：

同一 prompt 下生成 K 个不同回答（K=4 或 8 常见）：
  prompt: "解释什么是量子计算"
  
  Response A: "量子计算是利用量子力学原理..."     ← 人工排序第 1
  Response B: "量子计算是一种新型计算方式..."     ← 人工排序第 2
  Response C: "量子计算就是用量子..."             ← 人工排序第 3
  Response D: "量子计算很难解释..."               ← 人工排序第 4

  偏好对： (A, B) (A, C) (A, D) (B, C) (B, D) (C, D)

Bradley-Terry 排序损失：

$$P(A > B) = \frac{\exp(r_A)}{\exp(r_A) + \exp(r_B)} = \sigma(r_A - r_B)$$

优化目标：最大化所有偏好对中"好回答得分高于差回答"的概率。

关键数据集：

  • Anthropic hh-rlhf：helpful + harmless 偏好数据
  • OpenAI WebGPT comparisons：信息检索场景的人类偏好

3.3 PPO（Proximal Policy Optimization）

PPO 是 RLHF 的核心优化算法，涉及四个模型同时加载：

PPO 的四个模型（显存需求巨大）：
┌─────────────────────────────────────────────────────┐
│  Actor Model：    要优化的策略（即要微调的 LLM）     │
│  Reference Model：SFT 后的冻结副本（KL 约束基准）    │
│  Critic Model：   价值网络，估计当前状态的期望奖励    │
│  Reward Model：   打分模型（冻结）                   │
│                                                     │
│  四个模型 → 4× 原模型显存 → 只有大规模 GPU 集群可行  │
└─────────────────────────────────────────────────────┘

KL 散度约束： 限制优化后的策略不要偏离 SFT 策略太远，防止 Reward Hacking（模型学会使用"看起来很合理但实际错误"的回答来获取高分）。

$$\max_\theta \mathbb{E}\left[r(x, y)\right] - \beta \cdot D_{KL}\left(\pi_\theta(y|x) | \pi_{\text{SFT}}(y|x)\right)$$

  • β 越小：越追求高奖励，但可能偏离原有能力
  • β 越大：越保守，保持原有行为

工程复杂度： PPO-RLHF 是最复杂的训练阶段。需要同时加载 4 个模型（对于 70B 模型意味着 280GB+ 的显存）、协调多个分布式训练任务、调参敏感。这也是为什么 DPO 会迅速流行起来。

3.4 DPO（Direct Preference Optimization）

2023 年 Stanford 提出的突破性方法，核心洞察：Reward Model 可以用最优策略反推，从而跳过显式训练 Reward Model 的步骤。

数学推导的关键一步：

在 KL 约束下的最优策略有一个闭式解：

$$\pi^*(y|x) = \frac{1}{Z(x)} \pi_{\text{ref}}(y|x) \exp\left(\frac{1}{\beta} r(x, y)\right)$$

由此可以反解出：

$$r(x, y) = \beta \log \frac{\pi^*(y|x)}{\pi_{\text{ref}}(y|x)} + \beta \log Z(x)$$

将 Reward Model 的表达代入 Bradley-Terry 偏好模型，直接在偏好对上优化策略：

$$\mathcal{L}{\text{DPO}}(\pi\theta; \pi_{\text{ref}}) = -\mathbb{E}{(x, y_w, y_l)}\left[\log \sigma\left(\beta \log \frac{\pi\theta(y_w|x)}{\pi_{\text{ref}}(y_w|x)} - \beta \log \frac{\pi_\theta(y_l|x)}{\pi_{\text{ref}}(y_l|x)}\right)\right]$$

DPO vs PPO 对比：

维度 PPO-RLHF DPO
训练阶段 3 阶段（SFT + RM + PPO） 2 阶段（SFT + DPO）
模型数量 4 个（Actor + Ref + Critic + RM） 2 个（Policy + Ref）
显存需求 极大 约 PPO 的一半
训练稳定性 需要大量调参 相对稳定
理论优雅度 间接优化 直接优化偏好
现状 被 DPO 逐步替代 RLHF 的主流替代方案

DPO 的变体：

  • IPO（Identity Preference Optimization）：解决 DPO 对偏好强度不敏感的问题
  • KTO（Kahneman-Tversky Optimization）：不需要偏好对，只需要单条数据的"好/坏"标签
  • ORPO（Odds Ratio Preference Optimization）：将 SFT 和偏好对齐合并到一个阶段

四、参数高效微调（PEFT）

对于 Java 应用开发者，PEFT 是最实用的微调技术方向。你不需要几百 GB 的 GPU 显存，用一张消费级显卡就可以微调模型。

4.1 LoRA（Low-Rank Adaptation）

LoRA 的核心假设：模型微调时的权重更新矩阵 ΔW 是低秩的。因此可以用两个小矩阵的乘积来近似 ΔW。

LoRA 的数学本质：

原始前向传播： h = W₀x + ΔWx

LoRA 分解：    ΔW ≈ A × B
                A ∈ R^{d×r}  (下投影矩阵)
                B ∈ R^{r×k}  (上投影矩阵)
                r << d, k    (r 是秩，通常 8/16/32)

完整前向传播： h = W₀x + (α/r) · BAx
                             ↑
                         缩放因子，控制 LoRA 更新的幅度

关键参数的选择：

参数 典型值 含义 选择建议
r（秩） 8 / 16 / 32 低秩矩阵的秩 简单任务 r=8；复杂推理 r=32
α（缩放） 16 / 32 LoRA 输出缩放 α=2r 是常见起点
Target Modules Q, K, V, O 哪些层加 LoRA 至少加 Q+V，全加效果更好但参数更多

参数量对比：

LLaMA 2 70B 的微调参数量：
  Full Fine-Tuning：    70,000,000,000 参数（100%）
  LoRA r=8：               40,000,000 参数（0.057%）
  LoRA r=16：              80,000,000 参数（0.114%）
  LoRA r=32：             160,000,000 参数（0.229%）

这意味着：用 LoRA r=16 微调一个 70B 模型，
只需更新总参数的 0.1% → 显存需求从 280GB 降至 ~40GB

Adapter 合并：

LoRA 的一个关键优势：训练完成后可以将 LoRA 权重合并（merge）回原始权重。

合并前推理：
  h = W₀x + (α/r) · BAx
  需要：一次矩阵乘法 + 一次 LoRA 计算（有额外延迟）

合并后推理：
  W_new = W₀ + (α/r) · BA
  h = W_new x
  需要：一次矩阵乘法（零额外延迟）

这意味着你可以用 LoRA 微调一个模型，合并后作为标准的 GGUF/GPU 模型部署，推理时完全没有额外开销。

4.2 QLoRA

QLoRA 是 LoRA + 量化的组合，让在单张消费级 GPU 上微调 65B 模型成为可能。三个关键技术创新：

1. 4-bit NormalFloat (NF4)：

专门为正态分布权重设计的 4-bit 量化格式。假设预训练权重服从 N(0, σ)，NF4 在量化区间上非均匀分配——在概率密度高的区域（均值附近）分配更多量化值，在尾部区域分配更少。

传统 INT4（均匀量化）：
  [-3σ, 3σ] 均分为 16 个区间 → 每个区间宽度相同

NF4（非均匀量化）：
  在 [-σ, σ] 区域分配 ~10 个区间（密度高）
  在 [σ, 3σ] 区域分配 ~5 个区间（密度低）
  在 [-3σ, -σ] 区域分配 ~1 个区间（密度低）
  
结果：相同 4-bit 表示下，NF4 的信息损失更小

2. 双重量化（Double Quantization）：

对量化常数再进行一次量化——将 32-bit 的量化常数（scale + zero-point）压缩为 8-bit。这在模型很大时能节省约 0.5GB 显存。

3. 分页优化器（Paged Optimizers）：

利用 CPU 的统一内存（Unified Memory）机制：当 GPU 显存不足时，自动将优化器状态换出到 CPU 内存，需要时再换回。这防止了 OOM，让训练可以"勉强但能跑"。

QLoRA 的效果：

场景：微调 LLaMA 65B 模型
  Full Fine-Tuning：    ~780 GB 显存  → 需要多卡 A100
  LoRA (BF16)：         ~240 GB 显存 → 需要 3×A100 80GB
  QLoRA (NF4)：          ~48 GB 显存  → 单张 A6000 / RTX 6000

结论：QLoRA 让个人开发者在消费级硬件上微调大模型成为可能。

4.3 Adapter

Adapter 是另一种 PEFT 方法，在 Transformer 层之间插入小型可训练瓶颈网络：

原始 Transformer 层：
  x → Attention → FFN → output

加上 Adapter 后：
  x → Attention → Adapter₁ → FFN → Adapter₂ → output
                    ↑                      ↑
                down-project           down-project
                → activation          → activation
                → up-project           → up-project

Adapter 只在瓶颈网络部分训练，原始模型权重冻结。参数量通常为 d_model × d_bottleneck × 2（例如 4096 × 64 × 2 = 0.5M per layer）。

Adapter vs LoRA：

维度 LoRA Adapter
推理延迟 可 merge，零额外延迟 不可 merge，有额外计算
参数效率 极高（r 很小） 中等（bottleneck 通常 64-256）
实现复杂度 中等 简单
当前流行度 ⭐⭐⭐⭐⭐ ⭐⭐

Adapter 的主要缺点是推理时无法合并回模型，每次推理都有额外的瓶颈网络计算。LoRA 的 merge 能力让它成为 PEFT 的事实标准。

五、量化（Quantization）

量化是将模型的浮点权重压缩为更低精度表示的技术。它直接决定模型能否在你的硬件上运行。对 Java 开发者而言，量化格式的选择影响部署架构。

5.1 GGUF 格式

GGUF（GPT-Generated Unified Format）是 llama.cpp 生态的模型格式，面向 CPU 推理优化和单文件分发。

量化级别与命名规则：

GGUF 的量化命名体系：Q{bits}_{type}_{size}

Q4_0    → 4-bit，统一精度，最小体积
Q4_1    → 4-bit，部分层使用 FP16（已过时，不推荐）
Q4_K_M  → 4-bit，K-quant，中等大小（推荐起点）
Q4_K_S  → 4-bit，K-quant，小体积
Q5_0    → 5-bit，统一精度
Q5_K_M  → 5-bit，K-quant，中等大小（质量的 sweet spot）
Q5_K_S  → 5-bit，K-quant，小体积
Q6_K    → 6-bit，K-quant
Q8_0    → 8-bit，统一精度（几乎无损）
F16     → 16-bit 浮点（全精度的一半）
BF16    → Brain Float 16

K-quant（智能混合精度）：
  重要层（attention、output）→ 使用更高精度
  次要层（部分 FFN）→ 使用更低精度
  通过这种非均匀分配，在相同 bit 下达到更好的质量

GGUF 的适用场景：

  • 本地开发和测试（macOS / Windows 笔记本）
  • CPU-only 推理（边缘设备、低成本服务器）
  • 不需要 GPU 的小规模推理任务

5.2 GPTQ（Post-Training Quantization）

GPTQ 是面向 GPU 的后训练量化方法。不需要重新训练，使用少量校准数据，逐层地对模型进行量化。

工作原理（基于 OBQ 算法）：

GPTQ 的逐层量化流程：
  1. 收集一小批校准数据（通常 128 个样本）
  2. 对每一层：
     a. 获取该层在校准数据上的输入
     b. 逐行（weight row by row）进行量化
     c. 量化每一行后，对剩余未量化的权重做补偿更新
        → 最小化该层的输出误差
  3. 所有层量化完成 → 输出量化模型

核心优势：
  • 不需要反向传播或梯度 → 快速（几小时 vs 几天）
  • 最小化逐层输出误差 → 质量好
  • 面向 GPU 推理优化 → 推理速度快（可以用 CUDA kernel）

5.3 AWQ（Activation-Aware Weight Quantization）

AWQ 的一个精妙发现：不是所有权重同等重要，约 1% 的"显著权重"贡献了大部分输出。

AWQ 的核心洞察：

正常的 LLM 权重分布：
  大多数权重：值很小，接近 0，影响小
  少数权重：值很大（绝对值），显著影响输出

传统 GPTQ 均匀量化的问题：
  对所有权重同等对待 → 显著权重的信息被大量"不重要权重"稀释
  → 量化误差集中在显著权重上 → 模型质量下降明显

AWQ 的解决方案：
  1. 识别显著权重（基于激活值的统计）
  2. 对显著权重所在的 channel 进行 per-channel scaling（放大）
  3. 量化时，放大后的显著权重获得更高的有效精度
  4. 推理时，在 weight 上做相应的 inverse scaling

结果：保护了 1% 的关键权重 → 更少的质量损失

AWQ vs GPTQ（定性对比）：

维度 GPTQ AWQ
质量（同 bit） 基准 通常更好（1-2% gap 优势）
量化速度 较慢（几小时） 较快
推理速度 快 快（更优化的 kernel）
生态支持 vLLM、TGI vLLM、TGI

5.4 量化对模型能力的影响

以下是一个经验性的质量损失参考表：

精度 格式示例 质量损失 推荐场景
FP16 / BF16 原生 0%（基准） 云端 GPU 生产环境
INT8 Q8_0 < 0.5% 几乎无损，推荐优先选择
INT4 (AWQ) AWQ 4-bit 1-3% GPU 显存受限但质量要求较高
INT4 (GPTQ) GPTQ 4-bit 1-3% GPU 显存受限，备选方案
INT4 (GGUF Q4_K_M) GGUF Q4_K_M 2-5% CPU 推理的质量优先方案
INT4 (GGUF Q4_0) GGUF Q4_0 3-8% CPU 推理的极限压缩方案

经验法则：

  1. 能用 FP16/BF16 就不用 INT8
  2. 能用 INT8 就不用 INT4
  3. GPU 推理优先选 AWQ 4-bit（质量优于 GPTQ）
  4. CPU 推理优先选 Q5_K_M（5-bit 是 CPU 推理的 sweet spot）
  5. 不要为了节省显存盲目选低精度——先评估质量损失对你的业务是否可接受

Java 开发者如何验证量化效果： 用同一个评估集对不同量化级别的模型做 A/B 测试，对比输出质量。详见第八节的评估示例。

6.1 主流评估基准

MMLU 详解：

Chatbot Arena（LMSYS）：

这是目前最"真实"的评估方式。系统匿名展示两个模型的输出，用户投票选择哪个更好，通过 Elo 评分体系排名。优势是：

  • 不容易被刷榜（不知道哪两个模型在对比）
  • 反映真实用户偏好而非自动指标
  • 覆盖多种任务类型

6.2 评估陷阱

陷阱 描述 防护
训练数据污染 测试集泄露到训练数据中，模型"见过"考题 关注 Chatbot Arena Elo 而非 paper benchmark
Benchmark 过拟合 针对特定 benchmark 做针对性优化（刷榜） 用多个正交的 benchmark 交叉验证
指标不等于体验 高分不代表实际使用体验好 用你的真实业务数据做评估（Golden Dataset）
语言偏差 英文 benchmark 好不代表中文好 关注 C-Eval / CMMLU 等中文 benchmark

java
/**
 * Embedding 模型迁移的双写策略。
 * 使用 JDK 25 Virtual Threads 并发写入两个索引。
 */
@Service
public class EmbeddingMigrationService {

    private final EmbeddingModel oldModel;  // 旧模型（迁移中）
    private final EmbeddingModel newModel;  // 新模型（迁移目标）
    private final VectorStore oldStore;
    private final VectorStore newStore;

    public EmbeddingMigrationService(
            @Qualifier("bgeSmall") EmbeddingModel oldModel,
            @Qualifier("bgeLarge") EmbeddingModel newModel,
            @Qualifier("oldVectorStore") VectorStore oldStore,
            @Qualifier("newVectorStore") VectorStore newStore) {
        this.oldModel = oldModel;
        this.newModel = newModel;
        this.oldStore = oldStore;
        this.newStore = newStore;
    }

    /**
     * 双写：同时写入新旧两个索引。
     * 使用 Virtual Threads 并发执行，不增加主请求延迟。
     */
    public void dualWrite(Document doc) {
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            // 新索引写入（主路径，必须成功）
            var newTask = scope.fork(() -> {
                var embedding = newModel.embed(doc);
                newStore.add(List.of(new Document(doc.getId(), embedding)));
                return true;
            });

            // 旧索引写入（兼容路径，失败不阻塞）
            var oldTask = scope.fork(() -> {
                try {
                    var embedding = oldModel.embed(doc);
                    oldStore.add(List.of(new Document(doc.getId(), embedding)));
                } catch (Exception e) {
                    log.warn("旧索引写入失败（可以容忍）", e);
                }
                return true;
            });

            scope.join();
            scope.throwIfFailed();
        } catch (Exception e) {
            throw new RuntimeException("新索引写入失败，终止操作", e);
        }
    }

    /**
     * 召回率对比评估：对比两个模型在相同查询下的检索结果。
     */
    public record RecallComparison(
        String query,
        List<String> oldModelResults,
        List<String> newModelResults,
        double oldRecall,
        double newRecall
    ) {}

    public List<RecallComparison> evaluateRecall(List<String> testQueries,
                                                   List<String> groundTruthIds) {
        return testQueries.stream()
            .map(query -> {
                var oldResults = oldStore.similaritySearch(
                    SearchRequest.query(query).withTopK(10));
                var newResults = newStore.similaritySearch(
                    SearchRequest.query(query).withTopK(10));

                double oldRecall = calculateRecall(
                    oldResults, groundTruthIds);
                double newRecall = calculateRecall(
                    newResults, groundTruthIds);

                return new RecallComparison(
                    query,
                    oldResults.stream().map(Document::getId).toList(),
                    newResults.stream().map(Document::getId).toList(),
                    oldRecall, newRecall
                );
            })
            .toList();
    }

    private double calculateRecall(List<Document> results,
                                    List<String> groundTruth) {
        var retrievedIds = results.stream()
            .map(Document::getId)
            .collect(java.util.HashSet::new, java.util.HashSet::add,
                java.util.HashSet::addAll);
        long hits = groundTruth.stream().filter(retrievedIds::contains).count();
        return (double) hits / groundTruth.size();
    }
}

        assertThat(q8Results.avgTokensPerSecond())
            .isLessThanOrEqualTo(q4Results.avgTokensPerSecond() * 1.1);
        System.out.println("\n结论：Q8_0 速度略慢于 Q4_K_M 但质量更高");
        System.out.println("      CPU 推理推荐 Q5_K_M（速度与质量的平衡点）");
    }

示例 2：Embedding 模型切换对比

import org.junit.jupiter.api.BeforeAll;
import org.junit.jupiter.api.Test;
import org.springframework.ai.embedding.EmbeddingModel;
import org.springframework.ai.embedding.EmbeddingRequest;
import org.springframework.ai.ollama.OllamaEmbeddingModel;
import org.springframework.ai.ollama.api.OllamaApi;

import java.util.List;
import java.util.Map;

/**
 * 演示 Embedding 模型切换时的兼容性处理：
 * BGE-small (768维) → BGE-large (1024维) → BGE-M3 (1024维, 多语言)
 */
public class EmbeddingMigrationTest {

    private static OllamaEmbeddingModel smallModel;   // 768 维
    private static OllamaEmbeddingModel largeModel;   // 1024 维
    private static OllamaEmbeddingModel m3Model;      // 1024 维, 多语言

    private static final List<String> TEST_TEXTS = List.of(
        "Java Virtual Threads 是 JDK 21 引入的轻量级线程",
        "分布式事务的 Saga 模式实现",
        "PostgreSQL pgvector 向量检索性能优化",
        "人工智能在保险行业的应用",
        "Spring AI 框架的 ChatClient 使用指南"
    );

    @BeforeAll
    static void setUp() {
        var api = new OllamaApi("http://localhost:11434");
        smallModel = OllamaEmbeddingModel.builder()
            .withOllamaApi(api)
            .withDefaultOptions(OllamaOptions.builder()
                .withModel("bge-small:latest").build())
            .build();
        largeModel = OllamaEmbeddingModel.builder()
            .withOllamaApi(api)
            .withDefaultOptions(OllamaOptions.builder()
                .withModel("bge-large:latest").build())
            .build();
        m3Model = OllamaEmbeddingModel.builder()
            .withOllamaApi(api)
            .withDefaultOptions(OllamaOptions.builder()
                .withModel("bge-m3:latest").build())
            .build();
    }

    record ModelInfo(String name, int dimension,
                     Map<String, float[]> embeddings) {}

    @Test
    void compareEmbeddingModels() {
        var smallInfo = embedAll(smallModel, "BGE-small");
        var largeInfo = embedAll(largeModel, "BGE-large");
        var m3Info = embedAll(m3Model, "BGE-M3");

        System.out.println("===== Embedding 模型对比 =====");
        System.out.printf("BGE-small: %d 维%n", smallInfo.dimension());
        System.out.printf("BGE-large: %d 维%n", largeInfo.dimension());
        System.out.printf("BGE-M3:    %d 维%n", m3Info.dimension());

        // 验证：维度变化意味着向量数据库必须重建索引
        assertThat(smallInfo.dimension()).isNotEqualTo(largeInfo.dimension());
        System.out.println("\n⚠️ BGE-small → BGE-large: 维度变化 768→1024");
        System.out.println("   → 向量数据库必须重建索引");

        assertThat(largeInfo.dimension()).isEqualTo(m3Info.dimension());
        System.out.println("✅ BGE-large → BGE-M3: 维度相同 1024→1024");
        System.out.println("   → 可以尝试复用索引（但仍需验证语义兼容性）");

        // 测试同维度下的语义空间兼容性
        testSemanticCompatibility(largeInfo.embeddings(), m3Info.embeddings());
    }

    private ModelInfo embedAll(EmbeddingModel model, String name) {
        var request = new EmbeddingRequest(TEST_TEXTS, null);
        var response = model.call(request);
        var results = response.getResults();

        Map<String, float[]> embeddings = new java.util.LinkedHashMap<>();
        for (int i = 0; i < TEST_TEXTS.size(); i++) {
            embeddings.put(TEST_TEXTS.get(i), results.get(i).getOutput());
        }

        return new ModelInfo(name,
            results.getFirst().getOutput().length, embeddings);
    }

    /**
     * 测试同维度下的语义空间兼容性：
     * 即使维度相同，不同模型的 Embedding 空间仍可能不同。
     */
    private void testSemanticCompatibility(
            Map<String, float[]> emb1, Map<String, float[]> emb2) {
        double avgSimilarity = 0;
        int count = 0;

        for (var text : emb1.keySet()) {
            float[] v1 = emb1.get(text);
            float[] v2 = emb2.get(text);
            double sim = cosineSimilarity(v1, v2);
            avgSimilarity += sim;
            count++;
        }
        avgSimilarity /= count;

        System.out.printf("%n同一文本在不同模型上的平均余弦相似度: %.4f%n",
            avgSimilarity);
        if (avgSimilarity < 0.95) {
            System.out.println("⚠️ 语义空间不兼容（< 0.95），不建议复用旧索引");
        } else {
            System.out.println("✅ 语义空间兼容（>= 0.95），可以尝试复用索引");
        }
    }

    private double cosineSimilarity(float[] a, float[] b) {
        double dot = 0, normA = 0, normB = 0;
        for (int i = 0; i < a.length; i++) {
            dot += (double) a[i] * b[i];
            normA += (double) a[i] * a[i];
            normB += (double) b[i] * b[i];
        }
        return dot / (Math.sqrt(normA) * Math.sqrt(normB));
    }
}

示例 3：Virtual Threads 并发调用多推理服务进行 A/B 对比

java
import org.junit.jupiter.api.Test;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.time.Instant;
import java.util.List;
import java.util.concurrent.StructuredTaskScope;
import java.util.concurrent.Executors;

import static org.assertj.core.api.Assertions.assertThat;

/**
 * JDK 25 下使用 Virtual Threads 并发调用多个推理服务，
 * 对比不同模型在同一批 prompt 上的表现。
 *
 * 场景：评估 Qwen2.5-7B vs LLaMA 3.1-8B 在你的业务数据上的表现。
 */
public class ModelABComparisonTest {

    // OpenAI 兼容 API endpoint
    private static final String MODEL_A_URL =
        "http://localhost:11434/v1/chat/completions";  // Ollama
    private static final String MODEL_B_URL =
        "http://localhost:8000/v1/chat/completions";   // vLLM

    private static final List<String> BUSINESS_PROMPTS = List.of(
        "解释团体保险中的等待期条款",
        "根据以下信息推荐合适的保险产品：员工200人，IT行业，预算每人2000元/年",
        "批改（Endorsement）在保险业务流程中的作用是什么？"
    );

    record ModelResponse(String modelName, String prompt,
                         String content, Duration latency,
                         int outputTokens) {}

    record ComparisonReport(List<ModelResponse> responses,
                            Duration totalTime) {}

    @Test
    void compareModelsWithVirtualThreads() throws Exception {
        var start = Instant.now();

        // 所有请求完全并发，使用 Virtual Threads
        List<ModelResponse> allResponses;
        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            var tasks = BUSINESS_PROMPTS.stream()
                .flatMap(prompt -> List.of(
                    // 模型 A 的请求
                    scope.fork(() -> callModel(
                        MODEL_A_URL, "Qwen2.5-7B", prompt)),
                    // 模型 B 的请求
                    scope.fork(() -> callModel(
                        MODEL_B_URL, "LLaMA-3.1-8B", prompt))
                ).stream())
                .toList();

            scope.join();
            scope.throwIfFailed();

            allResponses = tasks.stream()
                .map(StructuredTaskScope.Subtask::get)
                .toList();
        }

        var elapsed = Duration.between(start, Instant.now());
        var report = new ComparisonReport(allResponses, elapsed);

        // 打印对比结果
        System.out.println("===== 模型 A/B 对比报告 =====");
        System.out.printf("总耗时（并发）: %dms%n", elapsed.toMillis());
        System.out.printf("并发请求数: %d%n%n",
            BUSINESS_PROMPTS.size() * 2);

        // 按模型分组统计
        var modelA = allResponses.stream()
            .filter(r -> r.modelName().equals("Qwen2.5-7B")).toList();
        var modelB = allResponses.stream()
            .filter(r -> r.modelName().equals("LLaMA-3.1-8B")).toList();

        printStats("Qwen2.5-7B", modelA);
        printStats("LLaMA-3.1-8B", modelB);

        // 打印逐题对比
        System.out.println("\n===== 逐题对比 =====");
        for (var prompt : BUSINESS_PROMPTS) {
            var respA = modelA.stream()
                .filter(r -> r.prompt().equals(prompt))
                .findFirst().orElseThrow();
            var respB = modelB.stream()
                .filter(r -> r.prompt().equals(prompt))
                .findFirst().orElseThrow();

            System.out.printf("""
                题目: %s
                  Qwen2.5-7B:   %dms, %d tokens
                  LLaMA-3.1-8B: %dms, %d tokens
                %n""",
                prompt.substring(0, Math.min(30, prompt.length())) + "...",
                respA.latency().toMillis(), respA.outputTokens(),
                respB.latency().toMillis(), respB.outputTokens());
        }
    }

    private ModelResponse callModel(String url, String modelName,
                                     String prompt) throws Exception {
        var start = Instant.now();

        var requestBody = String.format("""
            {
              "model": "%s",
              "messages": [{"role": "user", "content": "%s"}],
              "temperature": 0.0,
              "max_tokens": 512
            }
            """, modelName.replace(" ", "").toLowerCase(),
            prompt.replace("\"", "\\\""));

        try (var client = HttpClient.newBuilder()
                .connectTimeout(Duration.ofSeconds(30))
                .build()) {

            var request = HttpRequest.newBuilder()
                .uri(URI.create(url))
                .header("Content-Type", "application/json")
                .POST(HttpRequest.BodyPublishers.ofString(requestBody))
                .build();

            var response = client.send(request,
                HttpResponse.BodyHandlers.ofString());

            var elapsed = Duration.between(start, Instant.now());

            // 简化：用逗号粗略估计 token 数
            int tokenEstimate = response.body().split("\\s+").length;

            return new ModelResponse(
                modelName, prompt,
                response.body(), elapsed, tokenEstimate);
        }
    }

    private void printStats(String model, List<ModelResponse> responses) {
        double avgLatency = responses.stream()
            .mapToLong(r -> r.latency().toMillis())
            .average().orElse(0);
        double avgTokens = responses.stream()
            .mapToInt(ModelResponse::outputTokens)
            .average().orElse(0);

        System.out.printf("""
            %s 统计:
              平均延迟: %.0fms
              平均输出Token: %.0f
            %n""", model, avgLatency, avgTokens);
    }
}

九、常见问题

Q1: LoRA 的秩（r）如何选择？

A: r 越大，LoRA 的表示能力越强，但参数也越多。选择策略：

任务类型 推荐 r 理由
格式遵循 / 角色扮演 8 任务简单，不需要太多自由度
领域知识注入 16 平衡参数效率和效果
复杂推理 / 代码生成 32 需要更多自由度来学习新能力
从零学习全新能力 64+ 任务与原模型能力差异大

经验上，r=16 是一个安全的起点。如果效果不够，可以增加到 r=32。r 从 16 增加到 32 的效果提升通常大于从 8 到 16。但 r > 64 的边际收益快速递减。

Q2: 量化和微调能否同时进行？

A: 可以，这就是 QLoRA 的设计目标。QLoRA 在 4-bit 量化的基座模型上使用 LoRA 进行微调：

  • 基座模型权重：加载为 NF4 (4-bit)，冻结不变
  • LoRA 权重：保持在 BF16 精度，参与训练
  • 前向传播：量化的基座权重（去量化 → BF16）+ LoRA 权重
  • 反向传播：只更新 LoRA 参数（BF16），不更新基座权重

这意味着你可以在一张 24GB 显存的 GPU（如 RTX 4090）上微调 70B 模型。

Q3: 如何判断模型是否需要微调，还是直接用 Prompt Engineering？

A: 按以下梯度判断：

尝试顺序（从低成本到高成本）：
1. Prompt Engineering（精心设计 Prompt + Few-shot 示例）
   → 如果效果达标 → 不需要微调
   
2. RAG（检索增强 + 更好的上下文）
   → 如果效果达标 → 不需要微调
   
3. SFT 微调（使用 500-1000 条高质量数据）
   → 如果 Prompt + RAG 仍无法满足需求
   → 特别是：格式遵循、领域术语、特定风格
   
4. DPO 对齐（需要偏好数据）
   → 如果 SFT 后的输出"对但是不够好"
   → 例如：太啰嗦、太保守、格式不够规范

核心判断标准：如果问题是"模型不知道答案"，用 RAG；如果问题是"模型知道答案但回答方式不对"，用微调。

Q4: 微调模型如何评估效果？

A: 三层评估体系：

  1. 自动指标：在业务 Golden Dataset 上计算准确率、BLEU/ROUGE（如果适用）
  2. LLM-as-a-Judge：用 GPT-4/Claude 对新旧模型在相同 prompt 上的输出进行盲评打分
  3. 人工评估：让业务专家对 50-100 个真实业务场景的输出进行打分（好/中/差）
推荐的评估流程：
  Step 1: 用 Golden Dataset（50-100 条真实业务数据）跑自动指标
  Step 2: 随机抽取 30 条，用 LLM-as-a-Judge 盲评
  Step 3: 人工复核 10 条有代表性的样本
  Step 4: 三者一致 → 通过；不一致 → 回溯分析原因

Q5: Embedding 模型升级如何平滑迁移？

A: 核心挑战是维度变化和语义空间漂移。推荐四阶段渐进式迁移（详见第七节 7.3）：

  • 双写（新旧模型同时写，1-2 周）
  • 离线验证（Golden Dataset 评估召回率，1 周）
  • 灰度切换（5% → 100% 逐步切流，1 周）
  • 清理（稳定后删除旧索引）

关键原则：永远保留回滚能力。 在灰度切换的每一个阶段，都需要能快速切回旧模型。

Q6: 预训练、SFT、RLHF 分别贡献了什么能力？

A: 这三个阶段分工明确，各司其职：

阶段 核心贡献 如果跳过会发生什么
Pre-training 语言知识、世界知识、推理能力 模型什么都不懂
SFT 指令遵循、对话格式、任务执行 模型"知道"但不会"聊天"，输出可能是续写而非回答
RLHF/DPO 回答质量、安全性、符合人类偏好 模型会回答问题但可能啰嗦、不安全、不符合期望风格

一个有用的类比：Pre-training 是"上大学学知识"，SFT 是"职业培训学会干活"，RLHF 是"导师带你打磨工作质量"。

Q7: 不同推理服务（vLLM / Ollama / TGI）的量化格式兼容性如何？

A: 这是 Java 开发者部署时最常见的困惑：

格式 vLLM Ollama TGI 备注
GGUF 不支持 原生支持 不支持 Ollama 专用格式
GPTQ 支持 不支持 支持 GPU 推理
AWQ 支持 不支持 支持 GPU 推理，推荐
FP16/BF16 支持 支持 支持 通用，无量化

决策流程：先选部署环境，再选格式。本地开发 → Ollama + GGUF；GPU 生产 → vLLM + AWQ；HuggingFace 生态 → TGI + GPTQ/AWQ。
