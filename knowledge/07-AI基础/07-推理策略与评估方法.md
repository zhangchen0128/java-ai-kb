# Inference and Evaluation

> **性能数据声明：** 除非具体表格同时给出硬件、软件版本、数据规模、参数、
> 测试脚本、运行次数、P50/P95/P99、日期和原始结果链接，否则本文中的精确
> 性能数字均为“示意值，不代表基准结果”，不能用于容量规划或产品比较。

## 概述

推理（Inference）和评估（Evaluation）是 LLM 应用落地的两个关键环节。推理策略决定了模型"怎么说"（如何从概率分布中选择输出），评估方法决定了模型"说得好不好"（如何度量输出质量）。本条目从算法原理、性能优化到评估体系，全面覆盖这两方面。

## 推理策略

模型在每个生成步骤输出的是词汇表上的概率分布（logits → softmax → probabilities）。如何从这个分布中选择下一个 token，就是推理策略的核心问题。

### Greedy Decoding

最简单的策略：每步选择概率最高的 token。

```
Greedy Decoding:
  for each step t:
    probs = softmax(logits[t])
    token_t = argmax(probs)
    if token_t == EOS: break

优点：确定性，速度快，可复现
缺点：
  - 容易陷入重复循环（"I am happy. I am happy. I am happy..."）
  - 缺乏多样性，输出可能不是全局最优（贪心的局部最优 ≠ 全局最优）
```

**重复问题示例**：

```
Prompt: "What is Java?"
Greedy: "Java is a programming language that is a programming language
         that is a programming language..."  ← 陷入循环
```

**为什么 Greedy 会重复**：贪心选择使得之前选过的高概率 token 在后续步骤中仍然保持高概率，形成正反馈循环。

### Temperature 采样

在 softmax 之前对 logits 除以温度参数 T：

$$p_i = \frac{\exp(z_i / T)}{\sum_j \exp(z_j / T)}$$

```
T → 0:  等价于 Greedy（概率分布极度尖锐）
T = 0.7: 推荐用于事实类回答（平衡准确性和自然度）
T = 1.0: 标准采样（使用原始概率分布）
T = 1.5: 增加创造性（概率分布变平）
T → ∞:  等价于均匀分布（完全随机）
```

**Java 实现：**

```java
public class TemperatureSampling {

    /**
     * 应用温度参数后采样
     * @param logits 原始 logits
     * @param temperature 温度参数
     * @param random 随机数生成器
     * @return 采样得到的 token 索引
     */
    public static int sample(float[] logits, float temperature, java.util.Random random) {
        float[] probs = applyTemperature(logits, temperature);
        return sampleFromDistribution(probs, random);
    }

    public static float[] applyTemperature(float[] logits, float temperature) {
        if (temperature <= 0) temperature = 1e-6f;  // 防止除零
        float[] scaled = new float[logits.length];

        // 数值稳定性：减去最大值
        float maxLogit = Float.NEGATIVE_INFINITY;
        for (float l : logits) maxLogit = Math.max(maxLogit, l);

        double sum = 0;
        for (int i = 0; i < logits.length; i++) {
            scaled[i] = (float) Math.exp((logits[i] - maxLogit) / temperature);
            sum += scaled[i];
        }

        for (int i = 0; i < scaled.length; i++) {
            scaled[i] = (float) (scaled[i] / sum);
        }
        return scaled;
    }

    public static int sampleFromDistribution(float[] probs, java.util.Random random) {
        double r = random.nextDouble();
        double cumulative = 0;
        for (int i = 0; i < probs.length; i++) {
            cumulative += probs[i];
            if (r <= cumulative) return i;
        }
        return probs.length - 1;  // 兜底
    }

    /**
     * 演示不同温度的效果
     */
    public static void demonstrate() {
        // 模拟一个词汇表上的 logits
        float[] logits = {3.0f, 2.0f, 1.0f, 0.5f, 0.1f};
        String[] tokens = {"Java", "Python", "Rust", "Go", "C"};

        System.out.println("原始 logits: " + Arrays.toString(logits));
        System.out.println();

        for (float t : new float[]{0.1f, 0.7f, 1.0f, 2.0f}) {
            float[] probs = applyTemperature(logits, t);
            System.out.printf("T=%.1f: ", t);
            for (int i = 0; i < tokens.length; i++) {
                System.out.printf("%s:%.3f ", tokens[i], probs[i]);
            }
            System.out.println();
        }
        // 输出：
        // T=0.1: Java:0.996 Python:0.004 Rust:0.000 Go:0.000 C:0.000  (接近Greedy)
        // T=0.7: Java:0.614 Python:0.239 Rust:0.100 Go:0.035 C:0.012
        // T=1.0: Java:0.506 Python:0.266 Rust:0.148 Go:0.064 C:0.016
        // T=2.0: Java:0.351 Python:0.265 Rust:0.195 Go:0.128 C:0.061  (更平坦)
    }

    public static void main(String[] args) {
        demonstrate();
    }
}
```

### Top-k 采样

只保留概率最高的 k 个 token，将其他的概率设为 0，然后重新归一化采样。

```
Top-k 采样流程：
1. 取概率最高的 k 个 token
2. 将这 k 个 token 的概率重新归一化
3. 从这 k 个 token 中随机采样

k 值选择：
  k = 5-10:  高确定度输出（事实问答、代码生成）
  k = 20-50: 中等创造性（通用对话）
  k = 100+:  高创造性（创意写作、头脑风暴）

问题：固定的 k 无法适应不同上下文
  - 概率已集中在1-2个 token 时，k=50 引入了噪音
  - 概率均匀分布时，k=10 可能切掉了合理选项
```

**Java 实现：**

```java
public class TopKSampling {

    /**
     * Top-K 采样
     * @param logits 原始 logits
     * @param k 保留 top-k 个 token
     */
    public static int sample(float[] logits, int k, java.util.Random random) {
        // 创建索引数组并按 logits 降序排序
        var indices = new Integer[logits.length];
        for (int i = 0; i < logits.length; i++) indices[i] = i;
        Arrays.sort(indices, (a, b) -> Float.compare(logits[b], logits[a]));

        // 保留 top-k
        var filtered = new float[logits.length];
        for (int i = 0; i < k && i < logits.length; i++) {
            filtered[indices[i]] = logits[indices[i]];
        }

        // softmax 归一化 top-k
        float[] probs = TemperatureSampling.applyTemperature(filtered, 1.0f);
        return TemperatureSampling.sampleFromDistribution(probs, random);
    }
}
```

### Top-p (Nucleus) 采样

不固定 token 数量，而是从概率最高的开始累加，直到累积概率超过阈值 p：

```
Top-p 采样流程：
1. 将 token 按概率从大到小排序
2. 从大到小累加，直到累积概率 ≥ p
3. 只保留这些 token，重新归一化采样

p 值选择：
  p = 0.1:  非常保守（通常只保留 1-3 个 token）
  p = 0.5:  中等
  p = 0.9:  常用默认值（保留概率主体的 token）
  p = 0.95: 高创造性
  p = 1.0:  等价于纯 temperature 采样

优势：动态适应不同上下文
  - 概率集中时 → 自动取少（可能只需1-3个token就覆盖90%）
  - 概率均匀时 → 自动取多（可能需要100+个token才覆盖90%）
```

**Java 实现 Top-p 采样：**

```java
public class TopPSampling {

    /**
     * Top-p (Nucleus) 采样
     * @param logits 原始 logits
     * @param p 累积概率阈值 (如 0.9)
     */
    public static int sample(float[] logits, float p, float temperature,
                              java.util.Random random) {
        // 先应用 temperature
        float[] probs = TemperatureSampling.applyTemperature(logits, temperature);

        // 按概率降序排序
        record IndexedProb(int index, float prob) {}
        var sorted = new IndexedProb[probs.length];
        for (int i = 0; i < probs.length; i++) {
            sorted[i] = new IndexedProb(i, probs[i]);
        }
        Arrays.sort(sorted, (a, b) -> Float.compare(b.prob, a.prob));

        // 找 nucleus：累积概率达到 p 的 token 集合
        double cumulative = 0;
        int nucleusSize = 0;
        for (int i = 0; i < sorted.length; i++) {
            cumulative += sorted[i].prob;
            nucleusSize = i + 1;
            if (cumulative >= p) break;
        }

        // 重建概率分布（只有 nucleus 内的）
        var filteredProbs = new float[probs.length];
        double filteredSum = 0;
        for (int i = 0; i < nucleusSize; i++) {
            filteredProbs[sorted[i].index] = sorted[i].prob;
            filteredSum += sorted[i].prob;
        }
        // 重新归一化
        for (int i = 0; i < filteredProbs.length; i++) {
            filteredProbs[i] = (float) (filteredProbs[i] / filteredSum);
        }

        return TemperatureSampling.sampleFromDistribution(filteredProbs, random);
    }

    public static void main(String[] args) {
        // 演示 Top-p 在不同概率分布下的自适应行为
        float[] peakedLogits = {10.0f, 1.0f, 0.5f, 0.2f, 0.1f};  // 尖峰分布
        float[] flatLogits = {2.0f, 1.9f, 1.8f, 1.7f, 1.6f};     // 平坦分布

        var probs = TemperatureSampling.applyTemperature(peakedLogits, 1.0f);
        System.out.println("尖峰分布: " + Arrays.toString(probs));
        // nucleus 很小 (~1-2 tokens)

        probs = TemperatureSampling.applyTemperature(flatLogits, 1.0f);
        System.out.println("平坦分布: " + Arrays.toString(probs));
        // nucleus 很大 (可能全5个都需要)
    }
}
```

### Beam Search

保持 k 个候选序列（beam width），每步从 k × |V| 个候选中选出最优 k 个。

```
Beam Search (beam width = 3):
Step 1: [A:0.5] [B:0.3] [C:0.1]        ← 选 top-3
Step 2: [A→X:0.2] [B→Y:0.15] [A→Z:0.1]  ← 从所有延续中选 top-3
Step 3: ...
最终：返回分数最高的完整序列

得分 = Σ log P(token_t | tokens_{<t})    (对数概率之和)

问题：
  - 对长序列不友好（log prob 始终为负，越长总分越低）
  - 常用长度惩罚：score / length^α
  - 输出可能缺乏多样性（所有 beam 趋同）
```

```java
public class BeamSearch {

    record Beam(double score, List<Integer> tokens) {}

    public static List<Integer> search(
            java.util.function.Function<List<Integer>, float[]> modelForward,
            int beamWidth, int maxLen, int eosTokenId) {

        var beams = new ArrayList<Beam>();
        beams.add(new Beam(0.0, new ArrayList<>()));

        for (int step = 0; step < maxLen; step++) {
            var candidates = new ArrayList<Beam>();

            for (var beam : beams) {
                if (!beam.tokens.isEmpty() &&
                    beam.tokens.get(beam.tokens.size() - 1) == eosTokenId) {
                    candidates.add(beam);  // 保留已完成序列
                    continue;
                }

                float[] logits = modelForward.apply(beam.tokens);
                float[] probs = TemperatureSampling.applyTemperature(logits, 1.0f);

                for (int tokenId = 0; tokenId < probs.length; tokenId++) {
                    var newTokens = new ArrayList<>(beam.tokens);
                    newTokens.add(tokenId);
                    double newScore = beam.score + Math.log(probs[tokenId] + 1e-9);
                    candidates.add(new Beam(newScore, newTokens));
                }
            }

            // 选 top-k candidates
            candidates.sort((a, b) -> Double.compare(b.score, a.score));
            beams = new ArrayList<>(candidates.subList(0,
                Math.min(beamWidth, candidates.size())));
        }

        return beams.get(0).tokens;  // 返回最高分序列
    }
}
```

### 惩罚机制

除了采样策略，还可以通过惩罚项来抑制重复：

```java
public class RepetitionPenalties {

    /**
     * 重复惩罚 (Repetition Penalty)
     * 对已出现的 token 降低其概率
     */
    public static float[] applyRepetitionPenalty(
            float[] logits, Set<Integer> seenTokens, float penalty) {
        // penalty 通常取 1.1-1.5
        // penalty > 1: 惩罚已出现 token（让它们变难出现）
        // penalty = 1: 不惩罚
        // penalty < 1: 鼓励已出现 token（让它们更容易出现）
        float[] penalized = logits.clone();
        for (int tid : seenTokens) {
            if (penalized[tid] > 0) {
                penalized[tid] /= penalty;  // 降低正 logit
            } else {
                penalized[tid] *= penalty;  // 增大负 logit 的绝对值
            }
        }
        return penalized;
    }

    /**
     * 频率惩罚 (Frequency Penalty)
     * 按出现次数降低概率
     */
    public static float[] applyFrequencyPenalty(
            float[] logits, Map<Integer, Integer> tokenCounts, float freqPenalty) {
        float[] penalized = logits.clone();
        for (var entry : tokenCounts.entrySet()) {
            penalized[entry.getKey()] -= freqPenalty * entry.getValue();
        }
        return penalized;
    }

    /**
     * 存在惩罚 (Presence Penalty)
     * 只要出现过就惩罚（不管出现几次）
     */
    public static float[] applyPresencePenalty(
            float[] logits, Set<Integer> seenTokens, float presencePenalty) {
        float[] penalized = logits.clone();
        for (int tid : seenTokens) {
            penalized[tid] -= presencePenalty;  // 出现过就扣分
        }
        return penalized;
    }

    public static void main(String[] args) {
        float[] logits = {3.0f, 2.5f, 1.0f, 0.5f};

        System.out.println("原始: " + Arrays.toString(logits));
        System.out.println("重复惩罚(1.2): " +
            Arrays.toString(applyRepetitionPenalty(logits, Set.of(0), 1.2f)));
        System.out.println("存在惩罚(0.5): " +
            Arrays.toString(applyPresencePenalty(logits, Set.of(0, 1), 0.5f)));
    }
}
```

**惩罚参数配合使用建议：**

| 场景 | Temperature | Top-p | Freq Penalty | Presence Penalty |
|------|-------------|-------|--------------|------------------|
| 事实问答 | 0-0.3 | 0.9 | 0 | 0 |
| 通用对话 | 0.7 | 0.9 | 0.1 | 0.1 |
| 创意写作 | 0.9-1.2 | 0.95 | 0.3 | 0.3 |
| 代码生成 | 0-0.2 | 0.9 | 0 | 0 |
| 头脑风暴 | 1.2-1.5 | 0.95 | 0.1 | 0.5 |

## 推理性能优化

### KV Cache

KV Cache 是 LLM 推理最重要的性能优化。在自回归生成中，每个新 token 需要与所有历史 token 做 attention。如果不缓存，每个 step 都需要重新计算所有历史 token 的 K 和 V。

```
无 KV Cache:
  Step 1: 计算 token1 的 Q,K,V → attention
  Step 2: 计算 token1,token2 的 Q,K,V → attention  ← 重复计算了 token1!
  Step 3: 计算 token1,token2,token3 的 Q,K,V → attention  ← 重复计算了 token1,token2!
  计算量: O(n² × d) 每层每 token（因为重新计算）

有 KV Cache:
  Step 1: 计算 token1 的 Q,K,V → 缓存 K1,V1, attention
  Step 2: 计算 token2 的 Q, K2, V2 → 读取 K1,V1, attention  ← 不重复
  Step 3: 计算 token3 的 Q, K3, V3 → 读取 K1,K2,V1,V2, attention
  计算量: O(n × d²) 每层每 token（只计算新 token）
```

**内存占用分析：**

```
KV Cache 内存 = 2 × num_layers × batch_size × seq_len × num_heads × head_dim × dtype_size

示例（LLaMA 70B, half precision）：
  2 × 80 × 1 × 4096 × 64 × 128 × 2 bytes
  = 2 × 80 × 1 × 4096 × 8192 × 2
  ≈ 10.7 GB (仅 KV Cache!)

扩展到 128K 上下文：
  ≈ 10.7 GB × 32 = 342 GB (恐怖的 KV Cache)
```

### PagedAttention (vLLM)

PagedAttention 是 vLLM 的核心创新，借鉴了操作系统的虚拟内存管理：

```
传统 KV Cache 管理：
  ┌────────────────────────────────────────┐
  │ Token1 KV │ Token2 KV │ Token3 KV │ ...│   ┌─ 连续分配的整块内存
  └────────────────────────────────────────┘   └─ 碎片化严重

PagedAttention (分页管理):
  Block 0: [Tok1, Tok2, Tok3]  ← 一页存多个 token 的 KV
  Block 1: [Tok4, Tok5, Tok6]
  Block 2: [Tok7, Tok8, Tok9]  ← 不要求连续
  Block 3: [空闲]
  Block 4: [Tok10,Tok11,Tok12]

优势：
  1. 零内存碎片（通过动态分配 page）
  2. 内存共享（beam search 中不同 beam 共享同一 prefix 的 KV Cache）
  3. 高吞吐（可把 GPU 内存利用率从 20-40% 提升到 80%+）
```

### Multi-Query / Grouped-Query Attention

标准 Multi-Head Attention (MHA): Q, K, V 各有 h 个头
Multi-Query Attention (MQA): Q 有 h 个头，但 K, V 只有 1 个头（所有 Q 头共享）
Grouped-Query Attention (GQA): Q 有 h 个头，K, V 有 g 个头（g 组，每组共享）

```
MHA (标准):          MQA (极度压缩):       GQA (LLaMA 2 70B):
  Q K V               Q K V                 Q K V
  ■ ■ ■               ■ □ □                 ■ ◇ ◇
  ■ ■ ■     h=4       ■ □ □       h=4       ■ ◇ ◇       h=4
  ■ ■ ■               ■ □ □                 ■ ◆ ◆        g=2
  ■ ■ ■               ■ □ □                 ■ ◆ ◆

KV Cache 大小对比：
  MHA: size ∝ 2 × h     (1x)
  MQA: size ∝ 2 × 1     (1/h x)  ← h=64 时缩小 64 倍!
  GQA: size ∝ 2 × g     (g/h x)  ← g=8, h=64 时缩小 8 倍
```

GQA 是目前的最佳平衡点：LLaMA 2 70B 使用 g=8, h=64，KV Cache 缩小 8 倍，质量几乎无损失。

### Speculative Decoding

用一个小模型（草稿模型，Draft Model）快速生成候选 token，大模型（目标模型，Target Model）一次性验证：

```
Speculative Decoding 流程：
┌──────────────────────────────────────────────────────────┐
│ Step 1: Draft Model 快速生成 k 个候选 token              │
│   Draft(小模型): "The quick brown fox jumps" (5 tokens)  │
│   速度: 2000 tokens/s (小模型快)                         │
│                                                          │
│ Step 2: Target Model 一次性验证所有 k 个 token           │
│   Target(大模型): 前向传播一次，验证 5 个 token           │
│   结果: 前 3 个通过，第 4 个拒绝，第 4 个位置校正         │
│                                                          │
│ Step 3: 返回通过 + 校正的 token                          │
│   Output: "The quick brown fox"  (3 through + 1 corrected)│
│                                                          │
│ 加速比: 2-3x (实际吞吐提升)                              │
└──────────────────────────────────────────────────────────┘
```

**正确性保证**：Target Model 的验证过程确保了输出分布与直接使用 Target Model 完全相同（无质量损失）。

### Continuous Batching

传统 Static Batching 的致命缺陷：一个 batch 中所有请求必须等最长的那个完成才能一起返回。

```
Static Batching:
Batch = [Req1(10 tokens), Req2(100 tokens), Req3(5 tokens)]
  → Req3 和 Req1 完成了，但必须等 Req2 的 100 个 token 生成完
  → GPU 利用率低

Continuous Batching:
  时刻 0: Batch = [Req1, Req2, Req3]
  时刻 1: Req3 完成(EOS) → 立即从 batch 移除，插入新请求 Req4
  时刻 2: Req1 完成 → 移除，插入 Req5
  时刻 3: Batch = [Req2(继续), Req4, Req5]
  → GPU 始终满载，吞吐提升 10x+
```

## LLM 评估方法

### Perplexity

困惑度（Perplexity）是语言模型的最经典指标：

$$\text{PPL} = \exp\left(-\frac{1}{N}\sum_{i=1}^{N} \log P(w_i | w_{<i})\right)$$

```
直观理解：
  PPL = 1:   模型 100% 确定下一个 token（完美，但不现实）
  PPL = 10:  模型平均在 10 个 token 中选择（优秀）
  PPL = 100: 模型平均在 100 个 token 中选择（一般）
  PPL = 词汇表大小：等价于随机猜测

局限性：
  1. PPL 低 ≠ 生成质量高（可能只是学会了重复训练数据）
  2. PPL 高可能只是 tokenizer 差异导致的（不同 tokenizer 的 PPL 不可直接比较）
  3. 无法衡量事实准确性、逻辑一致性、有用性
```

### BLEU / ROUGE

用于机器翻译（BLEU）和文本摘要（ROUGE）的 n-gram 匹配指标：

```
BLEU: 计算生成文本和参考文本之间的 n-gram 精确匹配率
  BLEU-1: unigram 匹配
  BLEU-4: 1-4 gram 的几何平均（最常用）

ROUGE: 计算生成文本和参考文本之间的 n-gram 召回率
  ROUGE-1: unigram 召回率
  ROUGE-2: bigram 召回率
  ROUGE-L: 最长公共子序列 (LCS)

问题：
  - 过于字面：同义表达被视为错误
  - 无法评估创造性和灵活性
  - 在 LLM 时代几乎过时，仅用于极简单的翻译/摘要任务
```

### LLM-as-a-Judge

LLM-as-a-Judge 是目前最实用的 LLM 评估方法。用能力较强的模型来评判另一个模型的输出：

```
LLM-as-a-Judge 工作流：

输入：
  原始问题: "解释Spring Boot自动配置的原理"
  待评估回答: model_A 的输出
  参考标准: 人工编写的 gold answer (可选)

Judge Prompt:
  "你是一个严格的评审。请从以下维度给这段回答打分(1-10)：
   1. 准确性: 技术事实是否正确？
   2. 完整性: 是否覆盖了关键要点？
   3. 清晰度: 表达是否清晰易懂？
   4. 实用性: 是否包含可操作的指导？

   请给出各维度分数和理由。"

输出:
  准确性: 9, 完整性: 7, 清晰度: 8, 实用性: 8
  理由: ...
```

**Java LLM-as-a-Judge 实现：**

```java
import java.util.*;

public class LlmAsJudge {

    public record EvaluationDimension(String name, String description, double weight) {}

    public record EvaluationResult(
        Map<String, Double> scores,
        double weightedScore,
        String reasoning
    ) {
        @Override
        public String toString() {
            var sb = new StringBuilder();
            sb.append(String.format("总分: %.1f/10\n", weightedScore));
            sb.append("--- 各维度 ---\n");
            scores.forEach((dim, score) ->
                sb.append(String.format("  %s: %.1f/10\n", dim, score)));
            sb.append("--- 评语 ---\n").append(reasoning);
            return sb.toString();
        }
    }

    private final List<EvaluationDimension> dimensions;

    public LlmAsJudge(List<EvaluationDimension> dimensions) {
        this.dimensions = dimensions;
    }

    /**
     * 构建 Judge Prompt
     */
    public String buildJudgePrompt(String question, String answer, String reference) {
        var sb = new StringBuilder();
        sb.append("你是一个严格的评审。请从以下维度评估回答质量：\n\n");

        for (int i = 0; i < dimensions.size(); i++) {
            var dim = dimensions.get(i);
            sb.append(String.format("%d. %s: %s\n", i + 1, dim.name(), dim.description()));
        }

        sb.append("\n【问题】\n").append(question).append("\n\n");
        sb.append("【待评估回答】\n").append(answer).append("\n\n");

        if (reference != null && !reference.isBlank()) {
            sb.append("【参考答案】\n").append(reference).append("\n\n");
        }

        sb.append("请以 JSON 格式返回各维度的 1-10 评分和简要理由。");

        return sb.toString();
    }

    /**
     * 多模型 Panel（多裁判取平均）
     * 每维度的最终分数 = 所有裁判的分数去掉最高最低后取平均
     */
    public EvaluationResult panelEvaluation(
            List<Map<String, Double>> judgeResults) {
        var finalScores = new LinkedHashMap<String, Double>();

        for (var dim : dimensions) {
            var dimScores = judgeResults.stream()
                .map(r -> r.get(dim.name()))
                .sorted()
                .toList();

            // 去掉最高最低
            double sum = 0;
            int count = 0;
            for (int i = 1; i < dimScores.size() - 1; i++) {
                sum += dimScores.get(i);
                count++;
            }
            finalScores.put(dim.name(), count > 0 ? sum / count : dimScores.get(0));
        }

        double weightedSum = 0;
        double totalWeight = 0;
        for (var dim : dimensions) {
            weightedSum += finalScores.get(dim.name()) * dim.weight();
            totalWeight += dim.weight();
        }

        return new EvaluationResult(finalScores,
            weightedSum / totalWeight, "Panel 综合评定");
    }

    /**
     * 位置偏差检测
     * 如果答案在前的分数显著高于答案在后 → 存在位置偏差
     */
    public static boolean detectPositionBias(
            double scoreWhenFirst, double scoreWhenSecond, double threshold) {
        return Math.abs(scoreWhenFirst - scoreWhenSecond) > threshold;
    }

    public static void main(String[] args) {
        var dims = List.of(
            new EvaluationDimension("准确性", "技术事实是否正确", 0.4),
            new EvaluationDimension("完整性", "是否覆盖关键要点", 0.2),
            new EvaluationDimension("清晰度", "表达是否清晰", 0.2),
            new EvaluationDimension("实用性", "是否包含可操作指导", 0.2)
        );

        var judge = new LlmAsJudge(dims);
        var prompt = judge.buildJudgePrompt(
            "解释 CAP 理论",
            "CAP 理论是说分布式系统中一致性、可用性、分区容错性只能同时满足两个。",
            "CAP 定理由 Eric Brewer 在 2000 年提出..."

        );
        System.out.println(prompt);
    }
}
```

**位置偏差问题：**

LLM-as-a-Judge 的一个已知问题是位置偏差（Position Bias）-- 模型倾向于给先出现的回答更高分。

```
Position Bias 检测：
1. A vs B: 给 A 的打分 (4.5/5)
2. B vs A (交换位置): 给 B 的打分 (4.2/5)
  → 位置偏差 = (4.5 + 4.2) / 2 的差异 ≈ 0.3

缓解策略：
  - 双次评估：每个答案在第一位次各评一次取平均
  - 随机打乱：输出前先随机排列，减少系统偏差
  - 多模型 Panel：不同模型的偏好不同，取平均
```

### Arena Elo

LMSYS Chatbot Arena 是当前最有影响力的 LLM 评估平台。使用 Bradley-Terry 模型计算 Elo 分数。

```
Chatbot Arena 流程：
1. 用户输入任意问题
2. 系统随机选择两个匿名模型，同时生成回答
3. 用户投票（A更好/B更好/平局/都差）
4. 根据所有投票计算 Elo 分数

Elo 计算 (Bradley-Terry Model):
  P(model_i beats model_j) = σ(Elo_i - Elo_j)
  其中 σ 是 sigmoid 函数

优势：真实用户、真实问题、客观偏好
劣势：偏向英语、受用户群体偏好影响、无法评估具体维度
```

```java
public class HumanEvalEvaluator {

    /**
     * pass@k = 1 - C(n-c, k) / C(n, k)
     * 其中 n = 总生成数, c = 正确数, k = k
     */
    public static double passAtK(int totalGenerations, int correctCount, int k) {
        if (totalGenerations - correctCount < k) return 1.0;
        return 1.0 - combination(totalGenerations - correctCount, k)
                     / combination(totalGenerations, k);
    }

    private static double combination(int n, int k) {
        if (k > n) return 0;
        if (k == 0 || k == n) return 1;
        double result = 1;
        for (int i = 1; i <= k; i++) {
            result = result * (n - k + i) / i;
        }
        return result;
    }

    /**
     * 验证代码正确性（简化：编译+运行测试用例）
     */
    public static boolean verifyCode(String generatedCode, List<TestCase> testCases) {
        // 实际实现需要：
        // 1. 在沙箱中编译代码
        // 2. 运行所有测试用例
        // 3. 所有测试通过才返回 true
        return true; // 简化
    }

    record TestCase(String input, String expectedOutput) {}

    public static void main(String[] args) {
        // pass@1: 生成 10 份代码，其中 4 份正确
        System.out.println("pass@1 = " + passAtK(10, 4, 1));  // 0.4
        // pass@10: 同上，但 k=10
        System.out.println("pass@10 = " + passAtK(10, 4, 10)); // 1.0
    }
}
```

## 推理策略选择决策树

```
你需要什么样的输出？
├── 确定性 + 可复现
│   └── Greedy (Temperature=0) + 不需要惩罚
│       场景：事实提取、分类、数据转换
│
├── 高准确性 + 一定自然度
│   └── Temperature=0.3 + Top-p=0.9
│       场景：代码生成、事实问答、API 调用
│
├── 自然对话
│   └── Temperature=0.7 + Top-p=0.9 + FreqPenalty=0.1 + PresencePenalty=0.1
│       场景：客服对话、通用聊天
│
└── 高创造性
    └── Temperature=1.0-1.5 + Top-p=0.95 + PresencePenalty=0.3
        场景：创意写作、头脑风暴、故事生成
```

## 最佳实践

1. **默认推理参数**：Temperature=0.7, Top-p=0.9, FreqPenalty=0.1, PresencePenalty=0.1，这是绝大多数场景的合理起点
2. **生产环境**：务必使用 KV Cache + Continuous Batching，这两种优化在 vLLM 中已默认启用
3. **评估策略**：Perplexity 用于训练阶段监控，BLEU/ROUGE 基本淘汰，LLM-as-a-Judge 是当前最实用的方法
4. **LLM-as-a-Judge 陷阱**：一定要注意位置偏差，每次评估做双次交换位置取平均
5. **Human-in-the-loop**：关键评估结果必须有人工抽查，LLM judge 本身也有偏好和偏见

## 常见问题

**Q: Temperature=0 就是确定性吗？**

A: 理论上是的，但实际上不同 Provider 的实现可能略有差异（精度问题）。对于需要严格确定性的场景（如 API 输出格式、数据提取），建议用 Structured Output 而不是依赖 temperature=0。

**Q: Speculative Decoding 有没有质量损失？**

A: 没有。Target Model 的验证过程确保了目标分布的正确性。加速来自于用 Draft Model 做"投机"，但最终输出与纯 Target Model 完全相同。

**Q: 为什么不能只看 PPL？**

A: PPL 衡量的是模型对训练分布的拟合程度，不是对用户需求的有用程度。一个背下整个训练集的模型PPL极低，但对新问题毫无用处。LLM-as-a-Judge 的"有用性"评分比 PPL 更接近实际需求。

## 推理优化技术

### Speculative Decoding（投机解码）

投机解码是当前 LLM 推理加速最重要的技术之一。核心思想是用一个小型"草稿模型"（Draft Model）快速生成候选 token 序列，然后用大型"目标模型"（Target Model）一次性并行验证所有候选 token。

```
投机解码的详细流程：
┌──────────────────────────────────────────────────────────────┐
│ 1. Draft Model（如 LLaMA 68M）自回归生成 γ 个候选 token     │
│    → 草稿模型只有目标的 ~1/100 参数，生成速度极快            │
│                                                              │
│ 2. Target Model（如 LLaMA 70B）一次前向传播                  │
│    → 输入: prefix + 所有 γ 个候选 token                      │
│    → 输出: 每个位置的完整概率分布                             │
│                                                              │
│ 3. 逐个位置验证：                                            │
│    → 对每个位置 i，从 Target Model 的分布中采样              │
│    → 如果采样结果 == draft token_i → 接受（accept）          │
│    → 如果采样结果 != draft token_i → 拒绝（reject）          │
│    → 在拒绝位置用 Target Model 的分布重新采样并停止验证      │
│                                                              │
│ 加速比：2-3x（取决于 Draft 和 Target 的分布对齐程度）        │
│ 质量保证：输出分布与纯 Target Model 完全等价（零质量损失）    │
└──────────────────────────────────────────────────────────────┘
```

**接受率的关键影响因素：**
- Draft 和 Target 模型同家族时接受率最高（如 LLaMA 3.1-8B 做 Draft，LLaMA 3.1-70B 做 Target）
- Temperature 越低，接受率越高（因为分布更集中）
- 简单任务（翻译、摘要）的接受率高于复杂推理任务

```java
/**
 * Speculative Decoding 的 Java 模拟实现
 * 演示核心的"验证-接受/拒绝"逻辑
 */
public class SpeculativeDecodingDemo {

    /**
     * 模拟一次投机解码迭代
     * @param draftTokens 草稿模型生成的候选 token 序列
     * @param draftProbs 草稿模型在各位置的概率分布
     * @param targetProbs 目标模型在各位置的概率分布
     * @return 验证结果：接受哪些 token + 在哪个位置停止
     */
    public record VerificationResult(
        List<Integer> acceptedTokens,  // 被接受的 draft token
        int rejectionPosition,          // 拒绝位置（-1 表示全部接受）
        int correctedToken              // 在拒绝位置的校正 token
    ) {}

    public static VerificationResult verify(
            List<Integer> draftTokens,
            List<float[]> draftProbs,
            List<float[]> targetProbs,
            Random random) {

        var accepted = new ArrayList<Integer>();
        int gamma = draftTokens.size();

        for (int i = 0; i < gamma; i++) {
            int draftToken = draftTokens.get(i);
            float draftP = draftProbs.get(i)[draftToken];
            float targetP = targetProbs.get(i)[draftToken];

            // 核心验证：接受概率 = min(1, target_p / draft_p)
            double acceptProb = Math.min(1.0, targetP / Math.max(draftP, 1e-9f));

            if (random.nextDouble() < acceptProb) {
                accepted.add(draftToken);  // 接受该 token
            } else {
                // 拒绝：从 target 的调整后分布重新采样
                float[] adjustedProbs = targetProbs.get(i).clone();
                adjustedProbs[draftToken] = Math.max(0,
                    adjustedProbs[draftToken] - draftProbs.get(i)[draftToken]);
                int corrected = TemperatureSampling.sampleFromDistribution(
                    TemperatureSampling.applyTemperature(adjustedProbs, 1.0f), random);
                return new VerificationResult(accepted, i, corrected);
            }
        }
        // 全部接受
        return new VerificationResult(accepted, -1, -1);
    }

    public static void main(String[] args) {
        var random = new Random(42);
        // 模拟：draft 生成 [101, 205, 330]，target 验证
        var draftTokens = List.of(101, 205, 330);
        System.out.println("草稿 token: " + draftTokens);

        var result = verify(draftTokens,
            List.of(createDist(101), createDist(205), createDist(330)),
            List.of(createDist(101), createDist(205), createDist(330)),
            random);

        System.out.println("接受: " + result.acceptedTokens());
        if (result.rejectionPosition() >= 0) {
            System.out.println("在位置 " + result.rejectionPosition() +
                " 拒绝，校正为 token " + result.correctedToken());
        } else {
            System.out.println("全部接受，加速比 = " + draftTokens.size() + "x");
        }
    }

    private static float[] createDist(int peakToken) {
        var dist = new float[1000];
        dist[peakToken] = 5.0f;
        for (int i = 0; i < dist.length; i++) {
            if (i != peakToken) dist[i] = (float) (Math.random() * 0.5);
        }
        return TemperatureSampling.applyTemperature(dist, 1.0f);
    }
}
```

### KV Cache 量化

KV Cache 是推理时最大的显存消耗者（长上下文时可占总显存的 80%+）。KV Cache 量化将此缓存从 FP16 压缩到 INT8 甚至 INT4，大幅降低显存需求。

```
KV Cache 量化方案对比：

FP16（baseline）:
  存储: 每个 K/V 值占 2 bytes
  质量: 无损失
  示例（LLaMA 70B, 128K context）:
    2 × 80层 × 1 batch × 128K × 64头 × 128维 × 2 bytes ≈ 342 GB

INT8（per-channel）:
  存储: 每个值占 1 byte，每个 channel 额外存 scale（FP16）
  质量: < 0.5% 质量损失（在多数 benchmark 上不可见）
  显存: ~171 GB（减少 50%）

INT4（group-wise，如 KIVI）:
  存储: 每个值占 0.5 byte，每 group 额外存 scale + zero-point
  质量: 1-3% 质量损失（长上下文场景仍可接受）
  显存: ~85 GB（减少 75%）
```

**实际影响：**
- 在相同 GPU 显存下，KV Cache INT8 量化可支持的并发请求数接近翻倍
- INT4 量化在 128K+ 超长上下文场景中几乎必需——否则 KV Cache 独占全部显存
- vLLM 和 TGI 均已内置 KV Cache 量化支持，通过配置参数即可开启
- 建议：优先使用 INT8 KV Cache 量化（质量几乎无损），仅在显存极度受限时考虑 INT4

### Chunked Prefill

Chunked Prefill 是解决长上下文推理中"首 token 延迟"问题的关键技术。它将一个长 prompt 的 prefill 阶段切分成多个 chunk，与 decode 阶段交替执行。

```
传统 Prefill 的问题：
  输入: 一篇 100K token 的文档
  → Prefill：一次性处理全部 100K token（耗时 5-10 秒）
  → 然后才开始逐个生成 token
  → 用户等待 10 秒才能看到第一个字——体验极差

Chunked Prefill 的工作方式：
  将 100K token 分为多个 chunk（如每 2048 token 一个 chunk）：

  Chunk 1 (0-2048):     Prefill → 为 Chunk 1 计算 KV Cache
  Chunk 2 (2048-4096):  Prefill → 追加 KV Cache
  [如果有等待的 decode 请求，插入执行]  ← 关键：prefill 和 decode 交替
  Chunk 3 (4096-6144):  Prefill
  [继续交替 decode]
  ...

  优势：
  1. 首 token 延迟大幅降低（不必等全部 prefill 完成）
  2. 不会因为一个长 prefill 阻塞其他请求的 decode
  3. 与 Continuous Batching 天然兼容
```

在 vLLM 中，Chunked Prefill 通过 `--max-num-batched-tokens` 和 `--max-num-seqs` 参数配置。对 Java 开发者而言，这意味着选择推理服务时关注其是否支持 Chunked Prefill（vLLM 和 SGLang 均支持）。

## LLM-as-a-Judge 深入

### 评分准则（Rubric）设计最佳实践

一个设计良好的 Rubric 是 LLM-as-a-Judge 可靠性的基础。推荐使用 1-5 分制，每级有明确、可操作的描述：

```
评分准则设计模板（以"回答准确性"维度为例）：

1 分 — 完全错误
  • 核心事实全部错误或与问题无关
  • 包含严重的误导信息
  判定标准：任何具备基本知识的读者都能识别错误

2 分 — 有重大错误
  • 部分事实正确但存在关键性错误
  • 遗漏了核心要点
  判定标准：如果用户按照回答操作会导致错误结果

3 分 — 基本正确但不完整
  • 主要事实正确
  • 但遗漏了重要细节或边缘情况
  • 表达可能不够清晰
  判定标准：回答方向对但不完善

4 分 — 正确且较完整
  • 事实准确，覆盖主要要点
  • 表达清晰，结构合理
  • 可能存在少量可优化的细节
  判定标准：可以直接使用的回答

5 分 — 优秀
  • 完全准确，覆盖所有要点和边缘情况
  • 包含具体示例、最佳实践或深入洞察
  • 表达精炼、逻辑严谨
  判定标准：可以作为教学材料或官方文档引用
```

**Rubric 设计原则：**
1. **每级有判据而非模糊描述**：避免"较好""一般"等主观词，改用可验证的行为描述
2. **级间间距均匀**：1→2 的难度与 4→5 的难度接近
3. **提供锚定示例（Anchoring Examples）**：每级至少提供 1-2 个评分示例，让 Judge 模型校准评分标准
4. **维度独立**：准确性和清晰度分开评，避免"光环效应"（一个维度好导致全好）

### 位置偏差缓解

位置偏差（Position Bias）是 LLM-as-a-Judge 最顽固的问题之一——模型倾向给先出现的回答更高分。系统性的缓解需要多策略组合：

```java
/**
 * 位置偏差缓解的完整方案
 */
public class PositionBiasMitigation {

    /**
     * 方案1：交换位置双次评估
     * 对每对回答评估两次，交换 AB 顺序，取平均分
     */
    public record DebiasedScore(double scoreA, double scoreB, double biasDelta) {}

    public static DebiasedScore evaluateWithSwap(
            String question, String answerA, String answerB,
            Function<String, Map<String, Double>> judgeCall) {

        // 第一次：A 在前，B 在后
        var prompt1 = buildComparisonPrompt(question, answerA, answerB);
        var result1 = judgeCall.apply(prompt1);

        // 第二次：B 在前，A 在后
        var prompt2 = buildComparisonPrompt(question, answerB, answerA);
        var result2 = judgeCall.apply(prompt2);

        // 取平均消除位置偏差
        double scoreA = (result1.getOrDefault("answer_1", 0.0) +
                         result2.getOrDefault("answer_2", 0.0)) / 2.0;
        double scoreB = (result1.getOrDefault("answer_2", 0.0) +
                         result2.getOrDefault("answer_1", 0.0)) / 2.0;

        // 偏差量 = 第一次减第二次（正值表示倾向第一个位置）
        double biasDelta = (result1.getOrDefault("answer_1", 0.0) -
                            result2.getOrDefault("answer_1", 0.0));

        return new DebiasedScore(scoreA, scoreB, biasDelta);
    }

    private static String buildComparisonPrompt(
            String question, String first, String second) {
        return String.format("""
            请评估以下两个回答的质量（1-5分）：

            【问题】%s

            【回答1】%s

            【回答2】%s

            请以JSON格式返回：{"answer_1": <分>, "answer_2": <分>}
            """, question, first, second);
    }

    /**
     * 方案2：多模型 Panel 平均
     * 不同 Judge 模型的位置偏好不同，取平均可降低偏差
     */
    public static double panelScore(
            String question, String answer,
            List<Function<String, Map<String, Double>>> judgeModels) {
        // 每个 Judge 模型独立评分
        var scores = judgeModels.stream()
            .map(judge -> {
                var prompt = buildSinglePrompt(question, answer);
                return judge.apply(prompt).getOrDefault("score", 0.0);
            })
            .sorted()
            .toList();

        // 去掉最高最低后取平均（trimmed mean）
        if (scores.size() <= 2) {
            return scores.stream().mapToDouble(Double::doubleValue).average().orElse(0);
        }
        return scores.subList(1, scores.size() - 1).stream()
            .mapToDouble(Double::doubleValue).average().orElse(0);
    }

    private static String buildSinglePrompt(String question, String answer) {
        return String.format("""
            请评估以下回答的质量（1-5分）：

            【问题】%s
            【回答】%s

            请以JSON格式返回：{"score": <分>, "reasoning": "<理由>"}
            """, question, answer);
    }

    public static void main(String[] args) {
        System.out.println("位置偏差缓解策略总结：");
        System.out.println("1. 交换位置双次评估 — 最直接有效");
        System.out.println("2. 多Judge Panel — 利用模型多样性");
        System.out.println("3. 随机化位置 — 大样本下统计抵消");
        System.out.println("4. 校准集 — 用已知质量样本校准Judge");
    }
}
```

### 多 Judge 一致性度量：Fleiss' Kappa

当有多个 Judge（人工评审员或不同 LLM Judge）对同一批样本评分时，需要度量他们之间的一致性。Fleiss' Kappa 是适用于多个评分者、多个类别的标准统计量。

$$\kappa = \frac{\bar{P} - \bar{P_e}}{1 - \bar{P_e}}$$

其中 $\bar{P}$ 是观测到的一致性比例，$\bar{P_e}$ 是随机一致性期望值。Kappa > 0.6 表示中等一致，> 0.8 表示高度一致。

```java
/**
 * Fleiss' Kappa 的 Java 实现
 * 用于度量多个 Judge 之间的一致性
 */
public class FleissKappa {

    /**
     * 计算 Fleiss' Kappa
     * @param ratings 评分矩阵 [样本数][类别数]，值 = 对该样本给出该类别评分的评委数
     * @return Kappa 值 (-1 到 1)
     */
    public static double calculate(int[][] ratings) {
        int n = ratings.length;        // 样本数
        int k = ratings[0].length;     // 类别数
        int N = 0;                      // 评委总数（每样本相同）

        // 验证每样本的评委数一致
        for (int i = 0; i < n; i++) {
            int sum = 0;
            for (int j = 0; j < k; j++) sum += ratings[i][j];
            if (i == 0) N = sum;
            else if (sum != N) {
                throw new IllegalArgumentException(
                    "样本 " + i + " 的评委数 (" + sum + ") 与预期 (" + N + ") 不一致");
            }
        }

        // 计算 P_i：每个样本的观察一致性
        double[] Pi = new double[n];
        for (int i = 0; i < n; i++) {
            double sumSq = 0;
            for (int j = 0; j < k; j++) {
                sumSq += (double) ratings[i][j] * ratings[i][j];
            }
            Pi[i] = (sumSq - N) / (N * (N - 1.0));
        }

        // P_bar：平均观察一致性
        double Pbar = 0;
        for (double p : Pi) Pbar += p;
        Pbar /= n;

        // p_j：每类别被使用的总比例
        double[] pj = new double[k];
        for (int j = 0; j < k; j++) {
            double sum = 0;
            for (int i = 0; i < n; i++) sum += ratings[i][j];
            pj[j] = sum / (n * N);
        }

        // P_e_bar：随机一致性期望值
        double PbarE = 0;
        for (double p : pj) PbarE += p * p;

        // Kappa
        if (Math.abs(PbarE - 1.0) < 1e-9) return 1.0;
        return (Pbar - PbarE) / (1.0 - PbarE);
    }

    /**
     * 实际的 LLM Judge 一致性评估示例
     */
    public static void main(String[] args) {
        // 场景：3 个 Judge 对 10 个样本评分（1-5 分 = 5 个类别）
        // ratings[i][j] = 对样本 i，有几位评委给了 j+1 分
        int[][] ratings = {
            {0, 0, 0, 2, 1},  // 样本1: 2人给4分, 1人给5分
            {0, 0, 0, 0, 3},  // 样本2: 3人全给5分 → 完全一致
            {0, 0, 1, 2, 0},  // 样本3: 1人给3分, 2人给4分
            {0, 0, 0, 3, 0},  // 样本4: 3人全给4分 → 完全一致
            {0, 1, 2, 0, 0},  // 样本5: 1人给2分, 2人给3分
            {1, 2, 0, 0, 0},  // 样本6: 1人给1分, 2人给2分
            {0, 0, 0, 3, 0},  // 样本7
            {0, 0, 2, 1, 0},  // 样本8
            {0, 0, 0, 1, 2},  // 样本9
            {0, 0, 3, 0, 0},  // 样本10: 3人全给3分
        };

        double kappa = calculate(ratings);
        System.out.printf("Fleiss' Kappa = %.3f%n", kappa);
        System.out.println("解读：");
        if (kappa < 0.0) System.out.println("  < 0.0 — 低于随机水平（Judge 存在系统性分歧）");
        else if (kappa < 0.2) System.out.println("  0.0-0.2 — 轻微一致");
        else if (kappa < 0.4) System.out.println("  0.2-0.4 — 一般一致");
        else if (kappa < 0.6) System.out.println("  0.4-0.6 — 中等一致（可接受的最低标准）");
        else if (kappa < 0.8) System.out.println("  0.6-0.8 — 显著一致");
        else System.out.println("  0.8-1.0 — 近乎完美一致");

        // 使用建议：
        // - 单 Judge：无法计算 Kappa，必须用其他方法校准（如 Golden Set）
        // - 多 LLM Judge Panel：定期计算 Kappa 监控 Judge 一致性
        // - 人工 + LLM Judge：Kappa 低说明 LLM Judge 需要重新校准 Rubric
    }
}
```

**Kappa 值的实用判断：**
- **< 0.4**：评分者之间几乎没有有意义的一致性，Rubric 需要重新设计
- **0.4-0.6**：基本可用，但需要加强对边缘案例的统一标准
- **0.6-0.8**：良好，可以依赖 Judge 的评分做自动化决策
- **> 0.8**：优秀，Judge 之间的判断高度一致
