# Modern Java 25 深度解析

## 概述

本文深入剖析 JDK 25 LTS 中的九大核心现代特性，涵盖并发模型变革（Virtual Threads、Scoped Values、Structured Concurrency）、类型系统增强（Record、Sealed Class、Pattern Matching）、以及性能与互操作性提升（String Templates、FFM API、Vector API）。每个特性从其设计动机出发，通过原理分析、可运行代码示例、最佳实践与陷阱警示，构建完整的知识体系。

JDK 25 标志着 Java 并发模型的一次根本性范式转移：从"操作系统线程 + 异步回调"迁移到"虚拟线程 + 结构化并发"。这是自 Java 5 引入 `java.util.concurrent` 以来最重大的并发 API 变革。

## 1. Virtual Threads（虚拟线程，JEP 444）

### 设计动机

传统 Java 平台线程（`java.lang.Thread`）是操作系统线程的 1:1 包装。操作系统线程是昂贵资源——每个线程消耗约 1-2 MB 栈空间，且上下文切换涉及内核态切换。在"每个请求一个线程"的服务器编程模型中，当并发请求数达到数万时，线程数成为吞吐量的硬瓶颈。

历史上，开发者被迫采用异步/响应式编程（CompletableFuture、Reactor、RxJava）来规避线程瓶颈。这些框架将请求处理拆解为异步回调链，虽然提升了吞吐量，但代价巨大：难以调试（堆栈跟踪断裂）、难以观测（span 跨越多个线程）、难以理解（控制流与数据流分离）。

虚拟线程的设计目标是：**保留"每个请求一个线程"的简单编程模型，同时消除线程数量的可扩展性瓶颈**。

### 核心原理

虚拟线程由 JVM 而非操作系统管理。关键机制：

1. **Continuation（续体）**：虚拟线程的核心是 `jdk.internal.vm.Continuation`。一个 continuation 代表一个可挂起和恢复的执行序列。当虚拟线程在阻塞操作（如 I/O、`Thread.sleep()`、`LockSupport.park()`）上等待时，JVM 挂起其 continuation，释放底层的平台线程（载体线程）去执行其他虚拟线程。这个过程称为 **unmount（卸载）**。当阻塞操作完成，JVM 将 continuation 恢复（**mount，挂载**）到一个可用的载体线程上继续执行。

2. **ForkJoinPool 调度**：虚拟线程的默认调度器是 `ForkJoinPool`，以 FIFO 模式运行。调度器维护一个工作窃取队列，载体线程从这个队列中获取就绪的虚拟线程。

3. **Mount/Unmount 生命周期**：
   ```
   VT 创建 → 提交到 scheduler → mount 到 carrier → 执行 → (遇到阻塞)
   → unmount (carrier 被释放) → continuation 挂起在堆上（仅占用 ~300 bytes 对象）
   → 阻塞完成 → continuation 重新入队 → mount 到新的 carrier → 继续执行 → 完成
   ```

4. **栈存储**：虚拟线程的栈不是预先分配的连续内存区域，而是存储在堆上的 `Continuation` 对象中的栈帧链（stack chunk）。当栈增长时，分配新的 chunk 对象；栈缩小时，chunk 可以被 GC 回收。这允许 JVM 创建数百万个虚拟线程而不会耗尽内存。

### 代码示例

**传统平台线程 — 每个任务一个线程（无法扩展）：**

```java
// 旧方式：平台线程池，最大线程数受限于 OS 资源
var executor = Executors.newFixedThreadPool(200); // 最多 200 并发
for (int i = 0; i < 100_000; i++) {
    final int taskId = i;
    executor.submit(() -> {
        // 如果这里有阻塞 I/O，200 个线程不够用
        doBlockingIO(taskId);
        return taskId;
    });
}
```

**虚拟线程 — 百万并发无压力：**

```java
// JDK 25 方式：每个任务一个虚拟线程
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    var futures = new ArrayList<Future<Integer>>();
    for (int i = 0; i < 1_000_000; i++) {
        final int taskId = i;
        futures.add(executor.submit(() -> {
            Thread.sleep(Duration.ofMillis(100)); // 模拟 I/O 等待
            return taskId;
        }));
    }
    // 所有 100 万个虚拟线程并发等待，只占用少量载体线程
    // 载体线程数量 = CPU 核心数（默认）
    for (var future : futures) {
        future.get(); // 收集结果
    }
}
```

**直接创建虚拟线程：**

```java
// 方式 1：通过 Thread.ofVirtual()
var vt = Thread.ofVirtual()
    .name("my-virtual-thread-", 1)
    .start(() -> {
        System.out.println("Running in virtual thread: " + Thread.currentThread());
    });
vt.join();

// 方式 2：通过 Thread.Builder
var builder = Thread.ofVirtual()
    .name("worker-")
    .uncaughtExceptionHandler((t, e) -> 
        System.err.println("Uncaught in " + t.getName() + ": " + e.getMessage()));
var vt2 = builder.start(() -> processRequest());
vt2.join();
```

### 性能基准

以下是在 8 核机器上对 100 万个并发任务的近似测试结果：

| 并发模型 | 完成时间 | 峰值线程数 | 内存占用 |
|----------|----------|-----------|----------|
| 平台线程池 (200) | ~83 分钟 | 200 | ~400 MB |
| 虚拟线程 | ~1.5 秒 | 1,000,000 VT / 8 载体 | ~300 MB |

虚拟线程在 I/O 密集型场景下性能碾压平台线程池，因为平台线程池的并发度受线程池大小限制，而虚拟线程允许所有任务并发等待 I/O。

### 最佳实践

1. **不要池化虚拟线程**：虚拟线程是廉价的一次性对象。创建虚拟线程的成本与创建普通 Java 对象相当。`Executors.newVirtualThreadPerTaskExecutor()` 为每个任务创建新的虚拟线程，这是推荐用法。池化虚拟线程只会增加复杂性而没有收益。

2. **使用 `try-with-resources` 管理 ExecutorService**：`VirtualThreadPerTaskExecutor` 实现了 `Closeable`，在 try-with-resources 中关闭可确保所有任务完成。

3. **对 CPU 密集型任务使用平台线程**：虚拟线程的优势在于 I/O 等待期间的卸载。如果任务是纯 CPU 计算（不涉及阻塞），虚拟线程没有优势，反而会因为调度开销而略微降低性能。CPU 密集型任务应使用 `Executors.newFixedThreadPool(Runtime.getRuntime().availableProcessors())`。

4. **不要在虚拟线程中使用线程局部变量做缓存**：虚拟线程的生命周期短且数量巨大。如果每个虚拟线程都在 ThreadLocal 中缓存大对象，内存将被迅速耗尽。应使用 Scoped Values（见第 2 节）替代。

### 陷阱：Pinning（钉住）

虚拟线程最重要的限制是 **pinning**。当虚拟线程执行以下操作时，它会被"钉住"到载体线程，无法 unmount：

1. 执行 `synchronized` 块或方法内的阻塞操作
2. 调用 native 方法（JNI）
3. 在 `Object.wait()` 上等待（而非 `LockSupport.park()` 或 `ReentrantLock`）

**pinning 诊断示例：**

```java
// 危险：synchronized 内阻塞导致 pinning
var executor = Executors.newVirtualThreadPerTaskExecutor();
executor.submit(() -> {
    synchronized (lock) {           // VT 被 mount 到 carrier A
        Thread.sleep(10_000);       // 阻塞！但 carrier A 被 pinning 占用
    }                               // carrier A 在整个 sleep 期间不能服务其他 VT
});

// 安全：使用 ReentrantLock 替代 synchronized
var reentrantLock = new ReentrantLock();
executor.submit(() -> {
    reentrantLock.lock();           // VT 被 mount 到 carrier A
    try {
        Thread.sleep(10_000);       // 阻塞 → VT 从 carrier A unmount
                                    // carrier A 可以服务其他 VT
    } finally {
        reentrantLock.unlock();
    }
});
```

**诊断 pinning 的系统属性：**

```bash
# 当虚拟线程被 pinning 时打印堆栈跟踪
-Djdk.tracePinnedThreads=full
# 或只打印简短信息
-Djdk.tracePinnedThreads=short
```

**pinning 的常见场景和修复：**

| 被 pinning 的代码 | 修复方案 |
|-------------------|----------|
| `synchronized(this) { ...阻塞I/O... }` | 替换为 `ReentrantLock` |
| `synchronized` 保护的 HashMap | 替换为 `ConcurrentHashMap` |
| JNI 调用 | 迁移到 FFM API（见第 8 节）|
| 第三方库中的 `synchronized` | 联系维护者或寻找替代库 |

## 2. Scoped Values（作用域值，JEP 481）

### 设计动机

`ThreadLocal` 在 Java 中存在了二十多年，用于在同一个线程内隐式传递上下文（如用户身份、事务、请求 ID）。然而，在虚拟线程时代，`ThreadLocal` 暴露出三大问题：

1. **可变性**：`ThreadLocal.set()` 允许任意修改值，导致数据流难以追踪。
2. **无约束的生命周期**：值设置后没有被自动清理的机制，容易造成内存泄漏（尤其在虚拟线程数巨大的场景）。
3. **不支持结构化并发**：当任务分叉（fork）到多个子线程时，`ThreadLocal` 的值不会自动继承到子线程。

Scoped Values 的设计目标：**提供不可变的、作用域绑定的、线程安全的上下文传递机制，天然支持虚拟线程和结构化并发**。

### 核心原理

`ScopedValue` 的核心语义：

- **不可变性**：一旦创建，`ScopedValue` 实例不可修改。通过 `ScopedValue.where(SV, value).run(() -> {...})` 绑定值时，新值只在指定的作用域（lambda）内有效。
- **作用域绑定**：`run()` 方法创建一个有界作用域。进入作用域时绑定值，离开作用域时自动解绑。即使用异常退出，也会正确解绑。
- **继承语义**：子虚拟线程自动继承父线程的作用域值（通过 `StructuredTaskScope`）。
- **偏好（preference）语义**：每个 `ScopedValue` 是一个"偏好"键，在任何给定时间点，一个线程对给定的键最多有一个绑定值。

**ScopedValue 与 ThreadLocal 的核心差异：**

| 维度 | ThreadLocal | ScopedValue |
|------|-------------|-------------|
| 可变性 | `set()` 可变 | 不可变（仅 `where().run()` 绑定） |
| 生命周期 | 手动 `remove()`，易泄漏 | `run()` 结束自动清理 |
| 继承 | 需 `InheritableThreadLocal` | 自动继承到结构化并发子任务 |
| 内存开销 | 每个线程一个 Entry | 不可变快照，共享 |
| 虚拟线程友好 | 否（大量 VT 时内存浪费） | 是 |

### 代码示例

**声明和使用 ScopedValue：**

```java
// 声明一个 ScopedValue
final ScopedValue<User> CURRENT_USER = ScopedValue.newInstance();

// 在线程中绑定值
ScopedValue.where(CURRENT_USER, authenticatedUser)
    .run(() -> {
        // 在此作用域内，CURRENT_USER.get() 返回 authenticatedUser
        var user = CURRENT_USER.get();
        System.out.println("Current user: " + user.name());
        
        // 可以嵌套绑定（创建新的作用域）
        ScopedValue.where(CURRENT_USER, adminUser)
            .run(() -> {
                // 此处 CURRENT_USER.get() 返回 adminUser
                System.out.println("Admin override: " + CURRENT_USER.get().name());
            });
        // 退出嵌套后恢复为 authenticatedUser
        System.out.println("Back to: " + CURRENT_USER.get().name());
    });
// 退出 run() 后，CURRENT_USER 未绑定
// CURRENT_USER.get() 在此处抛出 NoSuchElementException
```

**对比：旧 ThreadLocal 方式 vs 新 ScopedValue 方式：**

```java
// === 旧方式：ThreadLocal ===
final ThreadLocal<User> tlUser = new ThreadLocal<>();
try {
    tlUser.set(authenticatedUser);
    handleRequest();    // handleRequest 内部通过 tlUser.get() 获取用户
} finally {
    tlUser.remove();    // 必须手动清理！忘了就内存泄漏
}

// === 新方式：ScopedValue ===
final ScopedValue<User> svUser = ScopedValue.newInstance();
ScopedValue.where(svUser, authenticatedUser)
    .run(() -> handleRequest());   // 自动绑定和清理
```

### 与结构化并发集成

Scoped Values 与 `StructuredTaskScope` 天然配合——子任务自动继承父作用域的值：

```java
final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();

ScopedValue.where(REQUEST_ID, UUID.randomUUID().toString())
    .run(() -> {
        // 父任务
        System.out.println("Parent: " + REQUEST_ID.get());

        try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
            // 子任务 1 — 自动继承 REQUEST_ID
            var task1 = scope.fork(() -> {
                System.out.println("Child 1: " + REQUEST_ID.get()); // 继承父作用域的值
                return fetchFromDB();
            });

            // 子任务 2 — 也自动继承
            var task2 = scope.fork(() -> {
                System.out.println("Child 2: " + REQUEST_ID.get()); // 同一个 REQUEST_ID
                return fetchFromCache();
            });

            scope.join().throwIfFailed();
            // 两个子任务看到的是同一个 REQUEST_ID，无需手动传递
        }
    });
```

### 最佳实践

1. **ScopedValue 实例应是 static final 字段**：这样确保全局唯一且不可修改。
2. **一个 ScopedValue 对应一个上下文属性**：不要用一个 ScopedValue 传递多个不相关的值。使用 record 类组合相关值。
3. **在框架的入口点绑定值**：例如 Servlet Filter、Spring Interceptor、或 gRPC Interceptor 中绑定请求级别的 Scoped Values。

### 陷阱

- **在 `run()` 之外调用 `get()`**：如果没有活跃的绑定，`ScopedValue.get()` 抛出 `NoSuchElementException`。如果需要可选的默认值，使用 `ScopedValue.getOrElse(defaultValue)` 或 `ScopedValue.where(SV, value, () -> defaultValue)`。
- **`call()` 和 `get()` 方法**：`ScopedValue.where(SV, value).call(() -> compute())` 有返回值版本，`run()` 无返回值。

## 3. Structured Concurrency（结构化并发，JEP 480）

### 设计动机

传统的并发编程中，任务分叉（fork）和汇合（join）之间没有强制的关系约束。使用 `ExecutorService` 时：

- 子任务可能在其父任务结束后继续运行（"游离线程"）
- 错误处理碎片化：一个子任务失败时，其他子任务可能继续执行浪费资源
- 取消传播复杂：需要手动跟踪 Future 并逐个调用 `cancel()`
- 线程转储中，父子任务的因果关系不清晰

结构化并发的核心思想来自并发编程的一个观察：**代码的结构化作用域（block）应该与任务的生命周期对齐**。如果父任务退出其代码块，所有子任务也应该完成（要么成功，要么被取消）。

### 核心原理

`StructuredTaskScope` 是结构化并发的核心 API。它将一组并发子任务绑定到一个作用域中：

- 所有子任务在 `StructuredTaskScope` 中 fork
- 当作用域关闭时（try-with-resources 结束），确保所有子任务已完成或已被取消
- 提供两种内置策略：`ShutdownOnFailure`（任何一个失败则取消所有其他）和 `ShutdownOnSuccess`（任何一个成功则取消所有其他）

### 代码示例

**ShutdownOnFailure — 任一失败则全部取消：**

```java
// 并行调用两个服务获取用户数据，任一个失败则整体失败
UserProfile fetchUserProfile(long userId) throws ExecutionException, InterruptedException {
    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        // fork 两个虚拟线程子任务
        var userFuture = scope.fork(() -> userService.findById(userId));
        var ordersFuture = scope.fork(() -> orderService.getRecentOrders(userId));

        // 等待所有子任务完成（或任一个失败）
        scope.join();           // 阻塞直到所有子任务完成或失败
        scope.throwIfFailed();  // 如果有子任务抛异常，在此处重新抛出

        // 所有子任务成功完成，合并结果
        return new UserProfile(userFuture.get(), ordersFuture.get());
    }
    // try-with-resources 确保作用域关闭，所有子任务已完成
}
```

**ShutdownOnSuccess — 任一成功即返回：**

```java
// 从多个副本查询数据，取最快返回的结果
String fetchFromReplicas(String key) throws ExecutionException, InterruptedException {
    try (var scope = new StructuredTaskScope.ShutdownOnSuccess<String>()) {
        // 并行从三个副本读取
        scope.fork(() -> readFromReplica("replica-1", key));
        scope.fork(() -> readFromReplica("replica-2", key));
        scope.fork(() -> readFromReplica("replica-3", key));

        // 等待任一个成功，其他被自动取消
        return scope.join().result(); // 返回第一个成功的结果
    }
}
```

**自定义策略：**

```java
// 自定义：收集所有子任务结果（包括失败的）
record TaskResult<T>(T value, Throwable error) {
    boolean isSuccess() { return error == null; }
}

<T> List<TaskResult<T>> executeAllWithResults(List<Callable<T>> tasks) 
        throws InterruptedException {
    try (var scope = new StructuredTaskScope<>()) {
        var futures = new ArrayList<StructuredTaskScope.Subtask<T>>();

        for (var task : tasks) {
            futures.add(scope.fork(task));
        }

        scope.join(); // 等待所有子任务完成（无论成功或失败）

        // 收集结果
        return futures.stream()
            .map(f -> {
                try {
                    return new TaskResult<>(f.get(), null);
                } catch (ExecutionException e) {
                    return new TaskResult<>(null, e.getCause());
                }
            })
            .toList();
    }
}
```

### 对比：CompletableFuture vs StructuredTaskScope

**CompletableFuture 方式（旧）：**

```java
CompletableFuture<User> userFuture = CompletableFuture.supplyAsync(() -> userService.findById(userId));
CompletableFuture<List<Order>> ordersFuture = CompletableFuture.supplyAsync(() -> orderService.getOrders(userId));

CompletableFuture<UserProfile> result = userFuture
    .thenCombine(ordersFuture, UserProfile::new);

// 问题：
// 1. 如果 userFuture 失败而 ordersFuture 仍在运行，ordersFuture 不会被取消
// 2. 线程转储中看不到 userFuture 和 ordersFuture 的父子关系
// 3. 错误处理需要多个 exceptionally() 调用
```

**StructuredTaskScope 方式（新）：**

```java
try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
    var user = scope.fork(() -> userService.findById(userId));
    var orders = scope.fork(() -> orderService.getOrders(userId));
    scope.join();
    scope.throwIfFailed();
    return new UserProfile(user.get(), orders.get());
}
// 优势：
// 1. 任一子任务失败 → 另一个被自动取消
// 2. 线程转储中父子关系可见
// 3. 错误处理集中在一个 throwIfFailed()
```

### 最佳实践

1. **优先使用 `ShutdownOnFailure`**：这是最安全的默认策略。大部分业务场景中，如果一部分数据获取失败，整体结果无法构建。
2. **使用虚拟线程作为底层的线程工厂**：`StructuredTaskScope` 默认使用虚拟线程，这是最优组合。
3. **嵌套结构化并发**：在 `StructuredTaskScope` 的子任务中，可以再次使用 `StructuredTaskScope`。

### 陷阱

- **不要忘记 `scope.join()`**：不调用 `join()` 就调用 `future.get()` 会导致 `Future.get()` 阻塞直到该子任务完成，但不会等待其他子任务。这破坏了结构化并发的目的。
- **`StructuredTaskScope` 创建时不会自动继承当前 `Executor`**：它默认使用虚拟线程 per-task executor。

## 4. Pattern Matching（模式匹配）

### 设计动机

传统 Java 中的类型检查和转换冗长且易出错：

```java
// 旧方式：类型检查 → 强制转换 → 使用
if (obj instanceof String) {
    String s = (String) obj;  // 重复了类型信息
    System.out.println(s.length());
}
```

模式匹配的设计目标：**将类型检查、转换和变量声明合并为一个原子操作，消除重复代码，由编译器保证类型安全**。

### instanceof 增强（JEP 394, final in JDK 16）

**基本用法：**

```java
// 旧方式
if (obj instanceof String) {
    String s = (String) obj;
    System.out.println(s.toUpperCase());
}

// 模式匹配 instanceof（JDK 16+）
if (obj instanceof String s) {
    System.out.println(s.toUpperCase()); // s 在此作用域内有效
}

// 与条件组合
if (obj instanceof String s && s.length() > 5) {
    System.out.println("Long string: " + s);
}

// 否定模式 — 变量在 else 分支有效
if (!(obj instanceof String s)) {
    return; // s 不在作用域内
}
System.out.println(s); // s 在此作用域内有效
```

### Record Patterns（JEP 440, final in JDK 21）

Record Patterns 允许解构 record 对象：

```java
// 定义
record Point(int x, int y) {}
record Line(Point start, Point end) {}

// 嵌套解构
void printLineCoordinates(Object obj) {
    if (obj instanceof Line(Point(int x1, int y1), Point(int x2, int y2))) {
        // x1, y1, x2, y2 直接被绑定！
        System.out.println("Line from (%d,%d) to (%d,%d)".formatted(x1, y1, x2, y2));
    }
}

// 简化写法 — 只提取需要的字段
if (obj instanceof Line(Point start, var end)) {
    System.out.println("Start point: " + start);
}
```

### switch 模式匹配（JEP 441, final in JDK 21）

这是最强大的模式匹配形式。`switch` 可以匹配类型模式、record 模式，且编译器检查完备性：

```java
// 旧方式：if-else 链
String legacyFormat(Object obj) {
    if (obj == null) return "null";
    if (obj instanceof Integer) return "Integer: " + obj;
    if (obj instanceof String)  return "String: " + obj;
    if (obj instanceof Long)    return "Long: " + obj;
    return "Unknown";
}

// 新方式：switch 模式匹配
String modernFormat(Object obj) {
    return switch (obj) {
        case null            -> "null";
        case Integer i       -> "Integer: " + i;
        case String s        -> "String: " + s;
        case Long l          -> "Long: " + l;
        default              -> "Unknown";
    };
}
```

**带有 when 守卫（guard）的模式匹配：**

```java
String classifyNumber(Object obj) {
    return switch (obj) {
        case Integer i when i > 0  -> "Positive integer: " + i;
        case Integer i when i < 0  -> "Negative integer: " + i;
        case Integer i             -> "Zero";
        case Double d when Double.isNaN(d) -> "NaN";
        case Double d              -> "Double: " + d;
        default                    -> "Not a number";
    };
}
```

**结合 Record Patterns 和 switch 进行 AST 处理（经典用例）：**

```java
// 定义一个代数数据类型（ADT）
sealed interface Expr permits IntExpr, AddExpr, MulExpr, NegExpr {}
record IntExpr(int value) implements Expr {}
record AddExpr(Expr left, Expr right) implements Expr {}
record MulExpr(Expr left, Expr right) implements Expr {}
record NegExpr(Expr expr) implements Expr {}

// 使用 switch + record pattern 进行求值
int eval(Expr e) {
    return switch (e) {
        case IntExpr(int v)              -> v;
        case AddExpr(var l, var r)       -> eval(l) + eval(r);
        case MulExpr(var l, var r)       -> eval(l) * eval(r);
        case NegExpr(var sub)             -> -eval(sub);
    };
    // 编译器验证：switch 覆盖了所有 Expr 子类型（因为 Expr 是 sealed）
    // 如果遗漏了某个 case，编译器会报错
}
```

### 最佳实践

1. **优先使用 switch 模式匹配替代 if-else 链**：编译器提供完备性检查，减少遗漏分支的风险。
2. **与 sealed class 结合使用**：sealed class 限定了所有子类型，编译器可以验证 switch 的完备性，消除 `default` 分支。
3. **使用 when 守卫（guard）进行细化**：将类型检查和条件检查放在同一个 switch 表达式中。

### 陷阱

- **模式匹配 switch 中的 null 处理**：JDK 21 之前，`switch` 在遇到 `null` 选择器时会抛出 `NullPointerException`。JDK 21 起，如果 `case null` 出现，则处理 null 值；否则行为不变。
- **支配性（dominance）**：case 标签必须按特定顺序排列。例如 `case Integer i` 必须在 `case Integer i when i > 0` 之后，否则后者永远不会被匹配到（被前者支配）。编译器会报错。

## 5. Record Classes（记录类，JEP 395）

### 设计动机

Java 代码中大量存在"数据载体"类——只有字段和简单的访问器方法，没有复杂行为。写这种类需要大量的样板代码：构造器、`equals()`、`hashCode()`、`toString()`、getter 方法。IDE 可以生成这些代码，但它们会与业务逻辑混在一起，且需要手动维护一致。

Record 的设计目标：**提供一种简洁的语法来声明"不可变数据载体"，编译器自动生成构造器、访问器、`equals()`、`hashCode()` 和 `toString()`**。

### 核心原理

Record 是一种限制性类（restricted class）：

- 所有字段是 `private final`
- 构造器执行后，对象状态不可改变（浅不可变）
- 自动生成规范构造器、组件访问器（`field()` 而非 `getField()`）
- 自动生成 `equals()`（基于所有组件）、`hashCode()`、`toString()`
- 不能继承其他类（隐式 extends `java.lang.Record`），但可以实现接口
- 不能声明非静态字段（但可以声明静态字段和方法）

### 代码示例

**基本 Record：**

```java
// 一行代码替代传统 40+ 行样板代码
public record Person(String name, int age, Address address) {
    // 紧凑构造器 — 进行验证
    public Person {
        if (age < 0) throw new IllegalArgumentException("年龄不能为负数: " + age);
        if (name == null || name.isBlank()) throw new IllegalArgumentException("名称不能为空");
    }

    // 派生方法 — 基于组件计算
    public boolean isAdult() {
        return age >= 18;
    }

    // 静态工厂方法
    public static Person of(String name, int age) {
        return new Person(name, age, null);
    }

    // 静态字段
    public static final Person UNKNOWN = new Person("Unknown", 0, null);
}

// 使用
var person = new Person("张三", 30, new Address("Beijing"));
System.out.println(person.name());   // "张三" — 访问器名为 name()，不是 getName()
System.out.println(person);           // Person[name=张三, age=30, address=Address[city=Beijing]]
```

**嵌套 Record：**

```java
public record User(Long id, String username, Email email) {}
public record Email(String address, boolean verified) {}

// 创建
var user = new User(1L, "alice", new Email("alice@example.com", true));

// 嵌套解构
if (user instanceof User(var id, var name, Email(var addr, var verified))) {
    System.out.println("User %s's email: %s (verified: %s)".formatted(name, addr, verified));
}
```

### 局限性

1. **浅不可变**：Record 本身不可变，但如果其组件是可变的引用类型（如 `ArrayList`），则 record 的整体不可变性被打破。
   ```java
   record Wrapper(List<String> items) {} // 危险：items 内容可以外部修改
   // 解决方案：
   record SafeWrapper(List<String> items) {
       public SafeWrapper {
           items = List.copyOf(items); // 在紧凑构造器中做防御性拷贝
       }
   }
   ```
2. **不能继承**：Record 是 final 的隐式子类。
3. **无默认构造器**：Record 始终需要一个包含所有组件的规范构造器。
4. **不能声明非静态字段**。

### Builder 模式替代方案

Record 没有 setter，但不推荐使用传统的 Builder 模式（这与 record 的不可变语义冲突）。以下是几种替代方案：

**方案 1：wither 模式（JDK 25 可能支持）：**

```java
// JDK 25 中通过 record 的派生创建
public record User(Long id, String name, String email, int age) {
    // 手动实现 wither
    public User withName(String newName) {
        return new User(id, newName, email, age);
    }
    public User withEmail(String newEmail) {
        return new User(id, name, newEmail, age);
    }
}

// 使用
var updated = user.withName("Bob").withEmail("bob@example.com");
```

**方案 2：分步构造（使用中间可变对象）：**

```java
// 适用于有很多字段且有默认值的场景
public record AppConfig(String host, int port, String dbUrl, int maxConnections, Duration timeout) {
    public static Builder builder() { return new Builder(); }

    public static class Builder {
        private String host = "localhost";
        private int port = 8080;
        private String dbUrl;
        private int maxConnections = 10;
        private Duration timeout = Duration.ofSeconds(30);

        public Builder host(String host) { this.host = host; return this; }
        public Builder port(int port) { this.port = port; return this; }
        public Builder dbUrl(String dbUrl) { this.dbUrl = dbUrl; return this; }
        public Builder maxConnections(int n) { this.maxConnections = n; return this; }
        public Builder timeout(Duration d) { this.timeout = d; return this; }

        public AppConfig build() {
            if (dbUrl == null) throw new IllegalStateException("dbUrl is required");
            return new AppConfig(host, port, dbUrl, maxConnections, timeout);
        }
    }
}

// 使用
var config = AppConfig.builder()
    .dbUrl("jdbc:postgresql://localhost/mydb")
    .maxConnections(20)
    .build();
```

### 序列化

Record 的序列化机制与传统类不同：

- 反序列化时使用规范构造器（而非绕过构造器的魔法机制）
- 这意味着 compact constructor 中的验证逻辑会在反序列化时自动执行
- 这天然防止了反序列化攻击（传统 Java 序列化中，恶意数据可以绕过构造器）

```java
public record SafeUser(String name, int age) {
    public SafeUser {
        if (age < 0 || age > 150) {
            throw new IllegalArgumentException("Invalid age: " + age);
        }
    }
}
// 反序列化 age=999 的数据会抛出 IllegalArgumentException
// 这是 record 相对于传统 POJO 的重大安全优势
```

## 6. Sealed Classes（密封类，JEP 409）

### 设计动机

传统 Java 中，类要么是 `final`（完全不开放扩展），要么是开放继承（任何人都可以扩展）。缺少一种"受控继承"的中间立场——允许扩展，但只允许指定的部分类扩展。

这种需求在领域建模中非常常见：例如 `Shape` 可以是 `Circle`、`Rectangle`、`Triangle`，但不应该被任意未知类扩展。这是代数数据类型（ADT）的核心概念。

Sealed Class 的设计目标：**让类作者明确控制哪些类可以扩展它，实现受控的多态**。

### 核心原理

- 用 `sealed` 修饰符声明一个类（或接口）
- 用 `permits` 子句指定允许的子类型
- 每个允许的子类型必须声明为 `final`、`sealed` 或 `non-sealed`
- `non-sealed` 表示"开放给任意扩展"——在密封层次结构中打开一个扩展点

### 代码示例

**基本用法：**

```java
// 密封层次结构
public sealed interface Shape
    permits Circle, Rectangle, Triangle, CustomShape {

    double area();
}

public record Circle(double radius) implements Shape {
    public double area() { return Math.PI * radius * radius; }
}

public record Rectangle(double width, double height) implements Shape {
    public double area() { return width * height; }
}

public record Triangle(double base, double height) implements Shape {
    public double area() { return 0.5 * base * height; }
}

// non-sealed: 允许用户自定义形状
public non-sealed interface CustomShape extends Shape {
    // 任何类都可以实现 CustomShape
}
```

**与模式匹配配合实现完备性检查：**

```java
double processShape(Shape shape) {
    return switch (shape) {
        case Circle(var r)       -> Math.PI * r * r;
        case Rectangle(var w, var h) -> w * h;
        case Triangle(var b, var h)  -> 0.5 * b * h;
        case CustomShape cs      -> cs.area(); // 兜底，调用自定义实现
    };
    // 编译器验证：switch 覆盖了所有 permits 子句中的子类型
    // 如果遗漏任何一个，编译报错（无需 default）
}
```

### 实际应用：领域建模

```java
// 支付结果建模
public sealed interface PaymentResult
    permits PaymentSuccess, PaymentFailure, PaymentPending {}

public record PaymentSuccess(String transactionId, BigDecimal amount, Instant timestamp)
    implements PaymentResult {}

public record PaymentFailure(String errorCode, String message, Instant timestamp)
    implements PaymentResult {}

public record PaymentPending(String paymentId, Instant expiresAt)
    implements PaymentResult {}

// 处理支付结果 — 编译器保证覆盖所有情况
void handlePayment(PaymentResult result) {
    switch (result) {
        case PaymentSuccess(var tid, var amt, var ts) ->
            notifyUser("Payment of %s succeeded: %s".formatted(amt, tid));
        case PaymentFailure(var code, var msg, var ts) ->
            logError("Payment failed [%s]: %s".formatted(code, msg));
        case PaymentPending(var pid, var expires) ->
            scheduleRetry(pid, expires);
    }
}
```

### 最佳实践

1. **优先密封接口，而非类**：接口更灵活（record 可以实现它们）。
2. **结合 Record 使用**：Record 不可变，是 sealed 层次结构中数据载体子类型的理想选择。
3. **exhaustiveness check 是最有价值的特性**：密封 + 模式匹配 = 编译时保证分支完备性，消除运行时遗漏。

## 7. String Templates（字符串模板，JEP 465）

### 设计动机

Java 长期缺少安全且可读的字符串插值机制。现有的字符串拼接方式各有缺陷：

- `+` 拼接：当变量多时难以阅读，且易引入注入漏洞
- `String.format()`：格式说明符与参数分离，容易错位
- `MessageFormat`：语法复杂，性能差
- `String.formatted()`：一定程度改善但没有根本解决问题

String Templates 的设计目标：**在编译时将模板中的嵌入表达式安全地组合到字符串中，同时防止注入攻击**。

### 核心原理

String Templates 由两部分组成：

1. **模板表达式**：`STR."text \{expression} more text"`
2. **模板处理器（Template Processor）**：`STR` 是默认处理器，只需简单的插值

模板处理器是一个实现 `StringTemplate.Processor` 接口的对象，它在模板的"洞"（`\{...}`）处插入值，并生成最终结果。不同的处理器有不同的安全策略。

**设计亮点**：模板表达式在编译时解析，`\{...}` 中的表达式在编译时类型检查。模板处理器接收的是结构化的模板（文本片段 + 值的列表），而非一个已拼接的字符串。这意味着处理器可以在插入值之前进行转义（如 SQL 参数化）。

### 代码示例

**基本插值：**

```java
var name = "Alice";
var age = 30;
var city = "Beijing";

// 旧方式
var old = name + " is " + age + " years old from " + city;                // 丑陋
var old2 = String.format("%s is %d years old from %s", name, age, city);  // 格式符与参数分离
var old3 = "%s is %d years old from %s".formatted(name, age, city);       // 稍好但仍有格式符

// String Templates
var message = STR."\{name} is \{age} years old from \{city}";             // 清晰、类型安全
```

**多行模板：**

```java
var product = "Laptop";
var price = 999.99;
var quantity = 3;
var total = price * quantity;

var receipt = STR."""
    ========== Receipt ==========
    Product:  \{product}
    Price:    $\{%.2f.format(price)}
    Quantity: \{quantity}
    ------------------------------
    Total:    $\{%.2f.format(total)}
    ==============================
    """;
```

**表达式在模板中：**

```java
var items = List.of("apple", "banana", "cherry");
var joined = STR."Items: \{String.join(", ", items)}";
var count = STR."Count: \{items.size()} item\{items.size() != 1 ? "s" : ""}";

// 计算表达式
var a = 10; var b = 20;
var calc = STR."\{a} + \{b} = \{a + b}";  // "10 + 20 = 30"
var max = STR."Max: \{Math.max(a, b)}";
```

**自定义模板处理器（安全示例）：**

```java
// SQL 参数化处理器 — 防止 SQL 注入
var SQL = StringTemplate.Processor.of(
    st -> {
        var sql = new StringBuilder();
        var params = new ArrayList<Object>();
        var fragments = st.fragments();
        var values = st.values();

        for (int i = 0; i < fragments.size(); i++) {
            sql.append(fragments.get(i));
            if (i < values.size()) {
                sql.append("?");
                params.add(values.get(i));
            }
        }
        return new ParameterizedSql(sql.toString(), params);
    }
);

// 使用
var username = req.getParameter("username"); // 不可信输入
var query = SQL."SELECT * FROM users WHERE username = \{username}";
// 如果 username = "alice' OR '1'='1"，SQL 处理器会将其安全地参数化
// 生成的 SQL: SELECT * FROM users WHERE username = ?
// 参数: ["alice' OR '1'='1"]
// 彻底防止 SQL 注入
```

**JSON 模板处理器：**

```java
var JSON = StringTemplate.Processor.of(
    st -> {
        var sb = new StringBuilder();
        var fragments = st.fragments();
        var values = st.values();
        for (int i = 0; i < fragments.size(); i++) {
            sb.append(fragments.get(i));
            if (i < values.size()) {
                var v = values.get(i);
                // 简单的 JSON 值转义
                if (v instanceof String s) {
                    sb.append('"').append(s.replace("\"", "\\\"")).append('"');
                } else {
                    sb.append(v);
                }
            }
        }
        return sb.toString();
    }
);

var userId = 42L;
var userName = "Alice \"The Coder\"";
var json = JSON."""
    {
        "id": \{userId},
        "name": \{userName}
    }
    """;
// 输出: { "id": 42, "name": "Alice \"The Coder\"" }
```

### 最佳实践

1. **默认使用 `STR` 处理器**用于日志、用户消息等不需要特殊转义的场景。
2. **为安全敏感场景使用专门的处理器**：SQL、HTML、JSON、Shell 命令等场景必须使用对应的安全处理器，永远不要用 `STR` 然后手动拼接。
3. **自定义处理器的返回值不一定是 String**：如 SQL 处理器可以返回一个包含参数化 SQL 和参数列表的对象。

### 陷阱

- **`STR` 不提供任何安全保证**：它的行为等同于字符串拼接。安全敏感场景必须使用专门的处理器。
- **该特性在 JDK 25 中的状态**：String Templates 在 JDK 21-22 中是 Preview，设计在社区反馈后有调整。JDK 25 中请查阅最新的 JEP 更新，确认是否为 Final。

## 8. Foreign Function & Memory API（FFM API，JEP 454）

### 设计动机

Java 从诞生之初就通过 JNI（Java Native Interface）支持调用本地代码。然而 JNI 存在严重的设计缺陷：

1. **极其复杂**：需要写 C/C++ 代码、生成头文件、管理全局引用、处理 JNI 特有的类型签名
2. **易出错**：手工管理本地内存、资源泄漏风险高
3. **性能差**：每次 JNI 调用有显著的跨边界开销
4. **不安全**：JNI 代码中的 bug（如缓冲区溢出）会直接 crash JVM
5. **不适合 Panama 项目**：JNI 的 C 中心设计不适合调用各类外部函数（如向量化指令、GPU 代码）

FFM API 的设计目标：**提供一个纯 Java API 来调用外部函数（任何语言编译的本地库）和安全地访问外部内存（堆外内存），完全替代 JNI**。

### 核心原理

FFM API 由两个核心抽象组成：

1. **MemorySegment**：表示一块连续的内存区域（堆外或内存映射文件）。提供安全的有界访问——每次读写都进行边界检查。
2. **SymbolLookup + Linker + FunctionDescriptor**：用于查找外部函数符号、链接并调用它。

**Arena（内存作用域）**：管理 MemorySegment 的生命周期。打开一个 Arena，在 Arena 中分配内存，关闭 Arena 时所有关联的内存被释放。类似于 `try-with-resources` 的确定性资源管理。

### 代码示例

**调用 C 标准库函数（`strlen`）：**

```java
// 1. 查找外部函数
var linker = Linker.nativeLinker();
var stdlib = SymbolLookup.libraryLookup(System.mapLibraryName("c"), Arena.ofAuto());

// 2. 描述函数签名
var strlenDesc = FunctionDescriptor.of(
    ValueLayout.JAVA_LONG,  // 返回类型: size_t → long
    ValueLayout.ADDRESS     // 参数类型: const char* → address
);

// 3. 链接
var strlenHandle = stdlib.find("strlen")
    .orElseThrow(() -> new RuntimeException("strlen not found"));
var strlen = linker.downcallHandle(strlenHandle, strlenDesc);

// 4. 调用 — 需要先分配 C 字符串内存
try (var arena = Arena.ofConfined()) {
    var cString = arena.allocateFrom("Hello, World!"); // 分配并写入 C 字符串
    var len = (long) strlen.invoke(cString);
    System.out.println("Length: " + len);  // 13
}
```

**调用系统函数获取 PID：**

```java
// Linux/macOS: getpid()
var linker = Linker.nativeLinker();
var stdlib = SymbolLookup.libraryLookup("c", Arena.ofAuto());

var getpidHandle = stdlib.find("getpid").orElseThrow();
var getpid = linker.downcallHandle(
    getpidHandle,
    FunctionDescriptor.of(ValueLayout.JAVA_INT) // int getpid(void)

```

**安全访问堆外内存：**

```java
// 对比 JNI：FFM API 中的所有内存访问都有边界检查
try (var arena = Arena.ofConfined()) {
    // 分配 1024 字节的堆外内存
    var segment = arena.allocate(1024);

    // 写入（带边界检查）
    var offset = 0;
    for (int i = 0; i < 256; i++) {
        segment.set(ValueLayout.JAVA_INT, offset, i); // 写入 int (4 bytes)
        offset += 4;
    }

    // 读取（带边界检查）
    offset = 0;
    for (int i = 0; i < 256; i++) {
        var value = segment.get(ValueLayout.JAVA_INT, offset);
        offset += 4;
    }

    // 如果偏移超过 1024，抛出 IndexOutOfBoundsException
    // segment.set(ValueLayout.JAVA_INT, 1025, 42); // 抛出异常！
}
// arena.close() 后，segment 失效，进一步访问会抛出异常
```

### 对比：JNI vs FFM API

| 维度 | JNI | FFM API |
|------|-----|---------|
| 需要写 C 代码 | 是 | 否（纯 Java） |
| 内存安全 | 否（缓冲区溢出 crash JVM） | 是（边界检查） |
| 资源管理 | 手动 | Arena（确定性、try-with-resources） |
| 调用开销 | 高 | 低（MethodHandle 优化） |
| 调用约定 | 固定 | 可选（downcall/upcall） |
| 代码量 | 数十行 C + 数十行 Java | 数行 Java |

### 最佳实践

1. **使用 `Arena.ofConfined()`**：确保单线程访问，性能最佳且安全。
2. **使用 try-with-resources 管理 Arena**：确保确定性释放。
3. **优先使用 FFM API 而非 `Unsafe` 或 `DirectByteBuffer`**：FFM API 是安全且有界的。
4. **对于简单的系统调用，优先使用 Java 库**：FFM API 是底层机制，大多数系统调用已有 Java 封装。

## 9. Vector API（向量 API，JEP 460，第七次孵化）

### 设计动机

现代 CPU 支持 SIMD（Single Instruction, Multiple Data）指令集，可以在一个 CPU 周期内对多个数据执行相同操作。例如，AVX-512 可以一次处理 16 个 32 位整数的加法。传统的 Java 循环是标量的（一次一个元素），白白浪费了 CPU 的 SIMD 能力。

JVM 的 JIT 编译器（C2）可以进行自动向量化（auto-vectorization），但它只在简单循环中有效，且不可预测（编译器的优化决策是启发式的）。

Vector API 的设计目标：**提供明确的、平台无关的向量化编程模型，让开发者可靠地利用 CPU SIMD 指令集，同时 JIT 编译器将向量操作编译为最优的硬件指令**。

### 核心原理

1. **Vector<E>**：表示一个可以容纳多个元素的向量。`Vector` 的 E 是元素类型（`Byte`、`Short`、`Int`、`Long`、`Float`、`Double`）。
2. **VectorSpecies<E>**：定义向量的"形状"——元素类型和长度。`VectorSpecies` 的实际长度取决于硬件支持的向量寄存器宽度（如 128-bit、256-bit、512-bit）。
3. **VectorMask<E>**：用于条件操作，选择性地将操作应用到向量的部分元素。
4. **VectorShuffle<E>**：用于重排向量中的元素。

### 代码示例

**标量 vs 向量：两个数组元素相加：**

```java
// 传统标量方式
void scalarAdd(float[] a, float[] b, float[] c) {
    for (int i = 0; i < a.length; i++) {
        c[i] = a[i] + b[i];
    }
}

// Vector API 方式
static final VectorSpecies<Float> SPECIES = FloatVector.SPECIES_PREFERRED;

void vectorAdd(float[] a, float[] b, float[] c) {
    int i = 0;
    var length = SPECIES.loopBound(a.length); // 向量化部分的上界

    // 以向量为单位处理
    for (; i < length; i += SPECIES.length()) {
        var va = FloatVector.fromArray(SPECIES, a, i);
        var vb = FloatVector.fromArray(SPECIES, b, i);
        var vc = va.add(vb);  // 一个指令执行 SPECIES.length() 个加法
        vc.intoArray(c, i);
    }

    // 处理剩余元素（少于一个向量长度的尾部）
    for (; i < a.length; i++) {
        c[i] = a[i] + b[i];
    }
}
```

**使用 VectorMask 进行条件操作：**

```java
// 将数组中所有正数翻倍，负数和零保持不变
void doublePositives(float[] arr) {
    var species = FloatVector.SPECIES_PREFERRED;
    int i = 0;
    var bound = species.loopBound(arr.length);

    for (; i < bound; i += species.length()) {
        var v = FloatVector.fromArray(species, arr, i);
        var mask = v.gt(0.0f);           // 创建掩码：哪些元素 > 0
        var doubled = v.mul(2.0f);       // 所有元素翻倍
        var result = v.blend(doubled, mask); // 只对 mask 为 true 的元素取 doubled 的值
        result.intoArray(arr, i);
    }

    for (; i < arr.length; i++) {
        if (arr[i] > 0) arr[i] *= 2;
    }
}
```

**点积（Dot Product）— SIMD 经典场景：**

```java
float dotProduct(float[] a, float[] b) {
    var species = FloatVector.SPECIES_PREFERRED;
    var acc = FloatVector.zero(species);  // 初始累加器
    int i = 0;
    var bound = species.loopBound(a.length);

    for (; i < bound; i += species.length()) {
        var va = FloatVector.fromArray(species, a, i);
        var vb = FloatVector.fromArray(species, b, i);
        acc = acc.add(va.mul(vb));  // FMA: fused multiply-add
    }

    // 将累加器中的多个部分和归约为一个标量
    var result = acc.reduceLanes(VectorOperators.ADD);

    // 标量尾部
    for (; i < a.length; i++) {
        result += a[i] * b[i];
    }
    return result;
}
```

### 性能特征

Vector API 在以下场景具有显著性能优势（2-16x 加速，取决于硬件支持）：

- 数学运算（大规模数组加减乘除）
- 线性代数（矩阵乘法、点积）
- 图像处理（像素操作、卷积）
- 信号处理（FFT、滤波）
- 文本处理（字符分类、转码）
- ML 推理（激活函数、归一化）

### 最佳实践

1. **使用 `SPECIES_PREFERRED`**：让 JVM 选择当前硬件支持的最佳向量长度。
2. **保持循环简单**：Vector API 主要适用于简单、规则的数据并行模式。复杂的控制流不适合向量化。
3. **尾循环必须保留**：数组长度很少刚好是向量长度的整数倍，必须处理剩余元素。
4. **避免过多的 lane-wise 操作**：尽量保持数据在向量寄存器内，减少与标量寄存器之间的数据移动。

### 陷阱

- **仍然在 Incubating（孵化中）**：Vector API 在 JDK 25 中仍在孵化阶段（第七次），API 可能变化。生产使用需将 `--add-modules jdk.incubator.vector` 加入编译和运行时参数。
- **硬件依赖**：可用的 SPECIES 长度取决于 CPU。同样的代码在 AVX-512 CPU 上一次处理 16 个 int，而在 ARM NEON CPU 上一次处理 4 个 int。
- **调试困难**：向量操作被编译为硬件指令后，调试器难以逐元素查看中间值。

## 跨特性综合示例：支付处理系统

以下示例综合运用了本文涉及的多项特性：

```java
import java.time.Instant;
import java.util.*;
import java.util.concurrent.*;

/**
 * 支付处理系统 — 展示 JDK 25 多项特性协同使用
 */
public class ModernPaymentSystem {

    // === 领域模型：Record + Sealed ===

    sealed interface PaymentResult
        permits PaymentSuccess, PaymentFailure, PaymentPending {}

    record PaymentSuccess(String txnId, Money amount, Instant time) implements PaymentResult {}
    record PaymentFailure(String code, String message, Instant time) implements PaymentResult {}
    record PaymentPending(String paymentId, Instant expires) implements PaymentResult {}
    record Money(BigDecimal amount, String currency) {
        public Money {
            if (amount.compareTo(BigDecimal.ZERO) < 0) {
                throw new IllegalArgumentException("金额不能为负");
            }
        }
    }

    // === ScopedValue: 传递请求上下文 ===

    static final ScopedValue<String> REQUEST_ID = ScopedValue.newInstance();
    static final ScopedValue<String> USER_ID = ScopedValue.newInstance();

    // === 服务入口：结合 ScopedValues + Structured Concurrency + Virtual Threads ===

    PaymentResult processPayment(Money amount, String userId) {
        return ScopedValue.where(REQUEST_ID, UUID.randomUUID().toString())
            .where(USER_ID, userId)
            .call(() -> {
                try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
                    // 并行执行风险检查和账户验证
                    var riskCheck = scope.fork(this::checkRisk);
                    var accountCheck = scope.fork(this::validateAccount);

                    scope.join();
                    scope.throwIfFailed();

                    // 两阶段都通过后执行支付
                    if (!riskCheck.get().passed()) {
                        return new PaymentFailure("RISK", "风险检查未通过", Instant.now());
                    }

                    return executePayment(amount);
                }
            });
    }

    // === Pattern Matching 处理结果 ===

    String formatResult(PaymentResult result) {
        return switch (result) {
            case PaymentSuccess(var txn, var amt, var time)
                when amt.amount().compareTo(new BigDecimal("10000")) > 0
                -> STR."大额支付成功: 交易号=\{txn}, 金额=\{amt}";

            case PaymentSuccess(var txn, var amt, var time)
                -> STR."支付成功: 交易号=\{txn}, 金额=\{amt}";

            case PaymentFailure(var code, var msg, var time)
                -> STR."支付失败 [\{code}]: \{msg}";

            case PaymentPending(var pid, var expires)
                -> STR."支付处理中: \{pid}, 超时时间: \{expires}";
        };
    }

    // === 批量支付：使用 Vector API 计算总金额 ===

    BigDecimal calculateTotal(float[] amounts) {
        var species = FloatVector.SPECIES_PREFERRED;
        var acc = FloatVector.zero(species);
        int i = 0;
        var bound = species.loopBound(amounts.length);

        for (; i < bound; i += species.length()) {
            var v = FloatVector.fromArray(species, amounts, i);
            acc = acc.add(v);
        }

        var total = acc.reduceLanes(VectorOperators.ADD);

        for (; i < amounts.length; i++) {
            total += amounts[i];
        }

        return new BigDecimal(String.valueOf(total));
    }

    // === 辅助方法（存根实现）===

    record RiskResult(boolean passed, String reason) {}
    record AccountResult(boolean valid, String accountId) {}

    RiskResult checkRisk() {
        var userId = USER_ID.get();
        // 实际实现：查询风控系统
        return new RiskResult(true, "OK");
    }

    AccountResult validateAccount() {
        var userId = USER_ID.get();
        // 实际实现：查询账户服务
        return new AccountResult(true, userId);
    }

    PaymentResult executePayment(Money amount) {
        // 实际实现：调用支付网关
        return new PaymentSuccess(
            UUID.randomUUID().toString(), amount, Instant.now());
    }
}
```

## 常见问题

**Q: Virtual Threads 是否使 CompletableFuture 过时？**
A: 两者解决不同的问题。Virtual Threads 替代的是"为了非阻塞 I/O 而被迫编写的异步代码"。当业务逻辑天然是异步的（如等待多个外部服务的最快响应），`CompletableFuture.anyOf()` 和 `StructuredTaskScope.ShutdownOnSuccess()` 仍然有用。但对于大多数服务端业务代码，同步风格 + 虚拟线程是更好的选择。

**Q: 所有现有代码都应该迁移到 Virtual Threads 吗？**
A: 对于 I/O 密集型服务（如 Web 服务器、微服务、数据库代理），迁移价值巨大。对于 CPU 密集型服务（如计算引擎、视频编码），迁移收益有限。迁移前先做 profiling。

**Q: Scoped Values 完全替代 ThreadLocal 吗？**
A: 在请求级别的上下文传递场景中（Web 请求、事务性操作）是替代。但对于线程生命周期长的场景（如线程池中的缓存），ThreadLocal 仍有用。核心判断标准：值的生命周期是否与代码块（作用域）绑定。
