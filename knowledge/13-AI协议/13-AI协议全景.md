# AI Agent 协议全景

## 三类边界

AI 应用里的“工具调用”并不是一个协议就能解决的问题。工程设计应先判断交互跨越了哪一层边界：

| 机制 | 连接的两端 | 主要职责 | 典型生命周期 |
|---|---|---|---|
| 应用内 Tool Calling | 模型与应用函数 | 参数生成、函数执行、结果回填 | 单次或多轮模型调用 |
| MCP | AI Host/Client 与能力 Server | 工具、资源、Prompt 的发现和调用 | 有状态会话 |
| A2A | 独立 Agent 与独立 Agent | 能力发现、消息、任务与制品协作 | 跨系统任务 |

三者可以组合，但不能混用概念：

- Tool Calling 的函数名不是 MCP 工具发现协议。
- MCP 的 `tools/call` 不是 A2A 的消息发送。
- A2A 的 Task 是跨 Agent 协作状态，不等同于一次模型推理。

## 选型顺序

1. 能力只在一个进程内使用时，优先应用内 Tool Calling。
2. 多个 AI 客户端要复用同一组工具或资源时，考虑 MCP。
3. 两个自治 Agent 需要交换消息、任务状态和制品时，考虑 A2A。
4. MCP Server 若需要完成长任务，可以把内部执行委托给 A2A Agent，但外部契约仍须保持清晰。

## 统一治理面

无论采用哪种协议，生产系统都需要统一的治理面：

- 身份：调用主体、租户和最终用户必须可区分。
- 授权：工具、资源、Agent 能力按最小权限授权。
- 输入输出：结构校验与大小、类型、内容策略限制。
- 可观测：记录协议、操作名、耗时、状态和关联 ID，不记录秘密。
- 审计：保留授权结果、人工审批和高风险动作结果。
- 降级：远端不可用时返回明确、可恢复的失败状态。
