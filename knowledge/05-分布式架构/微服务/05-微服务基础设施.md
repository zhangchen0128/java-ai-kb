# 微服务基础设施

## 概述

微服务基础设施是分布式系统稳定运行的基石。当单体应用拆分为数十甚至数百个独立服务后，三个根本问题随之而来：(1) 服务实例动态变化，调用方如何发现目标服务？(2) 配置散落在各服务中，如何集中管理和动态变更？(3) 请求跨多个服务，如何追踪完整的调用链路？服务注册与发现、配置中心、API 网关和分布式链路追踪构成了回答这三个问题的四大基础设施。

本文以 Nacos + Spring Cloud Gateway + Micrometer Tracing 为技术主线，深入服务注册发现的 AP/CP 协议权衡、配置中心的灰度发布与动态刷新机制、网关的路由断言过滤器三大核心、以及分布式链路追踪的采样策略与跨线程传播，覆盖从原理到生产实践的全链路知识。

## 一、服务注册与发现

### 1.1 Nacos 注册中心深度解析

Nacos（Dynamic Naming and Configuration Service）是阿里巴巴开源的集注册中心和配置中心于一体的基础设施组件，在 Spring Cloud Alibaba 生态中处于核心地位。

**AP 模式 — Distro 协议（临时实例）：**

Distro 协议是 Nacos 自研的 AP 一致性协议，专为临时实例设计。其工作原理：

```
┌─────────────────────────────────────────────────────┐
│                 Distro 协议工作流程                    │
│                                                      │
│   Client A  ──心跳──►  Node 1 ◄──同步──►  Node 2     │
│     │                    │                  │        │
│     │                DistroTask              │        │
│     │              (异步批量同步)             │        │
│     │                    │                  │        │
│     ▼                    ▼                  ▼        │
│   注册临时实例      本地数据存储          本地数据存储   │
│  (ephemeral=true)   + 异步同步到          + 接收同步    │
│                     其他节点              数据          │
└─────────────────────────────────────────────────────┘
```

关键行为：
- 临时实例通过 HTTP/UDP 心跳维持租约，默认心跳间隔 5 秒
- 连续 3 次心跳丢失（15 秒）后，Nacos 自动剔除该实例
- 数据同步采用异步批量方式（DistroTask），不阻塞注册请求
- 各节点独立判断实例健康状态，无中心化决策

**CP 模式 — Raft 协议（持久实例）：**

持久实例适用于期望即使服务下线也保留注册信息的场景（如数据库、中间件地址）：

```java
// 注册持久实例
var instance = new Instance();
instance.setIp("192.168.1.100");
instance.setPort(8080);
instance.setEphemeral(false);  // 持久实例 → 走 Raft 协议
instance.setClusterName("DEFAULT");

// NacosNamingService 内部根据 ephemeral 字段分流：
// ephemeral=true  → Distro 协议 → 临时节点
// ephemeral=false → Raft 协议   → 持久节点
```

CP 模式下的特性：
- 注册数据通过 Raft 一致性协议在集群中达成共识
- 实例下线后信息保留，不会自动剔除
- 适合注册数据库、消息队列等基础设施地址
- 写操作需要 Leader 节点处理，读操作可负载均衡

**Naming Service 三级隔离模型：**

```
Namespace (命名空间)         ← 租户/环境级隔离
  └─ Group (分组)            ← 业务/应用级隔离
       └─ Service (服务)      ← 具体微服务
            └─ Cluster (集群)  ← 同城/异地/灰度
                 └─ Instance (实例)
```

```yaml
# 服务发现配置示例
spring:
  cloud:
    nacos:
      discovery:
        server-addr: 127.0.0.1:8848
        namespace: dev           # dev/test/prod 环境隔离
        group: order-service     # 业务分组
        cluster-name: BJ         # 北京集群
        ephemeral: true          # 临时实例（AP）
```

**健康检查机制：**

| 检查类型 | 协议 | 适用场景 | 关键参数 |
|----------|------|----------|----------|
| TCP | TCP 连接 | 通用服务 | 端口可达即健康 |
| HTTP | GET 请求 | Web 服务 | 自定义路径、期望状态码 200 |
| MySQL | SQL 查询 | 数据库 | SELECT 1 探测 |

**源码关键类：**

| 类名 | 职责 |
|------|------|
| `NacosServiceRegistry` | 实现 Spring Cloud `ServiceRegistry` 接口，封装注册/注销逻辑 |
| `NacosRegistration` | 持有注册元数据：服务名、IP、端口、权重、元数据 Map |
| `NacosDiscoveryClient` | 实现 `DiscoveryClient`，提供 `getInstances(serviceId)` |
| `NacosWatch` | 定时心跳任务，维护与 Nacos Server 的连接和实例续约 |

### 1.2 Eureka — AP 模式与自我保护

Eureka 的自我保护机制是面试和故障排查中的高频话题：

```
自我保护触发条件：
  15 分钟内，实际心跳数 < 期望心跳数 × 85%

触发后行为：
  - 不再剔除任何实例（即使心跳超时）
  - 日志输出 "EMERGENCY! EUREKA MAY BE INCORRECTLY CLAIMING INSTANCES ARE UP"
  - 新注册和续约请求正常处理

风险：自我保护期间，调用方可能拿到已宕机的实例 → 必须配合重试+熔断
```

Eureka 的多层缓存架构：

```
服务实例变更
    │
    ▼
responseCache (ConcurrentHashMap, 180s TTL)
    │
    ▼
readWriteCacheMap (LoadingCache, 180s expire)
    │
    ▼
readOnlyCacheMap (ConcurrentHashMap, 30s 定时同步)
    │
    ▼
客户端拉取（默认 30s 间隔）
```

这导致 Eureka 的"最大不可用时间窗口"可达 30s（只读缓存同步间隔）+ 30s（客户端拉取间隔）= 60s，远超 Nacos 的 15s（3 次心跳间隔）。

### 1.3 Consul — CP 模式与 Service Mesh 就绪

Consul 基于 Raft 协议实现强一致性，内置健康检查丰富度超过 Nacos 和 Eureka：

```
健康检查类型：
  - Script:    执行自定义脚本，退出码 0 = 健康
  - HTTP:      GET /health 端点，2xx = 健康
  - TCP:       TCP 连接成功 = 健康
  - TTL:       应用主动上报，TTL 内上报即健康
  - gRPC:      gRPC Health Checking Protocol
  - Alias:     关联其他检查结果
```

Consul 在 Service Mesh 时代具备天然优势：
- 内置 Connect 功能，支持 mTLS 认证和 ACL 授权
- 原生 Sidecar Proxy（envoy）集成
- 支持 L7 流量策略（路由、分流、重试）

### 1.4 注册中心对比选型

| 维度 | Nacos | Eureka | Consul |
|------|-------|--------|--------|
| CAP 模型 | AP + CP 双模式 | AP | CP |
| 一致性协议 | Distro (AP) / Raft (CP) | Peer to Peer (最终一致) | Raft |
| 健康检查 | TCP/HTTP/MySQL | HTTP (默认) | Script/HTTP/TCP/TTL/gRPC |
| 配置中心 | 内置，功能完整 | 无（需配合 Spring Cloud Config） | 内置 KV Store |
| 控制台 | 完善（服务列表/详情/权重/保护阈值） | 基础 | 完善 |
| 自我保护 | 可配置 | 内置且不可关闭 | 无 |
| Spring Cloud 集成 | spring-cloud-starter-alibaba-nacos-discovery | spring-cloud-starter-netflix-eureka-client | spring-cloud-starter-consul-discovery |
| 社区活跃度 | 高（阿里维护，中文社区活跃） | 中（Netflix 已归档维护模式） | 高（HashiCorp 维护） |
| 推荐场景 | 首选，功能最全面 | 存量系统维护 | Service Mesh、强一致性需求 |

### 1.5 Spring Cloud LoadBalancer

Spring Cloud 2020.0 版本后，官方的 Spring Cloud LoadBalancer 正式替代了进入维护模式的 Netflix Ribbon。

```java
@Configuration
public class LoadBalancerConfig {

    // 方式一：按 serviceId 配置负载均衡策略
    @Bean
    @LoadBalanced
    public RestClient.Builder restClientBuilder() {
        return RestClient.builder();
    }

    // 方式二：自定义负载均衡策略
    @Bean
    public ReactorLoadBalancer<ServiceInstance> customLoadBalancer(
            Environment env,
            LoadBalancerClientFactory factory) {

        var serviceId = env.getProperty(LoadBalancerClientFactory.PROPERTY_NAME);

        // 加权随机策略
        return new RandomLoadBalancer(
                factory.getLazyProvider(serviceId, ServiceInstanceListSupplier.class),
                serviceId
        );
    }
}

// 使用 Virtual Threads + LoadBalanced RestClient
@Service
public class OrderServiceClient {

    private final RestClient restClient;

    public OrderServiceClient(@LoadBalanced RestClient.Builder builder) {
        this.restClient = builder.baseUrl("http://order-service").build();
    }

    public OrderDto getOrder(Long orderId) {
        // 底层通过 ServiceInstanceListSupplier 从注册中心获取实例列表
        // LoadBalancer 选择具体实例后发起 HTTP 调用
        return restClient.get()
                .uri("/api/orders/{id}", orderId)
                .retrieve()
                .body(OrderDto.class);
    }
}
```

`ServiceInstanceListSupplier` 是实例获取的核心接口，Spring Cloud 提供了多个实现：

| 实现类 | 功能 |
|--------|------|
| `DiscoveryClientServiceInstanceListSupplier` | 从注册中心获取实例列表 |
| `CachingServiceInstanceListSupplier` | 缓存实例列表，减少注册中心查询 |
| `HealthCheckServiceInstanceListSupplier` | 过滤掉不健康的实例 |
| `ZonePreferenceServiceInstanceListSupplier` | 优先同区域实例 |
| `SameInstancePreferenceServiceInstanceListSupplier` | 粘性会话（sticky session） |

## 二、配置中心

### 2.1 Nacos Config 深度配置

**dataId 命名规范：**

Nacos 中配置的唯一标识由 dataId + group 共同组成。Spring Cloud Alibaba 中 dataId 的默认拼接规则：

```
${spring.application.name}-${spring.profiles.active}.${spring.cloud.nacos.config.file-extension}

示例：
  order-service-dev.yml
  order-service-prod.yml
  order-service.yml              ← 不指定 profile 时
```

**命名空间与分组的多层隔离策略：**

```
                                    Nacos Config
                                         │
         ┌───────────────────────────────┼───────────────────────────────┐
         │                               │                               │
    namespace:dev                   namespace:test                 namespace:prod
         │                               │                               │
    ┌────┴────┐                   ┌────┴────┐                   ┌────┴────┐
    │         │                   │         │                   │         │
  group:    group:              group:    group:              group:    group:
  ORDER    PAYMENT             ORDER    PAYMENT             ORDER    PAYMENT
    │         │                   │         │                   │         │
  dataId:   dataId:            dataId:   dataId:            dataId:   dataId:
  order-   payment-           order-    payment-           order-    payment-
  service  service            service   service            service   service
```

**配置灰度发布（Beta IP）：**

Nacos 支持按 IP 维度进行配置灰度，即指定 IP 的实例拉取 Beta 版配置：

```yaml
# 操作流程（通过控制台或 API）：
# 1. 创建正式配置：order-service-dev.yml（version: 1）
# 2. 创建 Beta 配置：选择目标 IP 列表 ["192.168.1.10", "192.168.1.11"]
# 3. 灰度验证通过后，发布 Beta 配置为正式配置
```

配置拉取逻辑：
```
Client 请求配置 → Server 检查请求 IP
  ├─ IP 在 Beta 白名单中 → 返回 Beta 版本配置
  └─ IP 不在白名单中   → 返回正式版本配置
```

**配置监听 — Long Polling（长轮询）机制：**

```
┌─────────┐                    ┌──────────┐
│  Client  │                    │  Server  │
└────┬────┘                    └────┬─────┘
     │                              │
     │  GET /config?dataId=xxx      │
     │  + MD5=abc123               │
     │─────────────────────────────►│
     │                              │ 对比当前 MD5
     │                              │ MD5 未变 → hold 29.5s
     │                              │
     │  ... (最长 hold 30s) ...     │
     │                              │
     │  304 Not Modified (MD5相同)  │
     │◄─────────────────────────────│
     │                              │
     │  立即发起下一次 GET (重新hold)│
     │─────────────────────────────►│
     │                              │
     │  这次 MD5 不同               │
     │  200 OK + 新配置内容          │
     │◄─────────────────────────────│
     │                              │
     │  Client 更新本地配置           │
     │  触发 RefreshEvent           │
     │                              │
```

MD5 检测是 Long Polling 的核心：服务端在 hold 期间不断检查配置的 MD5 值是否变化，变化时立即返回新内容，未变化则等到超时（约 30 秒）返回 304。

**敏感配置加密：**

```yaml
# 加密配置值（Nacos 控制台操作或 API）
# 明文: spring.datasource.password=MyP@ssw0rd
# 加密后: spring.datasource.password={cipher}U2FsdGVkX1+...

# Java 端解密插件
@Component
public class AesEncryptionPlugin implements EncryptionPlugin {

    private static final String AES_KEY = System.getenv("NACOS_AES_KEY");

    @Override
    public String encrypt(String plainText) {
        // AES 对称加密
        return AESUtils.encrypt(plainText, AES_KEY);
    }

    @Override
    public String decrypt(String cipherText) {
        // AES 对称解密
        return AESUtils.decrypt(cipherText, AES_KEY);
    }
}
```

### 2.2 Spring Cloud Config

### 2.3 动态刷新机制

```java
// 方式一：@RefreshScope — 延迟重建 Bean
@RestController
@RefreshScope  // 收到 RefreshScopeRefreshedEvent 后，下次访问时重新初始化
public class FeatureController {

    @Value("${feature.new-checkout.enabled:false}")
    private boolean newCheckoutEnabled;

    @GetMapping("/feature/checkout-v2")
    public String checkout() {
        return newCheckoutEnabled ? "V2" : "V1";
    }
}

// 方式二：@ConfigurationProperties — 自动绑定刷新
@ConfigurationProperties(prefix = "app")
@Component
public class AppProperties {
    private int timeout;
    private int maxRetries;
    // getters/setters...
    // 属性变更时 EnvironmentChangeEvent 触发 → 自动重新绑定
}

// 方式三：监听 EnvironmentChangeEvent
@Component
public class ConfigChangeListener {

    @EventListener
    public void onEnvironmentChange(EnvironmentChangeEvent event) {
        // event.getKeys() 返回变更的 key 列表
        // 执行自定义清理逻辑：如清空本地缓存、重建连接池
        for (String key : event.getKeys()) {
            log.info("配置变更: {}", key);
        }
    }
}
```

**Spring Cloud Bus 批量刷新：**

```
POST /actuator/busrefresh?destination=order-service:**
  → 通过消息总线 (Kafka/RabbitMQ) 广播 RefreshRemoteApplicationEvent
  → 所有匹配 destination 的节点收到事件后刷新配置
```

### 2.4 配置中心对比

| 维度 | Nacos Config | Spring Cloud Config |
|------|-------------|-------------------|
| 配置存储 | 内置数据库 (Derby/MySQL) | Git / SVN / Vault / JDBC |
| 版本管理 | 内置历史版本（保留 30 天） | 依赖 Git 历史 |
| 灰度发布 | Beta IP 白名单 | 较难实现 |
| 管理 UI | 完善（配置编辑/历史/监听查询） | 无（依赖 Git 平台） |
| 动态刷新 | Long Polling | 需配合 Bus |
| 敏感配置加密 | 自定义加密插件 | {cipher} + encrypt.key |
| 推荐场景 | 功能更全，首选 | GitOps 工作流、简单场景 |

## 三、API 网关 — Spring Cloud Gateway

### 3.1 核心三要素

Spring Cloud Gateway 基于 Spring WebFlux（Netty）构建，三大核心概念：

```
Route（路由）= Route ID + 目标 URI + Predicates 集合 + Filters 集合

请求 → Predicates（断言匹配）
         ├─ 匹配 → Filters（过滤器链处理）→ 目标 URI
         └─ 不匹配 → 尝试下一条路由 → 最终 404
```

路由匹配优先级：按 `order` 值从小到大排序，第一个匹配的路由生效。order 默认 0，相同时按加载顺序。

### 3.2 Route Predicates（路由断言）

```yaml
spring:
  cloud:
    gateway:
      routes:
        # 路径匹配 — 最常用
        - id: user-service
          uri: lb://user-service
          predicates:
            - Path=/api/v1/users/**
          filters:
            - StripPrefix=1           # 剥离 /api 前缀后转发

        # Host 匹配 — 多域名路由
        - id: api-v2
          uri: lb://api-v2
          predicates:
            - Host=api-v2.example.com

        # 组合匹配
        - id: order-read
          uri: lb://order-service
          predicates:
            - Path=/api/orders/**
            - Method=GET                # 仅 GET 请求
            - Header=X-Version, v2      # 指定 Header
            - Query=includeDetails, true # 指定 Query 参数

        # 基于时间的路由（A/B 测试、定时上线）
        - id: promotion-route
          uri: lb://promotion-v2
          predicates:
            - Path=/api/promotions/**
            - After=2026-07-20T00:00:00+08:00
            - Before=2026-07-27T23:59:59+08:00

        # 权重路由 — 灰度发布
        - id: order-v1
          uri: lb://order-service-v1
          predicates:
            - Path=/api/orders/**
            - Weight=order-group, 80   # 80% 流量到 v1
        - id: order-v2
          uri: lb://order-service-v2
          predicates:
            - Path=/api/orders/**
            - Weight=order-group, 20   # 20% 流量到 v2
```

### 3.3 GatewayFilter 与 GlobalFilter

**GatewayFilter（路由级）：**

```yaml
spring:
  cloud:
    gateway:
      routes:
        - id: llm-service
          uri: lb://llm-service
          predicates:
            - Path=/api/llm/**
          filters:
            # 限流 — Redis 令牌桶
```

**GlobalFilter（全局级）— JWT 鉴权实现：**

```java
@Component
@Order(-1) // 高优先级，确保最先执行
public class JwtAuthGlobalFilter implements GlobalFilter {

    // 白名单路径，跳过鉴权
    private static final List<String> WHITELIST = List.of(
            "/api/auth/login",
            "/api/auth/register",
            "/api/public/**"
    );

    private static final AntPathMatcher pathMatcher = new AntPathMatcher();

    @Override
    public Mono<Void> filter(ServerWebExchange exchange, GatewayFilterChain chain) {
        var path = exchange.getRequest().getURI().getPath();

        // 白名单放行
        if (WHITELIST.stream().anyMatch(p -> pathMatcher.match(p, path))) {
            return chain.filter(exchange);
        }

        var authHeader = exchange.getRequest().getHeaders().getFirst(HttpHeaders.AUTHORIZATION);
        if (authHeader == null || !authHeader.startsWith("Bearer ")) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }

        try {
            var token = authHeader.substring(7);
            var claims = JwtUtils.parseToken(token);

            // 将用户信息注入 Header 向下游传递，下游服务无需再次解析 JWT
            exchange = exchange.mutate()
                    .request(r -> r.header("X-User-Id", claims.getSubject())
                                   .header("X-User-Name", claims.get("name", String.class))
                                   .header("X-Tenant-Id", claims.get("tenantId", String.class)))
                    .build();

            return chain.filter(exchange);
        } catch (JwtException e) {
            exchange.getResponse().setStatusCode(HttpStatus.UNAUTHORIZED);
            return exchange.getResponse().setComplete();
        }
    }
}
```

**跨线程传播 — Virtual Threads 时代的解决方案：**

```java
// JDK 25: Scoped Values 替代 ThreadLocal，天然支持 Virtual Thread 上下文传播
// Micrometer Tracing 已适配 Scoped Values

// 方式一：Observation API 自动传播（推荐）
// @Async 方法中，框架自动通过 Scoped Values 传递 Observation 上下文

// 方式二：手动包装（JDK 25 的 StructuredTaskScope）
public List<Order> fetchOrdersInParallel(List<Long> orderIds) {
    var observation = Observation.createNotStarted("order.batch-fetch", registry)
            .start();

    try (var scope = new StructuredTaskScope.ShutdownOnFailure()) {
        var tasks = orderIds.stream()
                .map(id -> scope.fork(() -> fetchOrder(id)))
                .toList();
        scope.join();
        return tasks.stream().map(Future::resultNow).toList();
    } catch (InterruptedException e) {
        Thread.currentThread().interrupt();
        throw new RuntimeException(e);
    } finally {
        observation.stop();
    }
}
```

Scoped Values 相比 ThreadLocal 的根本优势：Scoped Value 绑定到"值的生命周期"而非"线程的生命周期"，Virtual Thread 被调度到不同 Carrier Thread 时上下文不会丢失。

```java
@Configuration
public class TracingConfig {

    @Bean
    public SamplerFunction<HttpServerRequest> httpSampler() {
        return request -> {
            // 错误路径全量采样
            if (request.path().startsWith("/api/error-report")) {
                return true;
            }
            // 健康检查不采样
            if (request.path().startsWith("/actuator")) {
                return false;
            }
            // 统计类接口低采样率

                return Math.random() < 0.01;
            }
            return Math.random() < 0.1;
        };
    }

    // 基于响应状态的采样
    @Bean
    public SamplerFunction<HttpServerResponse> httpResponseSampler() {
        return response -> {
            var status = response.statusCode();
            // 5xx 错误 100% 采样
            if (status >= 500) return true;
            // 2xx/3xx 按正常比例
            return Math.random() < 0.1;
        };
    }
}

// 自适应采样 — 基于 QPS 动态调整
@Component
public class AdaptiveSampler {

    private final AtomicLong requestCount = new AtomicLong(0);
    private volatile double samplingRate = 0.1; // 初始 10%

    @Scheduled(fixedRate = 10_000)
    public void adjustRate() {
        var qps = requestCount.getAndSet(0) / 10.0;
        if (qps > 1000) {
            samplingRate = 0.01;  // 高 QPS 时降低采样率
        } else if (qps > 100) {
            samplingRate = 0.05;
        } else {
            samplingRate = 0.1;   // 低 QPS 时提高采样率
        }
    }

    public boolean shouldSample() {
        requestCount.incrementAndGet();
        return Math.random() < samplingRate;
    }
}
```

```java
public class CustomTracingSamplingConfig {

    /**
     * 分层采样策略：
     * - /api/health/** → 不采样
     * - /api/statistics/** → 1% 采样
     * - 5xx 错误 → 100% 采样
     * - 4xx 错误 → 20% 采样
     * - 正常请求 → 10% 采样

    @Bean
    public HttpSampler httpSampler(ObservationRegistry registry) {
        return new HttpSampler() {

            private final AntPathMatcher matcher = new AntPathMatcher();

            @Override
            public boolean shouldSample(HttpServerRequest request) {
                var path = request.path();

                // 健康检查和 actuator 端点不采样
                if (matcher.match("/actuator/**", path)
                        || matcher.match("/api/health/**", path)) {
                    return false;
                }

                // 统计接口低采样
                if (matcher.match("/api/statistics/**", path)) {
                    return ThreadLocalRandom.current().nextDouble() < 0.01;
                }

                return ThreadLocalRandom.current().nextDouble() < 0.1;

                // 5xx 全采：故障排查不能丢失任何一条
                if (status >= 500) return true;

                // 4xx 提高采样率：排查客户端错误模式
                if (status >= 400) {
                    return ThreadLocalRandom.current().nextDouble() < 0.2;
                }

                return ThreadLocalRandom.current().nextDouble() < 0.1;

        };
```

```java
// 加权随机负载均衡器
class WeightedRandomLoadBalancer extends RandomLoadBalancer {

    WeightedRandomLoadBalancer(ObjectProvider<ServiceInstanceListSupplier> supplier,
                               String serviceId) {
        super(supplier, serviceId);
    }

    @Override
    protected Mono<Response<ServiceInstance>> choose(Request request, String serviceId) {
        return getServiceInstances(serviceId)
                .map(instances -> {
                    if (instances.isEmpty()) return new EmptyResponse();

                    // 按权重分配概率区间
                    var totalWeight = instances.stream()
                            .mapToDouble(i -> {
                                var meta = i.getMetadata();
                                return meta.containsKey("nacos.weight")
                                        ? Double.parseDouble(meta.get("nacos.weight"))
                                        : 1.0;
                            })
                            .sum();

                    var random = ThreadLocalRandom.current().nextDouble() * totalWeight;
                    double cumulative = 0.0;
                    for (var instance : instances) {
                        var weight = Double.parseDouble(
                                instance.getMetadata().getOrDefault("nacos.weight", "1.0"));
                        cumulative += weight;
                        if (random <= cumulative) {
                            return new DefaultResponse(instance);
                        }
                    }
                    return new DefaultResponse(instances.getFirst());
                });
    }
}
```

## 常见问题

**Q: Nacos 1.x 升级 2.x 有哪些注意事项？**

A: Nacos 2.x 的 gRPC 通信协议是最大的变化，1.x 使用 HTTP + UDP，2.x 引入了 gRPC 长连接。升级要点：(1) 客户端必须升级到 2.x 对应的 SDK；(2) 2.x 新增了两个 gRPC 端口（默认 9848/9849），需在防火墙放行；(3) 2.x 中临时实例的心跳走 gRPC 长连接而非 HTTP 心跳，更高效但需确认网络可达；(4) 建议先在测试环境验证 gRPC 通道是否正常连通。

**Q: Gateway 路由冲突怎么排查？**

A: Gateway 路由匹配是"先到先得"模式。排查步骤：(1) 开启 Gateway 调试日志 `logging.level.reactor.netty=TRACE`；(2) 确认 `spring.cloud.gateway.discovery.locator.enabled=true` 时是否自动生成了与自定义路由冲突的规则；(3) 检查路由的 `order` 值（越小越优先），确保关键路由 order 设得更小；(4) Path 断言注意 `/api/**` 和 `/api/v1/**` 的包含关系，范围大的放后面。

**Q: 配置中心灰度发布如何实践？**

A: Nacos 支持 Beta IP 灰度，也可以借助命名空间实现更严格的环境隔离：(1) 创建 `dev-gray` 命名空间作为灰度环境；(2) 灰度实例注册时指定 `spring.cloud.nacos.discovery.namespace=dev-gray`；(3) 在 Gateway 中通过 Header（如 `X-Gray: true`）将灰度流量路由到灰度实例；(4) 灰度验证通过后将 `dev-gray` 的配置同步到正式 `dev` 命名空间，发布上线。

**Q: 链路追踪采样率如何调优？**

A: 采样本质是成本与可观测性的权衡。建议：(1) 正常流量 5%-10% 采样；(2) 错误请求（5xx/异常）100% 采样；(3) 核心业务接口提高采样率到 20%-30%；(4) 健康检查、静态资源类路径 0% 采样；(5) 监控存储成本：假设 1000 QPS，10% 采样率 = 每日约 864 万 Span（按每个请求 10 个 Span 计），评估 Tempo/SkyWalking 后端是否能承受。

**Q: 服务发现缓存与实时性如何权衡？**

A: 服务发现本质是一个"弱一致 + 最终一致"的系统。Nacos 临时实例 15 秒心跳超时后剔除，客户端拉取间隔默认可达数秒，加上 LoadBalancer 的 `CachingServiceInstanceListSupplier` 缓存（默认 35 秒），总延迟最多可能达到 50 秒以上。生产建议：(1) 缩短 `spring.cloud.loadbalancer.cache.ttl` 到 10-15 秒；(2) Nacos 客户端配置 `nacos.discovery.watch-delay` 减小监听间隔；(3) 必须配合重试机制，容忍短暂的实例列表滞后。

**Q: Spring Cloud Gateway 和 Nginx/Kong 怎么分工？**

A: 典型分层架构中，Nginx/Kong 作为"入口网关"（Edge Gateway），Spring Cloud Gateway 作为"微服务网关"（Internal Gateway）。Nginx 负责 SSL 终结、WAF、全局 IP 限流、静态资源；Spring Cloud Gateway 负责 JWT 鉴权、服务路由、业务限流、灰度发布。两者不是替代关系，而是互补分层。
