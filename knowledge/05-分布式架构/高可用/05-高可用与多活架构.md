# 高可用与多活架构

## 概述

高可用（High Availability, HA）是分布式系统的核心质量属性，其本质是在部分组件故障时系统仍能对外提供可接受的服务水平。可用性的技术体系从单机守护进程的冷备模式，演进到机架级/机房级/区域级的异地多活，覆盖故障检测、故障转移、数据同步、流量调度和灾备恢复的全生命周期。

在 AI 应用中，高可用尤为重要：模型推理服务的延迟敏感特性决定了秒级故障检测和自动恢复是刚需；RAG 知识库的多向量索引需要同步复制保障检索一致性；Agent 长任务的持久化执行状态需要跨可用区容灾。

本文从可用性指标出发，系统性地展开故障转移策略、多活架构设计、优雅关闭与滚动更新、灾备恢复等全套技术体系，并给出基于 JDK 25 + Spring Boot 4.x + Redis Sentinel/Redisson + Kafka ISR 的实战代码。

## 一、高可用基础

### 1.1 可用性指标

可用性是系统正常运行时间占总时间的比例，业界常用"几个9"来量化：

| 可用性等级 | 年宕机时间 | 月宕机时间 | 周宕机时间 | 典型场景 |
|-----------|-----------|-----------|-----------|---------|
| 99% (2个9) | 3.65 天 | 7.2 小时 | 1.68 小时 | 内部工具、开发环境 |
| 99.9% (3个9) | 8.76 小时 | 43.8 分钟 | 10.1 分钟 | 非关键业务系统 |
| 99.99% (4个9) | 52.56 分钟 | 4.38 分钟 | 1.01 分钟 | 核心业务系统 |
| 99.999% (5个9) | 5.26 分钟 | 26.3 秒 | 6.05 秒 | 电信级、金融核心 |
| 99.9999% (6个9) | 31.5 秒 | 2.6 秒 | 0.6 秒 | 极少达成 |

核心计算公式：

```
Availability = MTBF / (MTBF + MTTR)
```

- **MTBF** (Mean Time Between Failures)：平均无故障时间，表征系统稳定性
- **MTTR** (Mean Time To Repair)：平均修复时间，表征运维响应能力
- **MTTF** (Mean Time To Failure)：系统从启动到首次故障的平均时间（适用于不可修复系统）

**关键洞察：** 降低 MTTR 比提高 MTBF 更高效。将 MTTR 从 30 分钟降到 5 分钟，等同于将 MTBF 提升 6 倍。这也是自动化故障检测与恢复的工程价值所在——人工介入的 MTTR 通常以分钟计，而自动故障转移可将 MTTR 压缩到秒级。

### 1.2 故障检测机制

故障检测是故障转移的前提。必须有准确、低延迟的机制判断节点是否真的故障：

**心跳机制（Heartbeat）：**

```
┌─────────┐    TCP 连接保活/HTTP Health Check     ┌─────────┐
│  监控节点 │ ◄──────────────────────────────────► │  被监控节点│
└─────────┘     每 N 秒发送心跳，超时判定故障        └─────────┘
```

- **TCP 层心跳：** 依赖 TCP Keep-Alive 或自定义长度字节的心跳包，开销最低，但无法反映应用层状态
- **HTTP Health Check：** `/health`、`/actuator/health/liveness`、`/actuator/health/readiness`，能检测应用逻辑是否正常，是 K8s 和 Spring Boot 的标准方案
- **超时判死：** 连续 N 次心跳失败 → 判定节点故障。N 的取值需要平衡误判率和检测延迟
- **故障确认：** 单个监控节点的判定不可靠（可能是监控节点自身网络问题），通常需要多个监控节点达成共识

**TTL 租约（Lease）：**

节点定期续约一个带 TTL 的租约（如写入 Redis/etcd 一个带过期时间的 key）。节点故障后租约自动过期，其他节点可感知到。优势是避免了监控者单点问题，但依赖外部存储的可用性。

**Gossip 协议（成员关系传播）：**

```
Node A ──── 随机选择 ────► Node B ──── 随机选择 ────► Node C
  │                          │                          │
  └── 交换已知的成员状态 ─────┴── 交换已知的成员状态 ─────┘
```

每个节点周期性地与随机几个对等节点交换其已知的全体成员状态。信息以 O(log N) 轮次传播到整个集群。Cassandra、Redis Cluster、Consul 都使用 Gossip 或变体。优点是无中心化、扩展性好；缺点是收敛需要时间，存在短暂的不一致窗口。

**Phi Accrual Failure Detector（自适应阈值）：**

```
φ = -log₁₀(P(t | heartbeat_arrival_history))

φ = 1 → 约 10% 怀疑是故障
φ = 2 → 约 1% 怀疑是故障
φ = 8 → 约 10⁻⁸ 怀疑是故障
```

不设置固定的超时阈值，而是根据心跳到达的历史分布，动态计算节点故障的可疑程度（φ 值）。当 φ 超过阈值时触发故障怀疑。Akka 和 Cassandra 使用此机制。相比固定超时，在面对网络抖动和瞬时负载变化时更鲁棒。

### 1.3 故障转移基础

**自动 failover 流程：** 检测故障 → 选举新主 → 将流量切换到新主 → 通知相关组件

**手动 failover vs 自动 failover：**

| 维度 | 手动 failover | 自动 failover |
|------|-------------|-------------|
| MTTR | 分钟级到小时级 | 秒级到分钟级 |
| 误判风险 | 低（有人工判断） | 存在（网络分区误判） |
| 运维成本 | 高（需要 7x24 值班） | 低（自动化处理） |
| 复杂场景 | 灵活处理 | 需预定义规则 |

**脑裂（Split-Brain）问题：** 当网络分区导致集群分裂为两个或更多子集群，每个子集群都可能选出自己的 leader，导致数据写入冲突和数据丢失。解决方案：

1. **法定人数（Quorum）：** 要求 leader 获得超过半数节点的投票（Raft 的多数派原则）
2. **Fencing Token：** 每次 leader 变更递增一个单调递增的 token，存储系统拒绝小于当前 token 的写入请求
3. **外部锁：** 基于 ZooKeeper 临时节点的 leader 租约，只有持有租约的节点才能写入

## 二、故障转移策略

### 2.1 Active-Passive（主备模式）

| 模式 | 备节点状态 | 切换时间 | 资源利用率 | 适用场景 |
|------|-----------|---------|-----------|---------|
| 冷备（Cold Standby） | 未启动，故障时启动 | 分钟级 | 100%（仅备节点闲置） | 成本敏感的离线系统 |
| 温备（Warm Standby） | 已启动，未接管流量 | 秒级到分钟级 | 备节点部分闲置 | 对切换时间有一定要求的业务 |
| 热备（Hot Standby） | 已启动，实时同步，随时接管 | 秒级 | 备节点闲置但可做只读 | 核心数据库、关键服务 |

**VIP 漂移（Keepalived + VRRP）：**

```
         ┌──────────────┐
         │   VIP: 10.0.0.100 │
         └───────┬──────┘
                 │
     ┌───────────┴───────────┐
     │                       │
┌────┴─────┐          ┌──────┴────┐
│  Master   │  VRRP    │  Backup   │
│ (Priority │◄────────►│ (Priority │
│   100)    │  心跳     │   90)     │
└──────────┘          └───────────┘

Master 故障 → Backup 检测到 VRRP 心跳丢失
→ Backup 提升为 Master（优先级 100）
→ Backup 接管 VIP 10.0.0.100
→ 发送免费 ARP 通告新的 MAC 地址
→ 流量切换完成（通常 < 3 秒）
```

Keepalived 的核心是通过 VRRP（Virtual Router Redundancy Protocol）实现 IP 地址的虚拟化和漂移。但它只能做 IP 层面的切换，不感知应用状态——需要配合应用层健康检查脚本（如 `notify_master` 脚本中检测 MySQL 是否真的可写）。

### 2.2 Active-Active（双活模式）

两个节点同时处理流量，互为备份：

- **DNS 轮询 + 健康检查：** DNS 返回多个 A 记录，配合健康检查摘除故障节点。优点是最简单；缺点是 DNS 缓存导致切换延迟（TTL 内客户端仍会路由到故障节点）
- **全局负载均衡（GSLB）：** 在 DNS 层面做智能路由（基于地理位置、机房健康度、容量等），比简单轮询更灵活
- **数据冲突处理：** 双活的根本挑战是数据冲突——两个机房同时修改同一行数据。处理方案包括：
  - 按用户维度分片，保证同一用户的请求始终路由到同一机房（用户亲和性）
  - CRDT（Conflict-free Replicated Data Type）：数据结构本身保证合并无冲突
  - 最后写入胜出（LWW）：简单但有数据丢失风险
  - 业务规则合并：应用层自定义冲突解决逻辑

### 2.3 数据同步策略

数据复制的核心矛盾是：**一致性 vs 可用性 vs 延迟**。

| 同步模式 | 写入延迟 | 数据一致性 | 数据丢失风险 | 适用场景 |
|---------|---------|-----------|-------------|---------|
| 同步复制 | 高（等所有副本确认） | 强一致 | 零丢失 | 金融交易、支付系统 |
| 异步复制 | 低（主库立即返回） | 最终一致 | 可能丢失未同步数据 | 用户行为日志、社交动态 |
| 半同步复制 | 中（等至少一个副本确认） | 增强最终一致 | 少量丢失风险 | 通用业务数据库 |

**MySQL 半同步复制的 after_sync 模式：**

```
客户端 → 主库写入 binlog
          │
          ├── 等待至少 1 个从库确认收到 binlog（不等待执行完成）
          │
          └── 收到确认后，提交事务并返回客户端

优势：主库崩溃时，至少有一个从库拥有完整的 binlog
代价：如果半同步超时退化为异步，需要告警和人工介入
```

### 2.4 选举算法

**Raft 领导者选举：**

```
节点状态转换：
                      超时，开始选举
    ┌──────────┐ ────────────────────────► ┌──────────┐
    │ Follower │                           │ Candidate │
    └──────────┘ ◄──────────────────────── └──────────┘
          ▲         收到更高 term 的请求           │
          │                                       │
          │                               获得多数票 │
          │                                       ▼
          │                                ┌──────────┐
          └────────────────────────────────│  Leader   │
                 发现更高 term 的 Leader     └──────────┘
```

选举比较规则：先比较 term（任期号），term 大的胜出；term 相同比较 log index，日志更新的胜出。每个节点在一个 term 内只能投一票，防止脑裂。

**Bully 算法：** 节点 ID 最大的节点成为 leader。当节点发现 leader 故障时，"欺负"比自己 ID 小的节点。简单但在网络分区时容易双主。

**基于 ZooKeeper 的选举：**

```
/leader-election
    ├── _c_0000000001 (临时顺序节点, node-A)
    ├── _c_0000000002 (临时顺序节点, node-B)
    └── _c_0000000003 (临时顺序节点, node-C)

序号最小的节点（0000000001）成为 Leader
Leader 故障 → 临时节点自动删除 → 序号 0000000002 晋升
每个 Follower watch 前一个序号节点
```

ZooKeeper 的临时顺序节点 + watch 机制提供了工业级的 leader 选举方案。临时节点的特性保证了 leader 崩溃后自动释放锁；顺序节点的特性保证了先到先得且无惊群效应。

## 三、多活架构

### 3.1 多活架构层次

**同城双活：**

```
┌──────────────────── 同城（延迟 < 2ms）─────────────────┐
│                                                          │
│  ┌──────────────┐         数据同步         ┌──────────────┐ │
│  │  机房 A       │ ◄═══════════════════►   │  机房 B       │ │
│  │  (全量服务)    │     同步复制(强一致)      │  (全量服务)    │ │
│  └──────────────┘                          └──────────────┘ │
│                                                          │
│  数据库主从跨机房部署，同步复制保障零数据丢失                           │
│  任一机房故障，另一机房承载全部流量                                   │
└──────────────────────────────────────────────────────────┘
```

核心要求：
- 网络延迟极低（光纤直连，RTT < 2ms），否则同步复制的延迟代价不可接受
- 链路带宽充足，能承载数据同步和故障时全量流量
- 必须防脑裂——通常引入第三点（仲裁节点）或依赖多机房多数派

**两地三中心：**

```
    城市 A（同城双活）                         城市 B（异地灾备）
┌─────────────────────────┐        ┌─────────────────────┐
│  机房 A-1     机房 A-2    │ 异步复制│    机房 B-1           │
│  (主) ◄────► (从/备)   │═══════►│   (灾备)              │
│  同步复制              │ 延迟<2ms│                      │
└─────────────────────────┘        └─────────────────────┘

同城双活保障机房级容灾，异地灾备保障城市级容灾
异地之间的异步复制容忍分钟级延迟和数据丢失
```

这是国内金融行业的标准架构。异地灾备中心的资源可以用于灾备演练和非核心的读流量（如报表、数据分析）。

**单元化架构：**

```
用户 ID hash(user_id) % N  → 路由到固定的单元（Set）

┌──────────────┐    ┌──────────────┐    ┌──────────────┐
│   Set 0      │    │   Set 1      │    │   Set 2      │
│  user [0,N,2N]│   │ user [1,N+1] │   │ user [2,N+2] │
│              │    │              │    │              │
│  应用 + 数据库 │    │  应用 + 数据库 │    │  应用 + 数据库 │
│  缓存 + 消息   │    │  缓存 + 消息   │    │  缓存 + 消息   │
└──────────────┘    └──────────────┘    └──────────────┘

每个 Set 是自包含的完整业务单元
Set 之间无共享数据库，无跨 Set 事务
通过全局路由层将用户请求分发到所属 Set
```

单元化的优势：
- 故障爆炸半径可控——一个 Set 故障只影响该分片的用户
- 水平扩展简单——增加 Set 即可扩容
- 异地多活自然支持——不同的 Set 可以部署在不同的机房

代价是需要精心设计分片键，且跨 Set 的业务操作（如用户间转账）需额外的分布式事务支持。

### 3.2 全局路由

多活架构中，如何将用户请求路由到正确的机房/单元？

**GSLB（Global Server Load Balancing）+ 智能 DNS：**

```
用户 DNS 查询 your-api.example.com
        │
        ▼
    GSLB 设备/服务（根据以下策略决策）：
    ├── 用户 IP 的地理位置 → 最近机房
    ├── 各机房的实时健康度 → 剔除故障机房
    ├── 各机房的当前负载 → 负载均衡分发
    └── 用户所属单元 → 路由到对应机房
        │
        ▼
    返回目标机房的 VIP 或入口地址
```

**HTTP 302 重定向：** 用户首次访问任意机房的入口，该入口查询用户归属后返回 302 将浏览器重定向到正确机房。适用于 Web 应用，但不适用于 API 调用（增加一次额外往返）。

**Anycast IP：** 多个机房对外通告相同的 IP 地址，依赖 BGP 路由协议将用户流量自动导向最近的机房。Google 的 8.8.8.8 就是经典的 Anycast 部署。优点是网络层转发、无额外延迟；缺点是不感知应用层状态，切换依赖路由收敛。

### 3.3 数据分区与用户亲和性

```
路由策略的核心：
user_id → hash(user_id) % shard_count → Set ID → 机房映射

用户亲和性（Session Affinity / Sticky Session）：
同一用户的后续请求必须路由到同一机房/Set，避免跨机房读写的复杂性和延迟
```

**跨机房数据访问的兜底策略：**

1. **只读降级：** 用户的归属机房故障时，临时路由到其他机房，但只允许读取已有数据（禁止写入）
2. **异步写入暂存：** 本地暂存写入操作，等归属机房恢复后异步同步
3. **跨机房代理写：** 通过专线将写入请求代理转发到归属机房（延迟会显著增加）

### 3.4 数据同步延迟处理

多活架构无法回避的核心难题——数据同步总是有延迟的。

**最终一致性窗口：**

| 同步方式 | 典型延迟 | 数据差异 |
|---------|---------|---------|
| 同城同步复制 | < 1ms（网络）+ 磁盘写入 | 无差异 |
| 同城半同步 | < 1ms | 可能丢失未确认事务 |
| 跨城异步复制 | 10-100ms | 延迟窗口内数据不一致 |
| 跨洲异步复制 | 100ms - 数秒 | 较大的不一致窗口 |

**冲突解决策略：**

1. **Last Write Wins（LWW）：** 基于时间戳，最后写入的数据覆盖。最简单但可能丢失有效更新。适用于覆盖式操作（如更新用户头像）
2. **CRDT（Conflict-free Replicated Data Type）：** 数据结构本身保证合并无冲突。例如：
   - G-Counter（只增不减的计数器）：合并 = 取各副本的最大值
   - PN-Counter（可增可减的计数器）：通过正负两个 G-Counter 实现
   - OR-Set（Observed-Remove Set）：标记已删除元素，合并时考虑删除标记
3. **版本向量（Version Vector）：** 每个副本维护一个向量 `[counter_A, counter_B, counter_C]`，通过比较向量判断因果关系和冲突
4. **业务规则合并：** 应用层根据领域语义合并非冲突的更新，标记冲突交人工处理

**Read-Your-Writes 一致性：** 用户读取自己的写入时必须看到最新数据。实现方式：
- 写操作完成后返回一个版本号，后续读操作携带该版本号确保读到足够新的副本
- 用户写操作始终路由到主副本读取（牺牲一部分多活的负载分担效果）
- 异步复制场景下，写入后短暂时间内仍从主副本读取

### 4.2 K8s preStop Hook 与完整生命周期

```
Pod 终止的完整生命周期：

1. Pod 状态变为 Terminating（从 Service Endpoints 中移除）
2. preStop Hook 执行（如果配置了）
   └── 应用：标记 readiness 为 OUT_OF_SERVICE
   └── 等待 connection draining 完成（例如 sleep 10s）
3. SIGTERM 发送给容器主进程
   └── Spring Boot 收到 SIGTERM → 执行 graceful shutdown
   └── 拒绝新的 HTTP 请求
   └── 等待正在处理的请求完成（最多 timeout-per-shutdown-phase）
4. 等待 terminationGracePeriodSeconds（默认 30s）
5. 超时后，SIGKILL 强杀进程
```

```yaml
apiVersion: v1
kind: Pod
metadata:
  name: ai-service
spec:
  terminationGracePeriodSeconds: 60
  containers:
    - name: app
      image: ai-service:latest
      ports:
        - containerPort: 8080
      lifecycle:
        preStop:
          exec:
            command:
              - /bin/sh
              - -c
              - |
                # 1. 标记 readiness 为 OUT_OF_SERVICE
                curl -X POST http://localhost:8080/actuator/health/out-of-service
                # 2. 等待连接排干（通常 10-15 秒）
                sleep 15
      readinessProbe:
        httpGet:
          path: /actuator/health/readiness
          port: 8080
        initialDelaySeconds: 10
        periodSeconds: 5
        failureThreshold: 3
      livenessProbe:
        httpGet:
          path: /actuator/health/liveness
          port: 8080
        initialDelaySeconds: 30
        periodSeconds: 10
```

**连接排干（Connection Draining）的最佳实践：**

1. 先标记 readiness 为 OUT_OF_SERVICE → K8s 将该 Pod 从 Service Endpoints 中摘除
2. 存量连接自然完成或超时关闭（预留给 drain 窗口的时间）
3. 关闭端口 → 停止接受新连接
4. 停止应用 → 释放资源

完整的排干时间 = preStop sleep 时间 + graceful shutdown 执行时间，必须小于 `terminationGracePeriodSeconds`。

## 五、灾备与恢复

### 5.1 RPO 与 RTO

```
                    ┌────── 故障发生点 ──────┐
                    │                        │
    ────────────────┤   数据丢失窗口 (RPO)    ├──────── 时间轴
                    │◄─────────────────────►│
                    │                        │
                    │  ┌── 恢复窗口 (RTO) ──┤──── 服务恢复
                    │  │◄─────────────────►│
                    │  │                   │
                    ▼  ▼                   ▼
                  [故障] [开始恢复]    [恢复完成]
```

- **RPO (Recovery Point Objective)：** 可接受的数据丢失量。RPO=0 意味着零数据丢失（同步复制）；RPO=60s 意味着可接受丢失最近 60 秒的数据（异步复制）
- **RTO (Recovery Time Objective)：** 从故障发生到服务恢复的最大可接受时长。RTO=5min 意味着必须在 5 分钟内恢复服务

**RPO/RTO 的工程权衡：** 更低的 RPO 和 RTO 意味着更高的成本（同步复制、热备、专用链路）。并非所有系统都需要 RPO=0 和 RTO<1min——应根据业务分级制定。

### 5.2 备份策略

| 备份类型 | 原理 | 优点 | 缺点 |
|---------|------|------|------|
| 全量备份 | 完整数据集快照 | 恢复最简单 | 耗时长，存储大 |
| 增量备份 | 自上次备份以来的变更 | 速度快、存储小 | 恢复需要叠加多次备份 |
| 日志备份 | 连续归档 WAL/binlog | 支持任意时间点恢复（PITR） | 日志存储和管理复杂 |
| 冷备份 | 停机状态下备份 | 数据一致性最好 | 需要停机窗口 |
| 热备份 | 在线备份 | 不中断服务 | 可能影响性能 |

**MySQL 备份工具链：**
- `xtrabackup`（Percona）：物理热备份，不锁表，适合大数据库
- `mysqldump`：逻辑备份，简单但慢
- `mysqlbinlog`：binlog 连续归档，支持 PITR

**PostgreSQL 备份工具链：**
- `pg_dump` / `pg_dumpall`：逻辑备份
- `pg_basebackup`：物理在线备份
- WAL 连续归档：`archive_command` + `pg_receivewal`，支持 PITR

### 5.3 恢复演练与数据校验

**定期恢复演练是验证灾备有效性的唯一手段。** 必须定期（每季度/每半年）执行以下验证：

1. **从备份恢复数据库到指定时间点** → 验证 RPO 是否达标
2. **在灾备机房启动完整应用栈** → 验证 RTO 是否达标
3. **执行数据一致性校验** → 验证数据无静默损坏

**混沌工程故障注入：**

在受控环境下注入以下故障类型，验证系统的容灾能力：
- 数据库主节点宕机 → 验证自动 failover 和 RTO
- 网络分区（延迟注入/丢包） → 验证选举和一致性保障
- 机房级故障（模拟） → 验证多活切换和流量调度

**恢复手册（Playbook）的重要性：** 故障处置不能依赖记忆——必须在事先编写覆盖关键故障场景的逐步操作手册，包含以下要素：故障现象识别、人员通知流程、故障诊断步骤、恢复操作步骤（含精确命令）、验证恢复成功的检查步骤、回滚方案。

**数据一致性校验：**
- MySQL：`pt-table-checksum`（Percona Toolkit）—— 对主从数据进行 CRC 校验，发现不一致的行
- PostgreSQL：`pg_checksums` + 自定义校验脚本
- WAL/Binlog 完整性验证：确保日志序列无间断、无损坏

**GTID 模式下的主从切换优势：**

```sql
-- 传统 binlog + position 方式
CHANGE MASTER TO
  MASTER_LOG_FILE='mysql-bin.000123',
  MASTER_LOG_POS=456789;

-- GTID 方式（简化切换、自动定位）
-- 从库自动从正确的 binlog 位置开始同步
```

### 6.2 Redis Sentinel 故障转移

```
哨兵集群（至少 3 个节点，避免偶数节点投票平手）：

    ┌──────────┐    ┌──────────┐    ┌──────────┐
    │ Sentinel │    │ Sentinel │    │ Sentinel │
    │    1     │    │    2     │    │    3     │
    └────┬─────┘    └────┬─────┘    └────┬─────┘
         │               │               │
         └───────────────┼───────────────┘
                         │ 监控
         ┌───────────────┼───────────────┐
         │               │               │
    ┌────┴─────┐    ┌────┴─────┐    ┌────┴─────┐
    │  Master  │    │  Slave 1 │    │  Slave 2 │
    │  Redis   │◄───│  Redis   │    │  Redis   │
    └──────────┘ 复制└──────────┘    └──────────┘
```

**Sentinel 故障转移完整流程：**

1. **主观下线（SDOWN - Subjective Down）：** 单个 Sentinel 检测到 Master 在 `down-after-milliseconds` 时间内无响应，标记该 Master 为 SDOWN

2. **客观下线（ODOWN - Objective Down）：** 该 Sentinel 向其他 Sentinel 查询，当超过 `quorum` 个 Sentinel 都认为 Master 不可达时，将标记升级为 ODOWN

3. **选举 Sentinel Leader：** 需要进行故障转移的 Sentinel 之间通过 Raft-like 投票选举出一个 Leader（Leader 负责执行故障转移）

4. **选择新 Master：** Leader Sentinel 从所有 Slave 中选择一个新 Master（规则：排除已经标记 SDOWN 的、排除与旧 Master 断开时间过长的、优先级最高的、复制偏移量最大的、run_id 字典序最小的）

5. **执行故障转移：** Sentinel Leader 向选中的 Slave 发送 `SLAVEOF NO ONE` → 配置其他 Slave 复制新 Master → 更新 Sentinel 内部状态

6. **通知客户端：** Sentinel 通过 Pub/Sub（`+switch-master` 频道）或客户端重连机制通知新 Master 地址

```conf
# sentinel.conf
sentinel monitor mymaster 192.168.1.10 6379 2
sentinel down-after-milliseconds mymaster 5000
sentinel failover-timeout mymaster 30000
sentinel parallel-syncs mymaster 1
```

### 6.3 Kafka ISR 故障处理

```
Topic: ai-events, Partition: 0

    ┌──────────────────────────────────────────────────────┐
    │  ISR (In-Sync Replicas) = [Broker-1, Broker-2, Broker-3] │
    │                                                      │
    │  Leader: Broker-1                                    │
    │      消息写入 ─► Broker-1 日志                        │
    │                    │                                 │
    │               Follower 拉取                          │
    │        ┌──────────┼──────────┐                       │
    │        ▼          ▼          ▼                       │
    │    Broker-2    Broker-3    Broker-4                  │
    │    (ISR)       (ISR)      (不在 ISR，落后太多)        │
    └──────────────────────────────────────────────────────┘
```

**ISR 机制核心参数：**

```
min.insync.replicas = 2
→ 写入消息时，Leader 必须等待至少 2 个 ISR 副本确认
→ 如果 ISR 少于 2 个，写入被拒绝（NotEnoughReplicasException）
→ 配合 acks=all 使用，保障数据可靠性

unclean.leader.election.enable = false
→ false：ISR 外无活着的副本 → 分区不可用（宁可不可用也不丢数据）
→ true：允许从 ISR 外的副本选 Leader（可用性优先，但可能丢数据）
```

**Controller 故障转移：**

Kafka 集群中有一个 Controller（控制器）负责分区 Leader 选举和管理。

```
Controller 故障检测与转移：

1. Controller 与 ZooKeeper/KRaft 的 Session 超时
2. 其他 Broker 检测到 Controller 的临时节点消失
3. 所有 Broker 尝试在 ZooKeeper 中创建 /controller 临时节点
4. 先创建成功的 Broker 成为新 Controller
5. 新 Controller 读取所有分区的 ISR 信息
6. 对失去 Leader 的分区，从 ISR 中选举新 Leader
7. 将新的 Leader/ISR 信息通过 LeaderAndIsr 请求分发给所有 Broker
```

```java
        ready.set(false);

    }
}
```

```java
                // Sentinel 模式下启用主从切换监听

                // 密码（如有）
                .setPassword("your-redis-password");

        var redisson = (Redisson) Redisson.create(config);

        // 注册主从切换监听器
        redisson.getConnectionManager().getConnectionEventsHub()
                .addListener(new ConnectionListener() {
                    @Override
                    public void onConnect(InetSocketAddress addr) {
                        System.out.println("Connected to Redis: " + addr);
                    }

                    @Override
                    public void onDisconnect(InetSocketAddress addr) {
                        System.out.println("Disconnected from Redis: " + addr);
                    }
                });

        return redisson;
    }

    /**
     * 使用示例：带重试的 Redis 操作（应对主从切换瞬间的异常）
     */
    @Bean
    public CacheService cacheService(RedissonClient redisson) {
        return new CacheService(redisson);
    }
}

// 缓存服务：封装 Sentinel 切换时的重试逻辑
class CacheService {

    private final RedissonClient redisson;

    public CacheService(RedissonClient redisson) {
        this.redisson = redisson;
    }

    public String getWithRetry(String key) {
        int attempts = 3;
        for (int i = 0; i < attempts; i++) {
            try {
                var bucket = redisson.<String>getBucket(key);
                return bucket.get();
            } catch (Exception e) {
                if (i == attempts - 1) throw e;
                try {
                    // 主从切换期间的短暂不可用，短暂休眠后重试
                    Thread.sleep(200L * (i + 1));
                } catch (InterruptedException ie) {
                    Thread.currentThread().interrupt();
                    throw new RuntimeException(ie);
                }
            }
        }
        return null;
    }

    /**
     * 分布式锁 —— 依赖 Sentinel 高可用的锁
     */
    public void executeWithLock(String lockKey, Runnable task) {
        RLock lock = redisson.getLock(lockKey);
        try {
            // waitTime: 等锁时间, leaseTime: 锁自动释放时间
            if (lock.tryLock(3, 10, java.util.concurrent.TimeUnit.SECONDS)) {
                task.run();
            }
        } catch (InterruptedException e) {
            Thread.currentThread().interrupt();
        } finally {
            if (lock.isHeldByCurrentThread()) {
                lock.unlock();
            }
        }
    }
}
```

### 7.3 基于 Spring Cloud LoadBalancer 的服务健康检查 + 自动摘除

```java
package com.example.ha.config;

import org.springframework.cloud.client.DefaultServiceInstance;
import org.springframework.cloud.client.ServiceInstance;
import org.springframework.cloud.loadbalancer.core.ServiceInstanceListSupplier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import reactor.core.publisher.Flux;

import java.net.URI;
import java.net.http.HttpClient;
import java.net.http.HttpRequest;
import java.net.http.HttpResponse;
import java.time.Duration;
import java.util.List;
import java.util.Map;
import java.util.concurrent.ConcurrentHashMap;

@Configuration
public class LoadBalancerHealthCheckConfig {

    private final HttpClient httpClient = HttpClient.newBuilder()
            .connectTimeout(Duration.ofSeconds(2))
            .build();

    private final Map<String, Long> unhealthyInstances = new ConcurrentHashMap<>();
    private static final long UNHEALTHY_TTL_MS = 30_000; // 30 秒后重试

    @Bean
    public ServiceInstanceListSupplier healthCheckSupplier(
            ServiceInstanceListSupplier discoverySupplier) {

        return new ServiceInstanceListSupplier() {

            @Override
            public String getServiceId() {
                return discoverySupplier.getServiceId();
            }

            @Override
            public Flux<List<ServiceInstance>> get() {
                return discoverySupplier.get().map(instances -> {
                    // 过滤不健康的实例（带冷却期）
                    return instances.stream()
                            .filter(this::isHealthy)
                            .toList();
                });
            }
        };
    }

    private boolean isHealthy(ServiceInstance instance) {
        String key = instance.getInstanceId();
        Long unhealthySince = unhealthyInstances.get(key);

        // 如果在冷却期内，跳过健康检查，直接排除
        if (unhealthySince != null
                && System.currentTimeMillis() - unhealthySince < UNHEALTHY_TTL_MS) {
            return false;
        }

        // 执行健康检查
        try {
            var request = HttpRequest.newBuilder()
                    .uri(URI.create(instance.getUri() + "/actuator/health"))
                    .timeout(Duration.ofSeconds(2))
                    .GET()
                    .build();

            var response = httpClient.send(request, HttpResponse.BodyHandlers.ofString());

            if (response.statusCode() == 200
                    && response.body().contains("\"status\":\"UP\"")) {
                unhealthyInstances.remove(key); // 恢复健康
                return true;
            }
        } catch (Exception e) {
            // 健康检查失败
        }

        // 标记为不健康
        unhealthyInstances.put(key, System.currentTimeMillis());
        System.out.println("Marked unhealthy: " + instance.getHost() + ":" + instance.getPort());
        return false;
    }
}
```

## 八、常见问题

**Q1: 脑裂（Split-Brain）如何防范？**

脑裂的根本原因是网络分区导致集群分裂为多个子集，各自选出 leader 并写入数据。防范策略：

- **法定人数（Quorum）：** leader 选举和写入操作都要求获得超过半数节点的同意（如 Raft 的多数派原则），这样最多只有一个分区能满足多数派条件
- **Fencing Token：** 每个写入请求携带递增的 fencing token，底层存储拒绝 token 小于已处理最大值的请求。即使旧 leader 以为自己还是 leader，其写入也会被拒绝
- **外部仲裁者：** 引入独立于集群的第三方组件（如 ZooKeeper、etcd）作为 tie-breaker。但这引入了新的依赖
- **STONITH（Shoot The Other Node In The Head）：** 物理层面确保故障节点真的停止运行（如 IPMI 断电、云厂商 API 强制关机），这是最彻底的方案

**Q2: 主从延迟如何监控和降级？**

监控手段：
- MySQL：`SHOW SLAVE STATUS` 中的 `Seconds_Behind_Master`（注意这个值在某些场景下不准确），更准确的是使用 `pt-heartbeat`
- Redis：`INFO replication` 中的 `master_repl_offset - slave_repl_offset`
- 应用层：在写入时记录一个时间戳/版本号，在从库读取时校验是否已同步

降级策略：
- 关键业务（如支付确认）读写分离配置为强制读主库
- 非关键查询（如列表页、历史记录）允许读从库，但缓存"同步中"状态避免显示缺失数据
- 将从库延迟作为健康指标——延迟过大的从库从负载均衡中摘除

**Q3: 多活架构中数据冲突如何解决？**

数据冲突是多活架构中最难解决的本质问题。分层策略：

1. **设计层避免：** 按用户 ID 分片，保证同一用户请求始终路由到同一机房（用户亲和性 + 全局路由），从根本上避免跨机房写冲突
2. **协议层解决：** 使用 CRDT（如 Riak、Redis CRDT 数据结构），数据结构本身保证合并后无冲突
3. **应用层合并：** 版本向量检测因果冲突，写冲突时执行业务规则合并（如购物车 = 多机房的并集）
4. **最后写入胜出：** 最简单的方案，容忍一定程度的数据丢失（适用于用户行为日志、非关键配置）
5. **人工裁定：** 对无法自动合并且数据重要的场景，标记冲突交人工处理

**Q4: 如何验证灾备的有效性？**

灾备不仅仅是搭建，更需要持续验证：

- **定期恢复演练（每季度）：** 从备份介质完整恢复数据库，在灾备机房启动完整应用栈，执行冒烟测试和数据一致性校验
- **混沌工程注入：** 使用 Chaos Mesh/LitmusChaos 注入数据库故障、网络分区、机房级故障，验证自动 failover 机制
- **灰度验证灾备流量：** 将一小部分生产流量路由到灾备机房，验证服务能正常处理（注意数据隔离）
- **RPO/RTO 实测：** 记录故障注入到自动恢复的时间间隔，与应用约定的 RTO 对比；对比主备数据差异量，与约定的 RPO 对比
- **Playbook 验证：** 按恢复手册逐步演练，发现缺失步骤或过时命令，及时更新

**Q5: K8s 滚动更新如何做到流量无损？**

实现零流量损失的滚动更新，需要逐层保障：

- **就绪探针（Readiness Probe）：** 确保新 Pod 完全就绪后才加入 Service Endpoints。探针检查应覆盖数据库连接、缓存连接、消息队列连接等核心依赖
- **preStop Hook + 连接排干：** preStop 中先标记 readiness 为 OUT_OF_SERVICE → 等待排干窗口 → 接受 SIGTERM → 处理中请求完成 → 退出
- **`maxUnavailable: 0`：** 滚动更新期间不允许有不可用 Pod。需要配合 `maxSurge` 先创建新 Pod，确认就绪后再缩旧 Pod
- **Service Mesh（Istio/Linkerd）：** 在 sidecar 层面实现更精细的连接排干和流量迁移，不依赖 Pod 的就绪探针
- **重试与幂等：** 客户端必须具备重试能力（`RetryTemplate` / Resilience4j Retry），且所有写操作必须是幂等的——因为旧 Pod 关闭瞬间可能有请求已发送但未处理完
- **优雅关闭超时配足：** `terminationGracePeriodSeconds` 必须大于 preStop sleep + 应用 graceful shutdown timeout，否则 Pod 会被 SIGKILL 强杀导致流量中断
