# 数据库原理

## 概述

数据库是后端系统的核心——绝大多数业务系统的状态最终都持久化在数据库中。深入理解数据库原理（而非仅仅会写 SQL）是区分"会用"和"懂原理"的工程师的关键分界线。本文覆盖关系模型、索引原理、事务 ACID、MVCC 机制、查询优化、范式理论和锁机制，在关键知识点上对比 PostgreSQL 和 MySQL InnoDB 的不同实现选择，帮助理解两个主流数据库的设计哲学差异。

---

## 核心内容

### 一、关系模型

关系模型由 Edgar Codd 在 1970 年提出，核心概念：

- **关系（Relation）：** 一张二维表，由行（Tuple/元组）和列（Attribute/属性）组成
- **域（Domain）：** 每列的取值范围（数据类型 + 约束）
- **键（Key）：** 超键（唯一标识）、候选键、主键、外键
- **关系代数：** 选择（σ）、投影（π）、笛卡尔积（×）、连接（⨝）、并（∪）、差（−）

**关系代数的基础运算与 SQL 的对应：**

| 关系代数 | SQL 关键字 |
|---|---|
| σ(选择) | WHERE |
| π(投影) | SELECT 列列表 |
| ⨝(连接) | JOIN ... ON |
| ∪(并) | UNION |
| −(差) | EXCEPT / NOT IN |

理解关系代数对于读懂查询计划和优化 SQL 至关重要——本质上，SQL 优化器是在对关系代数表达式做等价变换，找到代价最小的执行计划。

### 二、索引原理

#### 2.1 B+Tree 索引

B+Tree 是数据库索引的主力。与红黑树不同，B+Tree 每个节点可以容纳大量 key（数百到数千），整棵树的高度通常为 2-4 层。

**B+Tree 的结构特点：**
- **非叶子节点（内节点）：** 存储 key 和指向下一层节点的指针，用于导航
- **叶子节点：** 存储 key 和对应的数据（或数据指针），叶子节点间通过双向链表连接
- **扇出（Fanout）：** 每个内节点可容纳的 key 数量。扇出越大，树高度越低

**PostgreSQL B-Tree（PG 内部称 B-Tree，行为类似 B+Tree）：** 索引叶子节点存储 key + TID（Tuple ID，指向堆中行的物理位置）。这意味着通过索引查询需要两次 I/O——先读索引页找到 TID，再读数据页拿到完整行。但这也使得同一行可以有多个索引指向它。

**MySQL InnoDB 聚簇索引：** 主键索引的叶子节点直接存储整行数据（聚簇/Clustered）。这意味着通过主键查询只需一次 I/O 到达叶子节点。但辅助索引（Secondary Index）的叶子节点存储的是主键值而非 TID，查询需要回表（回到聚簇索引查完整行）。

**两者的设计权衡：**
- PostgreSQL 方案：更新主键代价低（只改 TID 引用），但索引查询多一次 I/O
- InnoDB 方案：主键查询更快，但更新主键代价高（需要移动整行），辅助索引更紧凑

#### 2.2 其他索引类型

| 索引类型 | 适用场景 | PostgreSQL | MySQL InnoDB |
|---|---|---|---|
| Hash 索引 | 等值查询 | 支持（`USING hash`） | 有限支持（自适应哈希索引 AHI） |
| GiST | 几何数据、全文检索 | 支持 | 不支持 |
| GIN | 数组、JSONB、全文检索 | 支持 | 不支持（用 FULLTEXT） |
| BRIN | 与物理顺序相关的大表 | 支持 | 不支持 |
| FULLTEXT | 全文检索 | 支持 | 支持 |

#### 2.3 索引优化关键概念

- **覆盖索引（Covering Index）：** 查询所需的所有列都在索引中，不需要回表。PostgreSQL 通过 `INCLUDE` 子句支持；InnoDB 的辅助索引天然可以覆盖（因为存了主键值）。
- **索引选择性（Selectivity）：** 索引列的不同值数量/总行数。选择性越高，索引越有效。`gender` 的选择性约为 0.5（低），不适合建索引；`user_id` 选择性接近 1（高），适合建索引。
- **联合索引与最左前缀法则：** `INDEX(a, b, c)` 支持 `WHERE a=?`、`WHERE a=? AND b=?`、`WHERE a=? AND b=? AND c=?`，但不支持只查 `b` 或只查 `c`。

**索引字段顺序原则：**
1. 等值条件列放前，范围条件列放后
2. 选择性高的列放前（但需要结合查询模式综合考量）
3. 频繁作为查询条件的列放前

### 三、事务与 ACID

#### 3.1 ACID 详解

| 属性 | 含义 | 实现机制 |
|---|---|---|
| **原子性 (Atomicity)** | 事务全部执行或全部不执行 | Undo Log（回滚日志） |
| **一致性 (Consistency)** | 事务前后数据库保持一致状态 | 约束（PK/FK/Check）+ 应用逻辑 |
| **隔离性 (Isolation)** | 并发事务互不干扰 | MVCC + 锁 |
| **持久性 (Durability)** | 提交后数据不丢失 | Redo Log / WAL（Write-Ahead Log） |

**注意：** C（一致性）是 ACID 中最模糊的概念。在数据库原理中，C 更多是 A + I + D 的结果——如果原子性、隔离性和持久性都满足，一致性在大多数情况下自然也满足。约束（Check/Foreign Key）和触发器是数据库层面保证一致性的额外手段。

#### 3.2 隔离级别

SQL 标准定义了四种隔离级别，按隔离强度递增：

| 隔离级别 | 脏读 | 不可重复读 | 幻读 |
|---|---|---|---|
| Read Uncommitted | 可能 | 可能 | 可能 |
| Read Committed | 不可能 | 可能 | 可能 |
| Repeatable Read | 不可能 | 不可能 | 可能 |
| Serializable | 不可能 | 不可能 | 不可能 |

- **脏读（Dirty Read）：** 读到未提交事务的修改
- **不可重复读（Non-Repeatable Read）：** 同一事务内两次读取同一行，结果不同（被其他事务UPDATE）
- **幻读（Phantom Read）：** 同一事务内两次查询同一范围，结果集行数不同（被其他事务INSERT/DELETE）

**MySQL InnoDB 默认级别：** Repeatable Read
**PostgreSQL 默认级别：** Read Committed

**关键差异：** InnoDB 的 Repeatable Read 通过 Next-Key Lock 解决了部分幻读问题（范围查询时锁住间隙），使其接近 Serializable 的行为。PostgreSQL 选择 Read Committed 作为默认，鼓励开发者显式选择更高的隔离级别。

#### 3.3 快照隔离（Snapshot Isolation）

快照隔离是一个比 SQL 标准隔离级别更实用的概念。在快照隔离下，每个事务看到的是数据库的一个一致性快照（版本），在事务开始时刻确定。它是 MVCC 的自然体现。

PostgreSQL 的 Repeatable Read 和 InnoDB 的 Repeatable Read 都基于快照隔离，但在实现细节上有差异。

### 四、MVCC — PostgreSQL vs MySQL InnoDB 实现对比

MVCC（Multi-Version Concurrency Control）是多版本并发控制的简称。核心思想：写操作不阻塞读操作，读操作不阻塞写操作——通过保存数据的多个版本来实现。

#### 4.1 PostgreSQL MVCC

PostgreSQL 在堆表的每一行存储 4 个系统列（对用户不可见）：

- `xmin`：插入此行的事务 ID
- `xmax`：删除此行的事务 ID（0 表示未删除）
- `cmin`/`cmax`：同一事务内的命令序号

**可见性判断（简化）：** 对于事务 T，行 R 是可见的当且仅当：
- `R.xmin` 在 T 的快照中（已提交且在 T 开始前提交，或由 T 自己创建）
- `R.xmax` 无效（为 0 或对应的删除事务对 T 不可见）

**版本链：** PostgreSQL 不做 undo log，旧版本就留在堆表中。这意味着 UPDATE 实际上是一次 DELETE（设旧行的 xmax）+ 一次 INSERT 新行。随着时间推移，旧版本累积导致表膨胀（Table Bloat），需要 VACUUM 清理。

**VACUUM 机制：**
- 标记不再需要的旧版本为可重用空间
- 防止事务 ID 回卷（Transaction ID Wraparound，32 位 XID 耗尽）
- 更新可见性地图（Visibility Map）和空闲空间地图（Free Space Map）
- 自动 VACUUM（autovacuum）默认启用

#### 4.2 MySQL InnoDB MVCC

InnoDB 的 MVCC 基于 Undo Log 实现。每行有三个隐藏字段：

- `DB_TRX_ID`：最后修改此行的事务 ID（6 字节）
- `DB_ROLL_PTR`：指向 undo log 中上一版本的指针（7 字节）
- `DB_ROW_ID`：如果没有主键，用作隐式行 ID

**版本链：** InnoDB 的 Undo Log 形成一个版本链。新版本在聚簇索引的数据页中，旧版本通过 `DB_ROLL_PTR` 串联在 undo log 中。读操作沿着版本链找到对当前事务可见的版本。

**ReadView（一致性视图）：** InnoDB 在事务开始或第一次查询时创建 ReadView，包含：
- 当前活跃的事务 ID 列表（`m_ids`）
- 最小活跃事务 ID（`min_trx_id`）
- 下一个待分配的事务 ID（`max_trx_id`）

可见性规则：对于行版本 `trx_id`：
- `trx_id == 当前事务ID` → 可见（自己的修改）
- `trx_id < min_trx_id` → 可见（创建此版本的事务已提交）
- `trx_id >= max_trx_id` → 不可见（此版本由"未来"事务创建）
- `min_trx_id <= trx_id < max_trx_id` → 检查是否在活跃列表中

#### 4.3 对比总结

| 维度 | PostgreSQL | MySQL InnoDB |
|---|---|---|
| 旧版本存储 | 堆表中（导致表膨胀） | Undo Log 中（独立空间） |
| 版本清理 | VACUUM（需管理） | Purge 线程（后台自动） |
| UPDATE 开销 | 整行替换（Delete+Insert） | 就地更新 + Undo Log |
| 事务 ID 回卷风险 | 有（32 位 XID） | 低（有 Undo Log 保护） |
| 获取快照时机 | 事务第一条语句 | Read Committed：每条语句；Repeatable Read：事务第一条查询 |

### 五、查询优化

#### 5.1 逻辑优化 vs 物理优化

**逻辑优化（基于规则的优化/RBO）：**
- 谓词下推（Predicate Pushdown）：`WHERE` 条件下推到扫描层
- 列裁剪（Column Pruning）：只扫描查询所需列
- 子查询展开（Subquery Unnesting）：子查询转为 JOIN
- 常量折叠（Constant Folding）：编译时计算常量表达式

**物理优化（基于代价的优化/CBO）：**
- 统计信息收集（表的行数、列的不同值数量/直方图）
- 估算各种执行计划的代价（I/O 次数 + CPU 时间）
- 选择代价最小的计划

#### 5.2 JOIN 算法

| 算法 | 原理 | 适用场景 | 时间复杂度 |
|---|---|---|---|
| Nested Loop Join | 外层表每行扫描内层表 | 小表 JOIN 大表（内层有索引） | O(N*M) |
| Hash Join | 为小表建 Hash Table，大表探测 | 两个大表等值 JOIN | O(N+M) |
| Merge Join | 两表排序后按序归并 | 两表已有序 | O(N+M) |
| Index Nested Loop | Nested Loop 但内层走索引 | 外层小，内层有索引 | O(N*log M) |

PostgreSQL 和 MySQL 8.0+ 都支持上述所有 JOIN 算法。MySQL 5.7 不支持 Hash Join（这是升级 8.0 的重要理由之一）。

### 六、范式与反范式

#### 6.1 范式层级

| 范式 | 核心约束 |
|---|---|
| 1NF | 列不可再分（原子性） |
| 2NF | 满足 1NF，且每个非主键列完全依赖于主键（消除部分依赖） |
| 3NF | 满足 2NF，且每个非主键列直接依赖于主键（消除传递依赖） |
| BCNF | 满足 3NF，且每个决定性因素都是候选键 |

**3NF 的判断口诀：** "每个非主键列必须直接依赖于主键，不能依赖于另一个非主键列。"

**反例：**
```
学生表（学号, 姓名, 系编号, 系名称, 系地址）
  主键：学号
  传递依赖：学号 → 系编号 → 系名称/系地址
  违反 3NF → 分解为学生表 + 系表
```

#### 6.2 反范式的实际考量

完全遵守 3NF 的系统在查询时需要大量 JOIN，性能下降。实践中需要在范式化和反范式化之间做权衡：

- **读多写少的表** 可以适度反范式化（冗余部分字段减少 JOIN）
- **写多读少的表** 保持范式化（减少更新异常）
- **数据仓库** 通常使用星型模型（事实表 + 维度表），维度表可以反范式化

### 七、锁机制

#### 7.1 InnoDB 锁类型

| 锁类型 | 锁定范围 | 用途 |
|---|---|---|
| Record Lock | 单行索引记录 | 行级锁 |
| Gap Lock | 索引记录之间的间隙 | 防止在间隙中插入（幻读） |
| Next-Key Lock | Record Lock + Gap Lock | Repeatable Read 下默认的加锁方式 |
| Insert Intention Lock | 特殊间隙锁 | INSERT 时设置，表示要在间隙中插入 |
| 意向锁（IS/IX） | 表级 | 表锁和行锁的协调 |

**Next-Key Lock 示例：** 如果索引有值 10、20、30，Next-Key Lock 的锁区间为：
```
(-∞, 10], (10, 20], (20, 30], (30, +∞)
```
`SELECT ... WHERE id = 20 FOR UPDATE` 会锁住 `(10, 20]`（Next-Key Lock on 20）。

#### 7.2 死锁检测

InnoDB 使用等待图（Wait-for Graph）检测死锁。当检测到环时，选择代价最小的事务（undo log 最少）进行回滚。

**常见死锁模式：**
- 两个事务以不同顺序更新相同的行
- 一个事务持有 S 锁想升级为 X 锁，另一个事务持有 S 锁
- Gap Lock 导致的插入死锁

**Java 应用程序中的死锁预防：**
1. 始终以相同顺序访问资源
2. 缩短事务时间（只在事务中做必要的事）
3. 对于高并发场景，使用乐观锁（版本号）替代悲观锁
4. 设置 `innodb_lock_wait_timeout`（默认 50 秒太长）

## 代码示例 — Java JDBC 事务与隔离级别

```java
void transactionWithIsolation() {
    var dataSource = new HikariDataSource();
    dataSource.setJdbcUrl("jdbc:postgresql://localhost:5432/mydb");
    dataSource.setUsername("user");
    dataSource.setPassword("pass");

    try (var conn = dataSource.getConnection()) {
        conn.setAutoCommit(false);
        // 设置为 Repeatable Read
        conn.setTransactionIsolation(
            Connection.TRANSACTION_REPEATABLE_READ);

        try (var stmt = conn.prepareStatement(
                "UPDATE accounts SET balance = balance - ? WHERE id = ?")) {
            stmt.setBigDecimal(1, new BigDecimal("100.00"));
            stmt.setLong(2, 1L);
            stmt.executeUpdate();
        }

        try (var stmt = conn.prepareStatement(
                "UPDATE accounts SET balance = balance + ? WHERE id = ?")) {
            stmt.setBigDecimal(1, new BigDecimal("100.00"));
            stmt.setLong(2, 2L);
            stmt.executeUpdate();
        }

        conn.commit();
    } catch (SQLException e) {
        // conn.rollback() 由 auto-commit=false 的关闭自动触发
        throw new RuntimeException("Transfer failed", e);
    }
}
```

**使用 Spring `@Transactional` 管理隔离级别：**

```java
@Transactional(isolation = Isolation.REPEATABLE_READ,
               propagation = Propagation.REQUIRED,
               timeout = 30)
public void transfer(Long fromId, Long toId, BigDecimal amount) {
    accountRepo.debit(fromId, amount);
    accountRepo.credit(toId, amount);
}
```

## 常见问题 / 面试题

**Q1: 为什么 InnoDB 推荐用自增主键？而 PostgreSQL 不这么强调？**
InnoDB 数据按主键顺序存储（聚簇索引）。自增主键保证了插入按顺序追加，不需要页分裂和随机 I/O 的页内移动。如果使用随机 UUID 主键，每次插入可能发生在 B+Tree 的任意位置，导致大量页分裂和碎片。PostgreSQL 使用堆表（非聚簇），主键和数据物理存储分离，所以主键的选择不影响写入性能。

**Q2: PostgreSQL 的 autovacuum 触发条件是什么？**
默认：`autovacuum_vacuum_scale_factor = 0.2`（表 20% 的行被标记为 dead）或 `autovacuum_vacuum_threshold = 50`（至少 50 行）。对大表（10 亿行），20% = 2 亿条 dead tuple 才触发 VACUUM，这太晚了。建议对大表单独设置更积极的 scale factor（如 0.01）。

**Q3: 什么情况下索引不会被使用？**
- 对索引列使用函数或表达式：`WHERE UPPER(name) = 'JOHN'`（函数索引可解决）
- LIKE 以通配符开头：`WHERE name LIKE '%john'`
- 索引列参与了计算：`WHERE age + 10 > 30`
- 查询优化器认为全表扫描更快（小表、低选择性列）

**Q4: Phantom Read 在 MySQL InnoDB Repeatable Read 下真的不会发生吗？**
Next-Key Lock 在锁定读（`SELECT ... FOR UPDATE`）时阻止了其他事务在锁定范围内插入新行，因此在锁定读下确实解决了幻读。但对于一致性读（普通的 `SELECT`），快照隔离保证了只看到事务开始时的版本，也不会有幻读。不过，如果事务 A 做了一次快照读，事务 B 插入并提交，事务 A 再做 `UPDATE`（而非 `SELECT`），可能会"找到"并更新到 B 插入的行，产生类似幻读的效果。这是 MVCC 和锁定读的语义差异。

**Q5: 为什么 COUNT(*) 在大表上慢？**
InnoDB 不维护表的总行数计数器（因为 MVCC 需要返回对当前事务可见的行数，计数器无法区分版本）。`SELECT COUNT(*)` 走最小索引做全扫描。如果需要频繁获取近似行数，可以使用 `SHOW TABLE STATUS` 或 `EXPLAIN SELECT COUNT(*)` 的估计值。PostgreSQL 同样做全表/全索引扫描，但 VACUUM 更新了统计信息后，`pg_class.reltuples` 可以是近似行数的合理估计（注意是估计，非精确）。
