# 操作系统基础 — 与 Java 开发相关的 OS 知识

## 概述

Java 工程师通常通过 JVM 这一抽象层与操作系统交互，但在处理性能问题、并发调试、IO 优化、内存问题诊断时，理解操作系统层面的机制是不可或缺的。本文聚焦于与 Java 后端开发工作最密切相关的 OS 知识领域：进程/线程模型、虚拟内存、CPU 调度、同步机制、文件系统、IO 模型和内存管理。每一节都会将 OS 概念与 Java 中的具体表现相联系，让理论落地到日常开发实践。

---

## 核心内容

### 一、进程与线程

#### 1.1 Linux 进程模型

Linux 内核中，进程（Process）和线程（Thread）统一为 `task_struct` 结构。两者的核心区别在于资源共享程度：进程拥有独立的虚拟地址空间、文件描述符表、信号处理等；而同一进程的多个线程共享虚拟地址空间和文件描述符表。

`fork()` 系统调用创建新进程（子进程是父进程的副本，采用 Copy-on-Write 策略优化性能），`clone()` 系统调用可以更精细地控制资源共享粒度——当指定 `CLONE_VM | CLONE_FS | CLONE_FILES` 等参数时，`clone()` 创建的就是"线程"。

#### 1.2 NPTL 线程实现

Linux 的线程库经历了 LinuxThreads → NPTL（Native POSIX Thread Library）的演进。NPTL 基于 1:1 模型实现——每个用户态线程对应一个内核态 `task_struct`。这意味着：
- 线程调度由内核 CFS 调度器完成
- 线程可以在多核 CPU 上真正并行执行
- 但线程创建/销毁和上下文切换的开销比用户态线程（Green Threads）高

#### 1.3 Java 线程与 OS 线程的映射

**在 JDK 25（含 Virtual Threads 之前），每个 `java.lang.Thread` 实例对应一个 OS 线程**（基于 `pthread_create` 或等效的系统调用）。这一点在 HotSpot 源码的 `os_linux.cpp` 中可以看到：

```
JavaThread → OSThread → pthread_t → kernel task_struct
```

**Virtual Threads（JDK 25，JEP 444）** 打破了这个 1:1 映射。Virtual Thread 是用户态的轻量级线程，由 JVM 内部的 `ForkJoinPool` 作为调度器，多个 Virtual Thread 被多路复用到一个 Carrier Thread（即一个 OS 线程）上执行。当 Virtual Thread 执行阻塞 I/O 操作时，JVM 会自动将其从 Carrier Thread 上卸载（unmount），释放 OS 线程去执行其他 Virtual Thread。

这意味着数以百万计的 Virtual Thread 可以运行在少量 OS 线程之上，极大地减少了线程上下文切换的开销。

```java
// JDK 25 Virtual Threads：可以轻松创建 100 万个"线程"
try (var executor = Executors.newVirtualThreadPerTaskExecutor()) {
    for (int i = 0; i < 1_000_000; i++) {
        executor.submit(() -> {
            // 每个任务在一个 Virtual Thread 上执行
            Thread.sleep(Duration.ofSeconds(1));
            return null;
        });
    }
}
// 仅使用少量 OS 线程（默认等于 CPU 核心数）
```

### 二、虚拟内存

#### 2.1 分页与页表

Linux 内核使用分页（Paging）机制实现虚拟内存。虚拟地址被划分为固定大小的页（通常 4KB，也支持 2MB 大页和 1GB 巨页），物理内存被划分为同样大小的页框（Page Frame）。页表（Page Table）维护虚拟页到物理页框的映射。

多级页表（x86-64 使用 4 级或 5 级）解决了单级页表空间过大的问题——对于一个 48 位虚拟地址空间（256TB），4KB 页大小意味着 2^36 个页表项，单级页表需要 512GB 的内存，这显然不可行。

**x86-64 四级页表地址翻译过程（48 位虚拟地址）：**

虚拟地址按位被划分为 5 个字段（每级 9 位索引 + 页内偏移 12 位）：

```
| PML4[47:39] | PDPT[38:30] | PD[29:21] | PT[20:12] | Offset[11:0] |
```

完整翻译流程（硬件页表漫游，Hardware Page Table Walk）：

1. **CR3 寄存器** 持有当前进程的 PML4（Page Map Level 4）基物理地址
2. **PML4[47:39]**：取虚拟地址高 9 位，索引 PML4 中的一项（512 项之一），得到下一级 PDPT 的物理基地址
3. **PDPT[38:30]**：索引 PDPT，获得 PD（Page Directory）物理地址。若该项的 PS（Page Size）标志位为 1，表示这是一个 **1GB 大页**，直接拼接 Offset[29:0]，翻译结束
4. **PD[29:21]**：索引 PD，获得 PT（Page Table）物理地址。若 PS=1，表示这是一个 **2MB 大页**，拼接 Offset[20:0]，翻译结束
5. **PT[20:12]**：索引 PT，获得最终的 4KB 物理页框号
6. **物理地址 = (页框号 << 12) | Offset[11:0]**

每一步查表都是一次内存访问，因此一个完整的 4KB 页翻译在 **不命中 TLB 时需 4 次内存访问**（加上最终目标地址共 5 次）。这就是为什么 TLB 命中率直接影响系统性能——TLB 命中只需 1 个 CPU 周期，而硬件页表漫游需要 10-100 个周期。

> **5 级页表（LA57）：** Intel Ice Lake 及更新处理器支持 5 级页表，虚拟地址扩展到 57 位（128PB 寻址），在 PML4 之上增加 PML5。面向超大规模内存计算场景，对普通 Java 应用无影响。

**Linux 内核中页表的数据结构：**

```c
// Linux 内核中 pgd → p4d → pud → pmd → pte 的层次关系
// include/linux/mm_types.h 和 arch/x86/include/asm/pgtable.h
pgd_t *pgd  = pgd_offset(mm, addr);    // Page Global Directory  (= PML4)
p4d_t *p4d  = p4d_offset(pgd, addr);   // P4D (5级页表的过渡层)
pud_t *pud  = pud_offset(p4d, addr);   // Page Upper Directory   (= PDPT)
pmd_t *pmd  = pmd_offset(pud, addr);   // Page Middle Directory  (= PD)
pte_t *pte  = pte_offset_kernel(pmd, addr); // Page Table Entry  (= PT)
// 最终从 pte 中提取物理页框号 (PFN)
```

**对 Java 的影响：** JVM 的堆内存是 mmap 分配的大片连续虚拟地址空间。当 JVM 首次访问未映射的堆页时，内核按需分配物理页并填充页表。使用 `-XX:+AlwaysPreTouch` 可以让 JVM 在启动时就访问所有堆页，触发物理页分配和页表建立，虽然增加启动时间，但避免了运行时的缺页中断抖动。

#### 2.2 TLB（Translation Lookaside Buffer）

TLB 是 CPU 内部的硬件缓存，缓存最近使用的虚拟地址到物理地址的转换结果。TLB 命中时，地址转换只需一个 CPU 周期；TLB 未命中则需要访问多级页表（3-5 次内存访问），代价高昂。

**对 Java 的影响：**
- 大对象（或大数组）分散在多个 4KB 页中，容易造成 TLB 未命中
- 使用大页（Huge Pages，如 2MB 页）可以减少 TLB 压力——`-XX:+UseLargePages` 启用
- 对于堆内存 > 32GB 的 JVM，大页带来的 TLB 收益更加显著

**TLB Miss 的完整处理流程：**

当 CPU 进行地址翻译时在 TLB 中查不到对应映射，触发 TLB miss。x86-64 上的处理流程如下：

```
虚拟地址 → TLB 查找 → 未命中（TLB miss）
    ↓
MMU 硬件页表漫游（Hardware Page Table Walk）
    ↓
├─ 遍历过程中任一页表项 Present 位 = 0 → 触发 Page Fault（缺页中断）
│       ↓
│   OS 缺页处理程序（do_page_fault）：
│   1. 检查地址合法性（vm_area_struct → vm_start ≤ addr < vm_end）
│   2. 区分 Minor / Major fault
│   3. Minor：分配物理页，建立页表映射，返回
│   4. Major：触发磁盘 I/O（swap in / 文件读取），阻塞当前进程
│   5. 缺页处理完成后，重新执行引发 fault 的指令
│
└─ 页表项有效 → 将虚拟→物理映射加载到 TLB
       ↓
   需要驱逐一个旧的 TLB entry（LRU 或随机替换）
       ↓
   重新执行原指令，此次 TLB 命中
```

**TLB 刷新（Flush）的性能影响：**

每次进程/线程上下文切换，内核需要切换地址空间（切换 CR3 寄存器），这导致 **TLB 全部失效**（除非启用 PCID，Process Context Identifier）。这就是线程切换频繁时产生"TLB 冷启动"——上下文切换后的一段时间内 TLB miss 率飙升，每次 miss 需要 4 次内存访问，大幅拖慢执行速度。Java Virtual Threads 的关键优势之一就是：用户态切换不涉及 CR3 切换，已有的 TLB 内容全部保留。

**大页（Huge Pages / Transparent Huge Pages）深度分析：**

| 页大小 | 单页覆盖 | TLB 覆盖范围（假设 64 条 L1 D-TLB entry） | 页表级数 |
|---|---|---|---|
| 4KB | 4KB | 256KB | 4 级 |
| 2MB | 2MB | 128MB | 3 级（跳过 PT） |
| 1GB | 1GB | 64GB | 2 级（跳过 PT+PD） |

**显式大页（HugeTLB）：**
- 需要系统管理员预先在 `/proc/sys/vm/nr_hugepages` 中预留大页
- JVM 通过 `-XX:+UseLargePages`（JDK 8 需额外 `-XX:LargePageSizeInBytes=2m`）启用
- 预留页面不会换出（不被 swap 管理），保证了延迟的确定性
- 缺点：预留过多会浪费内存，且需 root 权限配置

**透明大页（Transparent Huge Pages, THP）：**
- 内核在后台自动将连续的 4KB 页合并为 2MB 大页，对应用透明
- 后台 khugepaged 线程定期扫描并合并，但可能引入 CPU 尖峰
- THP 分配大页失败时可能触发直接压缩（compaction），导致短暂 STW 延迟
- `echo never > /sys/kernel/mm/transparent_hugepage/enabled` 可禁用

**THP 对 Java 应用的影响：**

对于 JVM（尤其是 GC），THP 有双重影响。当堆很大（如 32GB+）且存活对象集中在相邻页时，内核将大量 4KB 页合并为 2MB 大页，显著提升 TLB 命中率。**但如果 JVM 频繁分配/释放对象**，碎片化会阻止大页合并，THP 的 compaction 反而增加延迟抖动。这也是为什么某些场景下建议 THP 设为 `madvise`（仅在应用明确标记时使用大页），结合 `-XX:+UseTransparentHugePages`（JDK 8u102+），让 JVM 只在堆区域使用大页。

```bash
# 查看当前 THP 模式
cat /sys/kernel/mm/transparent_hugepage/enabled
# [always] madvise never

# 查看 JVM 进程的实际大页使用
grep -E "AnonHugePages|VmFlags" /proc/<pid>/smaps | grep -A1 "thp"
```

```java
// JVM 启动参数示例 — 使用 2MB 大页优化大堆 TLB
// java -Xms32g -Xmx32g -XX:+UseLargePages -XX:LargePageSizeInBytes=2m
//       -XX:+AlwaysPreTouch -XX:+UseTransparentHugePages
// AlwaysPreTouch：启动时即触达所有堆页，提前触发 THP 合并，避免运行时 compaction 抖动
```

#### 2.3 缺页中断（Page Fault）

当程序访问一个虚拟地址但对应的物理页不在内存中时，触发缺页中断：
- **Minor Page Fault：** 页在内存中但未映射到当前进程页表（如共享库页面），只需更新页表。
- **Major Page Fault：** 页不在内存中，需要从磁盘加载（swap in），代价极高。

**Java GC 与缺页的关系：**
- Full GC 后，存活对象被压缩到连续的内存区域，可能之前分散的页面被释放，留下空洞
- 如果 GC 后访问已被 swap out 的页面，会触发 Major Page Fault，导致 GC 暂停后的"第二次暂停"
- 生产环境建议禁用 swap（`vm.swappiness=0`），或使用 `mlockall` 锁定 JVM 堆

#### 2.4 mmap 与 Java DirectByteBuffer

`mmap` 系统调用将文件映射到进程的虚拟地址空间，实现文件与内存的直接映射。读写映射区域等同于读写文件，由内核的 Page Cache 机制自动同步。

**Java 中的对应：**

```java
// 使用 FileChannel.map 进行内存映射 I/O
try (var channel = FileChannel.open(Path.of("large.dat"),
        StandardOpenOption.READ)) {
    var buffer = channel.map(
        FileChannel.MapMode.READ_ONLY, 0, channel.size());
    // 直接通过内存访问文件内容，无需 read() 系统调用
    byte[] data = new byte[1024];
    buffer.get(data);
}
```

`DirectByteBuffer` 分配的是堆外内存（off-heap memory），底层使用 `malloc`/`mmap`。优势：绕过 JVM 堆和 GC 管理、网络 I/O 时避免从堆内存到堆外内存的额外拷贝。例如 Netty 的内部缓冲区就基于 `DirectByteBuffer`。

**DirectByteBuffer 内部机制详解：**

`DirectByteBuffer` 的底层分配机制在 HotSpot 中的实现（`java.nio.DirectByteBuffer` 构造器）：

```java
// 简化示意 — DirectByteBuffer 的底层分配路径
// 1. ByteBuffer.allocateDirect(capacity) →
// 2. new DirectByteBuffer(capacity) →
// 3. Unsafe.allocateMemory(size)  ← 调用本地方法
// 4.   └→ os::malloc(size) 或 mmap   ← HotSpot 本地实现

// HotSpot src/hotspot/share/services/allocator.cpp 中的实际路径：
// ┌─ 小内存 (< 某个阈值)：通过 malloc 分配（glibc ptmalloc）
// └─ 大内存：通过 mmap(MAP_PRIVATE | MAP_ANONYMOUS) 匿名映射
```

**mmap 两种映射类型与 DirectByteBuffer 的关系：**

| mmap 标志 | 用途 | Java 对应 |
|---|---|---|
| `MAP_ANONYMOUS` | 匿名映射（无文件后备），分配堆外内存 | `ByteBuffer.allocateDirect()` |
| `MAP_SHARED` + fd | 文件映射，Page Cache 与用户空间共享 | `FileChannel.map()` → `MappedByteBuffer` |
| `MAP_PRIVATE` + fd | 文件映射（写时复制），修改不写回文件 | — |

**DirectByteBuffer 释放机制与 Cleaner：**

`DirectByteBuffer` 的内存不由 GC 直接回收，而是通过 `java.lang.ref.Cleaner` 机制：当 `DirectByteBuffer` 对象本身被 GC 时，其关联的 `Cleaner` 被触发，调用 `Unsafe.freeMemory()` 释放堆外内存。这意味着：

1. **堆外内存泄漏风险：** 如果 DirectByteBuffer 被"遗忘"在 old generation 但未触发 GC，堆外内存持续占用
2. **显式释放：** `((DirectBuffer) buffer).cleaner().clean()` 可主动释放（Netty 的 `PooledByteBufAllocator` 就是这样管理堆外内存池的）
3. **监控：** `jcmd <pid> VM.native_memory summary` 可追踪堆外内存使用量

```java
// Netty 的堆外内存管理思路（PooledByteBufAllocator）：
// 1. 预分配大块堆外内存（mmap）
// 2. 内部池化小块分配（类似 Jemalloc 的 slab）
// 3. 引用计数管理生命周期，避免 GC 不确定性
// 4. 内存泄漏检测（-Dio.netty.leakDetection.level=PARANOID）

// 这与内核的 slab 分配器思想一致：大块分配 + 内部精细管理
```

### 三、CPU 调度

#### 3.1 CFS 调度器

Linux 从 2.6.23 开始使用完全公平调度器（Completely Fair Scheduler, CFS）。CFS 的核心思想是：为每个可运行的任务维护一个 `vruntime`（虚拟运行时间），调度器始终选择 `vruntime` 最小的任务执行。`vruntime` 的增长速率与任务权重（由 nice 值决定）成反比——权重越高的任务，`vruntime` 增长越慢，从而获得更多 CPU 时间。

CFS 使用红黑树组织所有可运行任务，保证选择最小 `vruntime` 任务的时间为 O(log n)。

#### 3.2 CPU 亲和性

CPU 亲和性（CPU Affinity）控制进程/线程绑定到特定的 CPU 核心或 NUMA 节点，减少缓存失效和跨 NUMA 节点内存访问。

**Java 中的应用：**
- 可以使用 `taskset` 命令限定 JVM 进程的 CPU 亲和性
- `-XX:+UseNUMA` 启用 NUMA 感知的内存分配和 GC
- 对于延迟敏感的应用（如高频交易），将关键线程绑定到独立核心可以避免缓存污染

#### 3.3 Java 线程优先级与 OS 的关系

`Thread.setPriority(int)` 设 1-10 的优先级。在 Linux 上，JVM 将 Java 优先级映射到 nice 值（-20 到 19）。但这种映射是不可靠的——Linux CFS 调度器使用 nice 值作为权重因子，但不能保证高优先级线程一定能抢占低优先级线程。因此，**不要依赖线程优先级来保证程序正确性**；它只作为调度提示使用。

### 四、同步机制

#### 4.1 互斥锁、自旋锁、futex

- **互斥锁（Mutex）：** 最常用的排他锁。当锁被持有时，尝试获取的线程进入睡眠（阻塞），CPU 可用于其他任务。
- **自旋锁（Spinlock）：** 不断循环检查锁是否可用，不释放 CPU。适合临界区非常短的情况（锁持有时间 < 上下文切换开销），否则严重浪费 CPU。
- **futex（Fast Userspace muTEX）：** Linux 特有的混合锁机制。在无竞争时，完全在用户态完成（通过原子操作），不涉及系统调用；有竞争时，才通过 `futex()` 系统调用让线程进入内核等待队列。

**futex 系统调用的完整工作流程：**

futex 是一个 32 位整数的用户态地址，配合 `futex()` 系统调用实现高效率的锁。它的核心哲学是："无竞争，无事发生"（no contention, no kernel involvement）。

```
futex 工作流程（以互斥锁为例）：

【阶段 1：快速路径 — 用户态获取（无竞争）】

线程 A 尝试获取锁：
  1. 原子 CAS(&futex_word, 0, 1)  — 如果 futex_word 原值为 0（无锁），
     将其设为 1（锁定），成功获取锁
  2. 无需任何系统调用！全程在用户态完成，约 10-20 ns

线程 A 执行临界区代码...


【阶段 2：竞争 — 内核态等待】

线程 B 尝试获取锁（锁已被 A 持有）：
  1. 原子 CAS(&futex_word, 0, 1)  — futex_word 当前值为 1（A 持有），CAS 失败
  2. 自旋等待（用户态自旋，可选）：短暂循环重试 N 次（取决于锁竞争历史和自适应
     自旋策略），希望 A 很快释放锁
  3. 自旋超时/次数耗尽 → futex(FUTEX_WAIT, &futex_word, 1, NULL)
     ┌─ 进入内核
     ├─ 内核在 futex_hash_bucket（全局哈希表）中查找该 futex_word 的等待队列
     ├─ 将线程 B 加入等待队列（futex_q）
     ├─ 将线程 B 设为 TASK_INTERRUPTIBLE（可被信号唤醒）
     ├─ 调用 schedule() 让出 CPU，执行其他线程
     └─ 阻塞完成


【阶段 3：释放与唤醒】

线程 A 释放锁：
  1. 原子 CAS(&futex_word, 1, 0)  — 将锁状态重置为 0
  2. futex(FUTEX_WAKE, &futex_word, 1)
     ┌─ 进入内核
     ├─ 从 futex 等待队列中取出一个等待者（wake 参数 = 1 表示只唤醒一个）
     ├─ 将其设为 TASK_RUNNING 状态
     ├─ 加入 CPU 运行队列
     └─ 返回用户态
  3. 被唤醒的线程 B 从 futex(FUTEX_WAIT) 返回，重新尝试 CAS 获取锁
```

**futex 的内核数据结构：**

```c
// 简化示意 — Linux kernel/futex/waitwake.c
struct futex_q {
    struct plist_node list;        // 优先级链表节点
    struct task_struct *task;      // 等待的线程
    union futex_key key;           // futex_word 的哈希 key
    // ...
};

// 全局 futex 哈希表：futex_queues[256] (per CPU / total)
// futex_word → hash(futex_word, mm_struct) → futex_hash_bucket → plist
```

**futex 的设计精妙之处：**
- **用户态判断无冲突**（CAS）—— 90% + 的锁获取在用户态完成
- **内核态处理冲突**（futex_wait / futex_wake）—— 仅在有真正竞争时进入内核
- 等待队列使用 **plist（优先级链表）**，支持 PI futex（Priority Inheritance，优先级继承），防止优先级反转

#### 4.2 Java synchronized 的底层实现

`synchronized` 关键字经历了从重量级锁（JDK 1.0-1.2）到偏向锁→轻量级锁→重量级锁的锁膨胀过程（JDK 6+）。

**锁膨胀路径：**

```
无锁 → 偏向锁（Biased Locking）→ 轻量级锁（CAS自旋）→ 重量级锁（futex）
```

1. **偏向锁：** 第一次被线程 A 获取时，在 Mark Word 中记录 A 的线程 ID。之后 A 再次进入同步块时无需任何同步操作。当另一个线程 B 尝试获取时，撤销偏向锁。
2. **轻量级锁：** 通过 CAS 在线程栈帧的 Lock Record 和对象头的 Mark Word 之间拷贝/替换。失败则自旋等待。适合锁持有时间短的场景。
3. **重量级锁：** 向 OS 申请 mutex，未获取到锁的线程阻塞（通过 `pthread_cond_wait` → `futex`）。线程唤醒需要内核态切换，开销最大。

**注意：JDK 15 默认禁用了偏向锁**（`-XX:-UseBiasedLocking`，JDK 21+ 已移除偏向锁实现），因为在高并发场景下偏向锁的撤销成本高于其收益。

**锁升级路径与 Linux futex 的对应关系：**

每次锁升级都对应着底层机制的根本变化，从纯粹的 CPU 原子指令逐步过渡到内核调度：

```
Java 层面：         Linux 内核层面：
─────────          ───────────────

偏向锁 ────────→  （纯用户态，仅写 Mark Word 线程 ID）
   ↓ 撤销（需要 STW SafePoint）
轻量级锁 ──────→  CAS 自旋（用户态原子操作，不涉及系统调用）
   ↓ 膨胀（CAS 失败次数超过阈值 -XX:PreBlockSpin=10，或等待超过一定时间）
重量级锁 ──────→  futex(FUTEX_WAIT) → 内核等待队列 → schedule()
   ↓
管程结构 ──────→  ObjectMonitor → cxq/EntryList/WaitSet → pthread_cond_wait
```

**重量级锁的完整膨胀过程（从轻量级到重量级）：**

1. 线程 A 持有轻量级锁（Lock Record 在 Mark Word 中）
2. 线程 B 尝试 CAS 获取锁，失败，自旋等待（默认自旋 10 次，可通过 `-XX:PreBlockSpin` 调整）
3. 自旋失败后，JVM 决定将锁膨胀为重量级锁：
   - 分配 `ObjectMonitor` 对象
   - 将 Mark Word 从轻量级锁形态替换为指向 `ObjectMonitor` 的指针
   - 调用 `ObjectMonitor::EnterI()` → `os::PlatformEvent::park()` → `pthread_cond_wait()` → `futex(FUTEX_WAIT)`
4. 线程 B 挂起，进入内核的 futex 等待队列，状态变为 `TASK_INTERRUPTIBLE`
5. 线程 A 释放锁时：
   - 调用 `ObjectMonitor::exit()` → `os::PlatformEvent::unpark()` → `pthread_cond_signal()` → `futex(FUTEX_WAKE)`
   - 内核将被唤醒线程从等待队列移到运行队列
   - 被唤醒线程重新竞争获取锁

**完整的 HotSpot 源码路径：**

**伪共享（False Sharing）的完整解释：**

现代 CPU 的缓存一致性协议（如 MESI / MOESI）以 **缓存行（Cache Line，典型 64 字节）** 为单位进行操作。当核心 A 写入变量 X 所在的缓存行时，它必须获得该缓存行的 **独占（Exclusive/Modified）** 状态——这意味着核心 B 缓存中同一缓存行的副本被标记为无效（Invalid）。

即使核心 A 和核心 B 访问的是同一缓存行中 **完全不同、毫无关联的两个变量**，这个失效机制仍然触发：

```
核心 A                          核心 B
  │                               │
  │  写 varX（地址 0x1000）         │  读 varY（地址 0x1038）
  │  ┌─────────────────┐          │  ┌─────────────────┐
  │  │ Cache Line #42   │          │  │ Cache Line #42   │
  │  │ [0x1000-0x103F]  │  ←──→   │  │ [0x1000-0x103F]  │
  │  │ varX=1  varY=0   │  总线嗅探 │  │ varX=1  varY=0   │
  │  └─────────────────┘          │  └─────────────────┘
  │  (Modified 状态)              │  (Invalid 状态!)
  │                               │
  │  A写varX → B的缓存行失效 → B读varY 时触发 cache miss
  │  即使 varX 和 varY 毫无关系！
```

**诊断伪共享的性能代价：** 当两个频繁写入的变量不幸在同一个缓存行时，缓存行在两个核心之间反复弹跳（cache-line bouncing / ping-pong），有效带宽被总线流量耗光，吞吐量可能下降 **10-100 倍**。

**Java 中的解决方案：**

```java
// 1. JDK 9+ 使用 @Contended 注解（需 -XX:-RestrictContended 或 JDK 内部使用）
public class Counter {
    // 每个 cell 独占一个缓存行，互不干扰
    @jdk.internal.vm.annotation.Contended
    volatile long value;
}

// 2. 手动填充（JDK 8 兼容）
public class PaddedCounter {
    // 前填充：确保 value 不会与上一个对象共享缓存行
    long p1, p2, p3, p4, p5, p6, p7;
    volatile long value;
    // 后填充：确保 value 不会与下一个对象共享缓存行
    long p8, p9, p10, p11, p12, p13, p14;
    // 共 7*8 + 8 + 7*8 = 120 字节 >= 128，比 2 个缓存行还多
    // 注意：JDK 8 @Contended 内部也使用 128 字节填充
}

// 3. 实际应用：ConcurrentHashMap 内部实现
// src/jdk.unsupported/share/classes/sun/misc/Contended.java
// striping 计数器每条 stripe 独占一个缓存行，避免写竞争时互相 invalidate
```

**典型伪共享场景 — Disruptor RingBuffer：**

LMAX Disruptor（高性能无锁队列）的设计核心之一就是通过填充避免 RingBuffer 的 sequence 计数器之间的伪共享。每一个生产者的 sequence 和每一个消费者的 sequence 都被填充到不同缓存行，确保高并发下的写入不会互相干扰。这也是 Disruptor 能达到每秒千万级事件处理的关键技术之一。

### 五、文件系统与 I/O

#### 5.1 inode 与 VFS

Linux 使用 VFS（Virtual File System）向上提供统一的文件操作接口（`open`/`read`/`write`/`close`），向下适配不同文件系统（ext4、xfs、btrfs 等）。

`inode`（Index Node）是文件系统的核心数据结构，存储文件的元数据（权限、大小、时间戳、数据块指针），但不包含文件名。文件名存储在目录文件中（目录本质上是一个从文件名到 inode 编号的映射表）。

**对 Java 开发的影响：**
- `Files.getAttribute()` 可以读取 inode 中的元数据
- 小文件过多时，inode 耗尽也是一个常见问题（`df -i` 检查）
- 目录中文件数过多（1000 万级别）时，`ls` 变慢是因为遍历目录文件需要多次磁盘 I/O

#### 5.2 Page Cache

Linux 内核使用 Page Cache 缓存文件数据页。当读取文件时，内核先将数据读到 Page Cache，再从 Page Cache 拷贝到用户缓冲区；写入时，先写入 Page Cache，标记为脏页，随后由内核在适当时机刷写到磁盘。

**Java FileChannel 与零拷贝（Zero Copy）：**

`FileChannel.transferTo()` 利用 Linux 的 `sendfile()` 系统调用实现零拷贝——数据直接从 Page Cache 传输到 Socket Buffer，不经过用户态缓冲区。这是 Kafka 高性能的关键技术之一。

```java
// 零拷贝：文件直接传输到网络，不经过用户空间
try (var fileChannel = FileChannel.open(Path.of("large.file"), READ);
     var socketChannel = SocketChannel.open(new InetSocketAddress("host", 8080))) {
    fileChannel.transferTo(0, fileChannel.size(), socketChannel);
}
```

普通 I/O 的数据路径（4 次拷贝 + 4 次上下文切换）：
```
磁盘 → Page Cache（DMA）→ 用户缓冲区（CPU）→ Socket Buffer（CPU）→ 网卡（DMA）
```

`sendfile` 零拷贝的数据路径（2 次拷贝 + 2 次上下文切换）：
```
磁盘 → Page Cache（DMA）→ 网卡（DMA+CPU 描述符）
```

#### 5.3 I/O 模型

| 模型 | 阻塞点 | Java 对应 API |
|---|---|---|
| 阻塞 I/O | `read()` 阻塞直到有数据 | `InputStream.read()`、`Socket.getInputStream()` |
| 非阻塞 I/O | `read()` 立即返回（有数据则返回，无数据返回 -1 或 0） | `SocketChannel.read()`（需先设 `configureBlocking(false)`） |
| I/O 多路复用 | `select()/poll()/epoll_wait()` 阻塞，等待多个 fd 中的任一个就绪 | `Selector.select()` |
| 异步 I/O | 从不阻塞，完成后回调通知 | `AsynchronousSocketChannel`（基于线程池模拟，非真正内核 AIO） |

#### 5.4 Java NIO 与 epoll 的关系

`Selector` 是 Java NIO 多路复用的核心。在 Linux 上，`Selector.open()` 默认使用 `EPollSelectorImpl`（基于 epoll）：

```
Selector.select() → EPollArrayWrapper.epollWait() → epoll_wait() 系统调用
```

**epoll 相比 select/poll 的优势：**
- **O(1) 复杂度：** epoll 使用红黑树管理注册的 fd，`epoll_wait` 只需取出就绪列表（rdlist），复杂度 O(1)；而 select/poll 需要遍历整个 fd 集合 O(n)
- **无 fd 数量限制：** select 默认 1024，poll 无上限但大集合性能差；epoll 支持数百万 fd
- **事件驱动：** epoll 通过回调机制在 fd 就绪时将事件加入就绪列表，不需要每次轮询

Netty 框架底层就是基于 `Selector` + epoll（或 kqueue on macOS）构建高性能网络通信。

**epoll 两种触发模式详解（Level-Triggered vs Edge-Triggered）：**

epoll 提供两种事件通知模式，理解它们的区别是写出正确、高性能 NIO 代码的前提。

| 维度 | Level-Triggered（LT，水平触发） | Edge-Triggered（ET，边缘触发） |
|---|---|---|
| 通知行为 | fd 就绪期间，每次 `epoll_wait` 都返回该事件 | fd **从非就绪变为就绪时**只通知一次 |
| 读写策略 | 可以分批读写，读一部分也能再收到通知 | **必须一次性读完/写完**所有数据，否则数据丢失/事件饥饿 |
| 编程复杂度 | 低，容错性好 | 高，必须使用非阻塞 I/O + 循环直到返回 EAGAIN |
| 适用场景 | 简单应用、连接数少 | 高性能服务器（Nginx、Netty epoll 传输） |
| `epoll_wait` 开销 | 略高（就绪 fd 持续触发） | 低（每个 fd 只通知一次） |

**LT 模式的工作方式：**

```
Socket fd 收到 4KB 数据，内核缓冲区有 4KB
│
├─ 第 1 次 epoll_wait → 返回 fd（EPOLLIN），用户 read(fd, buf, 4096)
│   用户只读了 1KB，缓冲区还剩 3KB
│
├─ 第 2 次 epoll_wait → 再次返回 fd！因为缓冲区还有 3KB 未读
│   用户 read(fd, buf, 3072)，缓冲区清空
│
├─ 第 3 次 epoll_wait → 不返回 fd（缓冲区空，无新数据到达就阻塞）
```

**ET 模式的工作方式（必须循环读直到 EAGAIN）：**

```c
// epoll ET 模式的正确读操作（C 代码）
// 关键：循环读直到返回 EAGAIN（表示缓冲区已空）
int sockfd; // 已注册到 epoll，EPOLLIN | EPOLLET
char buf[4096];

// epoll_wait 返回此 fd 后：
while (1) {
    ssize_t n = read(sockfd, buf, sizeof(buf));
    if (n > 0) {
        process_data(buf, n);  // 处理读到的数据
    } else if (n == 0) {
        // 对端关闭连接
        close(sockfd);
        break;
    } else { // n == -1
        if (errno == EAGAIN || errno == EWOULDBLOCK) {
            // 缓冲区已空，此次通知的数据已全部读完
            // 可以退出循环，等待下一次 epoll_wait 通知
            break;
        }
        // 其他错误（EINTR 等）需要处理
    }
}

// 如果不用循环读到 EAGAIN：
// 下次 epoll_wait 不会再通知这个 fd！
// 缓冲区中剩余的数据将永远被"忽略"，导致连接挂起
```

**同一个 fd 边沿触发时只通知一次的含义：**

```
Socket fd 收到 4KB 数据，内核缓冲区从 0 → 4KB（状态变化！）
│
├─ epoll_wait → 返回 fd（EPOLLIN），唯一一次通知
│   用户 read() 读到部分数据（因为用非阻塞 I/O）
│   剩余数据还在内核缓冲区，但不会再触发 epoll 通知了！
│
├─ 下次 epoll_wait → 不会返回 fd（因为没有新的"边缘"事件）
│   → 剩余数据永远等待，连接"挂死"
```

这便是 ET 模式要求"一次读完"的根本原因。使用 ET 模式的正确做法是**一直 read 直到返回 EAGAIN**。

**io_uring — 新一代 Linux 异步 I/O：**

io_uring 是 Linux 5.1+ 引入的革命性异步 I/O 接口，从根本上重新设计了异步 I/O 的模型：

**传统 AIO 的问题：** Linux 的 POSIX AIO（`aio_read`/`aio_write`）长期不被推荐使用——它在内部通常使用线程池模拟异步操作（glibc 实现），并非真正的内核异步 I/O。这使得 Java 的 `AsynchronousSocketChannel` 实际上也是基于线程池而非内核级异步 I/O。

**io_uring 的核心设计 — 共享环形缓冲区（Submission Queue + Completion Queue）：**

```
用户态                       内核态
┌──────────┐               ┌──────────┐
│ 应用     │               │  内核    │
│          │──SQ (写)──→   │          │
│ mmap映射 │               │ 处理请求  │
│          │←──CQ (读)──   │          │
└──────────┘               └──────────┘

SQ（Submission Queue）：应用写入 I/O 请求（READ/WRITE/ACCEPT 等 SQE）
CQ（Completion Queue）：内核写入完成结果（CQE）

两者都在用户态和内核态之间通过 mmap 共享，零拷贝！
```

**io_uring 相比 epoll 的关键优势：**

1. **系统调用次数：** epoll 至少需要 `epoll_wait` + `read`/`write` 两次系统调用；io_uring 在 SQ 非空时可以通过 `io_uring_enter` 一次性提交+收割，甚至在 SQPOLL 模式下做到 **零系统调用**（内核线程持续轮询 SQ）
2. **批量提交与收割：** 一次 `io_uring_enter` 可以提交 N 个 I/O 请求、收割 M 个完成结果
3. **文件 I/O 真正异步：** epoll 只能监控网络 fd，对文件 I/O 无能为力（文件总是"就绪"的）。io_uring 对 文件 I/O（read/write 文件）也能做到真正的异步——内核在后台执行直接 I/O 或 buffered I/O
4. **Buffer Ring / Fixed Buffers：** 预注册缓冲区，避免每次 I/O 的缓冲区映射开销

**Java 中的 io_uring 现状与 Project Loom 的关系：**

截止 JDK 25，Java 标准库尚未原生支持 io_uring。但 Netty 已在实验性分支中引入了基于 JNI 的 `IoUringEventLoop`。更深远的影响来自 **Project Loom**：

```
epoll 模型（当前）：              io_uring 模型（未来）：
Virtual Thread 阻塞 read()      Virtual Thread 阻塞 read()
    ↓                               ↓
JVM park() Carrier Thread          JVM 提交 SQE 到 io_uring SQ
    ↓                               ↓
Carrier Thread 调用 epoll_wait     Carrier Thread 立即释放执行其他 VT
    ↓                               ↓
epoll_wait 返回 → unpark VT        CQ 完成 → unpark VT

关键差异：
epoll 时代：即使有 VT，底层仍依赖 epoll（事件驱动 + 回调）
io_uring 时代：VT 挂起时直接提交异步请求，无需事件循环
              理论上 I/O 吞吐量和 CPU 利用率都能再上一个台阶
```

```java
// Project Loom + io_uring 的理想未来（JDK 尚未实现，仅示意）
// 每个 Virtual Thread 都可以做"真正的异步 I/O"
try (var server = new ServerSocketChannel(...)) {
    while (true) {
        // accept 在 io_uring 中异步完成，VT park 不耗 OS 线程
        var client = server.accept();
        Thread.startVirtualThread(() -> {
            // read 在 io_uring 中异步完成
            var data = client.read(...);
            // write 同样异步完成
            client.write(response);
        });
    }
}
// 所有 I/O 都在内核 io_uring 中异步执行
// Virtual Thread 仅在数据就绪时被唤醒
// 这意味着数百万并发连接只需极少 OS 线程
```

### 六、内存管理

#### 6.1 伙伴系统（Buddy System）

Linux 内核使用伙伴系统管理物理页面分配。它将空闲页面按 2^n 页（n = 0 到 10，即 1 页到 1024 页）组织为多个空闲链表。分配时找到第一个足够大的块，必要时分裂；释放时尝试与相邻的"伙伴"块合并。

**对 Java 的影响：** JVM 堆内存预分配时，`-Xms` 和 `-Xmx` 之间的差异可能导致内存碎片。将 `-Xms` 和 `-Xmx` 设为相同值可以减少堆增长带来的碎片化。

#### 6.2 Slab 分配器

伙伴系统以页为单位分配（最小 4KB），但对于内核中频繁分配的小对象（如 inode、dentry、task_struct），4KB 的粒度太粗糙。Slab 分配器建立在伙伴系统之上，为每种常用大小的内核对象维护对象缓存（cache），实现高效的小对象分配。

#### 6.3 NUMA（Non-Uniform Memory Access）架构详解

**NUMA 拓扑结构：**

多路服务器中，CPU 和内存被组织为多个 **NUMA 节点**。每个节点包含一组 CPU 核心和一段直连的本地内存。节点之间通过 **互联总线**（如 Intel UPI、AMD Infinity Fabric）连接：

```
┌─────────────────────────────────────────────────────┐
│                  NUMA Node 0                        │
│  ┌──────────┐  ┌──────────┐    ┌────────────────┐  │
│  │  Core 0  │  │  Core 1  │    │  本地内存 0     │  │
│  │  Core 2  │  │  Core 3  │    │  (64GB DDR5)   │  │
│  └──────────┘  └──────────┘    └────────────────┘  │
│                           │                         │
│                      UPI / IF (互联总线)             │
│                           │                         │
│                  NUMA Node 1                        │
│  ┌──────────┐  ┌──────────┐    ┌────────────────┐  │
│  │  Core 4  │  │  Core 5  │    │  本地内存 1     │  │
│  │  Core 6  │  │  Core 7  │    │  (64GB DDR5)   │  │
│  └──────────┘  └──────────┘    └────────────────┘  │
└─────────────────────────────────────────────────────┘
```

**访问延迟差异（量化参考）：**

| 访问类型 | 典型延迟 | 带宽 |
|---|---|---|
| L1 Cache | ~1 ns (4 cycles) | ~1 TB/s |
| L2 Cache | ~4 ns (14 cycles) | ~500 GB/s |
| L3 Cache (LLC) | ~12 ns (40 cycles) | ~300 GB/s |
| 本地内存（Local NUMA） | ~80-100 ns | ~100 GB/s |
| 远端内存（Remote NUMA） | **~130-160 ns** (1.3x-1.6x) | ~60 GB/s |

远端内存访问比本地慢 30%-60%，且带宽大幅降低。当多核同时争抢互联总线时，这个差距会进一步放大。

```bash
# 查看 NUMA 拓扑
numactl --hardware
# available: 2 nodes (0-1)
# node 0 cpus: 0 1 2 3 4 5 6 7 ...
# node 0 size: 64435 MB
# node 0 free: 12445 MB
# node distances:
# node   0   1
#   0:  10  21   ← 本地 10，远端 21（相对距离，乘以 10 ≈ 实际倍数）
#   1:  21  10

# 查看进程的 NUMA 内存分布
numastat -p <pid>
# Per-node process memory usage (in MBs) for PID 12345
#                            Node 0  Node 1  Total
#                  Private      512     2048  2560
#                  Shared      1024     1024  2048
```

**Java 在 NUMA 上的优化：**

1. **`-XX:+UseNUMA`** — 启用 NUMA 感知的内存分配和 GC：
   - JVM 启动时，Eden 区会在 **每个 NUMA 节点** 分别分配，而非只在一个节点分配大块
   - 线程优先从本地的 Eden 区分配对象（TLAB 本地化）
   - 幸存区晋升到老年代时，也尽量保持在本 NUMA 节点
   - Parallel GC 和 G1 GC 完整支持；ZGC（JDK 21+）逐步支持 NUMA

2. **`-XX:+UseNUMAInterleaving`** — 交错模式：将内存 round-robin 分配在所有 NUMA 节点。适合大量线程跨节点随机访问共享数据的场景（避免单一节点热点）

3. **`numactl` 绑定策略：**
```bash
# 将 JVM 绑定到 NUMA node 0 的 CPU 和内存
# 适合延迟敏感应用：避免任何跨节点访问
numactl --cpunodebind=0 --membind=0 java -jar app.jar

# 优先在 node 0 分配内存，不够时用其他节点
numactl --cpunodebind=0 --preferred=0 java -jar app.jar

# 交错分配（适合大堆共享数据场景）
numactl --interleave=all java -jar app.jar
```

NUMA 优化在生产中能带来 **5-15% 的吞吐提升**（大堆、高并发场景下更明显），但也可能因为内存跨节点迁移（NUMA balancing）导致性能波动。建议在绑核 + NUMA 感知的同时禁用自动 NUMA balancing：
```bash
echo 0 > /proc/sys/kernel/numa_balancing  # 生产环境建议关闭
```

#### 6.4 内存水位线（Watermark）与 OOM Killer

**内核内存回收水位线机制：**

Linux 内核为每个内存 zone（DMA、DMA32、Normal）维护三个水位线，用于驱动内存回收：

```
物理内存容量
│
├─── HIGH 水位线 ─────────────────────────────────
│    内存充足，无回收压力                             
│    kswapd 线程处于睡眠状态
│
├─── LOW 水位线 ──────────────────────────────────
│    内存开始紧张                                    
│    内存分配触发 kswapd 唤醒（异步回收）               
│    kswapd 扫描 LRU 链表：回收匿名页（swap）、文件页（丢弃） 
│
├─── MIN 水位线 ──────────────────────────────────
│    内存严重不足                                    
│    内存分配进入 直接回收（Direct Reclaim）             
│    分配线程自身执行回收操作（同步阻塞！）               
│    通常表现为 Java 应用的延迟尖刺                     
│
├─── 0
```

**水位线数值：** `/proc/sys/vm/min_free_kbytes` 设定了 min 水位线的绝对值（默认基于内存总量自动计算，约 0.1-0.2%）。low = min * 1.25，high = min * 1.5。

**内存分配路径与回收决策：**

```c
// 简化示意 — Linux mm/page_alloc.c
// 申请物理页时执行：
get_page_from_freelist(order, alloc_flags)
  ├── 空闲页足够（当前 zone free > low） → 直接分配，O(1)
  ├── 空闲页在 [min, low) → 唤醒 kswapd 后台回收 → 分配成功
  ├── 空闲页 < min → 进入 __alloc_pages_direct_reclaim()
  │     ├── 同步直接回收 → 阻塞当前线程！（Java 应用表现为 GC 后仍 STW）
  │     └── 回收成功 → 分配
  └── 回收失败 → __alloc_pages_direct_compact() → 尝试内存压缩
           ↓ 还是失败
       __alloc_pages_may_oom() → 选择进程 → OOM Killer
```

**OOM Killer 触发条件与评分：**

当所有回收手段（kswapd 回收 + 直接回收 + 内存压缩）均无法获得所需页面时，内核调用 `out_of_memory()`，选择并杀死一个进程以释放内存。

选择算法（`oom_badness()`）：
```c
// oom_score = (进程占用的总内存页数 + 子进程内存 × 0.5) / 总内存
// 然后通过 oom_score_adj 调整（范围 -1000 ~ 1000）
// oom_score_adj = -1000 → 永远不会被 OOM Killer 选中
// oom_score_adj = 1000  → 首当其冲被杀

// sshd 等关键守护进程通常设置为 -1000：
// cat /proc/$(pidof sshd)/oom_score_adj → -1000
```

**生产环境对 JVM 的保护策略：**

```bash
# 1. 调整 JVM 进程的 oom_score_adj，使其不轻易被 OOM Killer 选中
echo -500 > /proc/<java_pid>/oom_score_adj

# 2. 或使用 systemd 的 OOMScoreAdjust
# ExecStart=/usr/bin/java -jar app.jar
# OOMScoreAdjust=-500

# 3. 配置 vm.overcommit_memory=2 + vm.overcommit_ratio，防止内存过度承诺
# 避免"名义上内存充足，实际上已耗尽"

# 4. 使用 cgroup v2 的 memory.high / memory.max 做软/硬限制
# echo 8G > /sys/fs/cgroup/<group>/memory.max
# 达到 memory.high 时触发节制（throttling），超过 memory.max 触发 OOM

# 5. 监控 slab 内存泄漏
# slabtop -o  → 检查 dentry、inode、kmalloc 等内核 slab 是否异常增长
# 这是常见的"应用内存正常但系统内存耗尽"的根因
```

**Java 应用视角的水位线意义：**

- 当系统空闲内存低于 low 水位线时，JVM 的任何内存分配（堆扩展、DirectByteBuffer 分配、线程栈分配）都可能触发直接回收，表现为 GC 暂停时间异常、请求延迟尖刺
- 大堆场景（如 -Xmx 32G）下，堆本身的内存就已接近系统物理内存，GC 触发的内存扫描容易引发 `kswapd` 回收，建议留出至少 20% 的系统内存给 Page Cache 和内核使用

## 常见问题 / 面试题

**Q1: 线程上下文切换的开销具体是多少？**
每次上下文切换的开销约 1-5 微秒（取决于 CPU 架构和缓存状态），主要包括：保存/恢复寄存器、切换页表、刷新 TLB、切换内核栈。对于高频交易或延迟敏感系统，这个开销不可忽视。Virtual Threads 通过用户态切换避免了内核上下文切换。

**Q2: mmap vs read 的区别？**
`read` 将数据从 Page Cache 拷贝到用户缓冲区（2 次内存拷贝）；`mmap` 将 Page Cache 直接映射到用户空间（零拷贝，但可能触发缺页中断）。`mmap` 适合随机访问和大文件，`read` 适合顺序读取。`mmap` 的映射和解除映射有开销，不适合频繁 map/unmap。

**Q3: epoll 的 LT（Level Triggered）和 ET（Edge Triggered）模式有何区别？**
LT（水平触发，默认模式）：只要 fd 就绪，每次 `epoll_wait` 都会返回该 fd。ET（边缘触发）：fd 就绪后只通知一次，必须一次性读完/写完所有数据。ET 模式减少 `epoll_wait` 调用次数，但编程复杂度更高（必须用非阻塞 I/O + 循环读写）。

**Q4: Java synchronized 锁升级过程能否倒退？**
能。在安全点（SafePoint）时，如果 JVM 检测到锁没有竞争，可以将重量级锁降级回轻量级锁。但偏向锁一旦撤销不会重新偏向（JDK 15+ 已移除偏向锁，不再适用）。

**Q5: 什么是假共享（False Sharing），如何避免？**
当两个不相关的变量位于同一个缓存行（通常 64 字节）中，核心 A 修改变量 X 会导致核心 B 的变量 Y 失效（缓存一致性协议），尽管 B 并没有使用 X。Java 中使用 `@Contended` 注解（JDK 9+，需 `-XX:-RestrictContended`）或手动填充来隔离变量到不同的缓存行。`ConcurrentHashMap` 的 `CounterCell` 和 `LongAdder` 内部都使用了 `@Contended`。
