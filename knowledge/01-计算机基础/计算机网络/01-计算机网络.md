# 计算机网络 — 后端工程师必备网络知识

## 概述

网络是后端系统的血管——每个 API 调用、数据库查询、消息投递和缓存操作都经过网络。不理解网络协议栈的工程师在排查超时、连接重置、延迟抖动等问题时，只能依赖猜测而非基于原理的推理。本文以 TCP/IP 协议栈为主线，深入 HTTP/2/3 协议演进、TLS 加密体系、DNS 解析、Socket 编程和常见网络问题诊断，并全程以 Java 代码示例衔接理论与实践。

---

## 核心内容

### 一、TCP/IP 协议栈

#### 1.1 四层模型

| 层 | 协议示例 | 数据单元 | 功能 |
|---|---|---|---|
| 应用层 | HTTP、DNS、TLS | Message | 应用程序数据格式 |
| 传输层 | TCP、UDP | Segment/Datagram | 端口号、可靠性、流量控制 |
| 网络层 | IP、ICMP | Packet | IP 地址、路由 |
| 链路层 | Ethernet、Wi-Fi | Frame | MAC 地址、物理传输 |

封装路径：应用数据 → TCP Segment（加 TCP 头）→ IP Packet（加 IP 头）→ Ethernet Frame（加 MAC 头 + CRC 尾）

#### 1.2 为什么分四层？

分层遵循单一职责原则。每层可以独立演进——比如物理介质从铜线升级到光纤不用修改 TCP 协议；HTTP 从 1.1 升级到 2 不需要改变 IP 路由。这种"层间接口稳定，层内自由演进"的设计使互联网在过去 50 年里不断扩展。

### 二、TCP 详解

TCP（Transmission Control Protocol）提供面向连接的、可靠的、有序的字节流传输。

#### 2.1 三次握手

```
Client                              Server
  | --- SYN (seq=x) ---------------> |    (1) 客户端发 SYN，进入 SYN_SENT
  | <-- SYN+ACK (seq=y, ack=x+1) -- |    (2) 服务器发 SYN+ACK，进入 SYN_RCVD
  | --- ACK (ack=y+1) -------------> |    (3) 客户端发 ACK，双方进入 ESTABLISHED
```

**为什么是三次而不是两次？** 两次握手无法防止已失效的连接请求到达服务器。假设客户端第一次 SYN 因网络拥堵延迟，客户端重传 SYN，连接建立、传输完成并关闭。之后第一个超时的 SYN 到达服务器，服务器以为客户端又想建连接，返回 SYN+ACK，但客户端已经不需要这连接——这导致服务器端挂着一个半开连接，浪费资源。三次握手让客户端必须在第三次发送 ACK 来确认连接。

#### 2.2 四次挥手

```
Client                              Server
  | --- FIN (seq=u) ---------------> |    (1) 客户端：我没有数据要发了
  | <-- ACK (ack=u+1) ------------ |    (2) 服务器：收到，但我可能还有数据
  | <-- FIN (seq=v, ack=u+1) ----- |    (3) 服务器：我也没有数据要发了
  | --- ACK (ack=v+1) -------------> |    (4) 客户端：收到
  |  进入 TIME_WAIT (2MSL)           |   服务器关闭
```

**TIME_WAIT 为什么需要 2MSL？**（MSL = Maximum Segment Lifetime，通常 30-120 秒）
1. 确保最后一个 ACK 能到达服务器：如果 ACK 丢失，服务器重传 FIN，客户端能重发 ACK
2. 让旧连接的所有报文在网络上消失，避免干扰同端口的新连接

**生产环境的 TIME_WAIT 问题：** 高并发短连接场景下（如频繁的 HTTP/1.1 短连接），服务器上可能出现大量 TIME_WAIT 状态的连接（`netstat -an | grep TIME_WAIT | wc -l` 可能达到数万），导致端口耗尽。解决方案：
- 使用 HTTP 长连接 (`Connection: keep-alive`)
- 调整内核参数：`net.ipv4.tcp_tw_reuse = 1`

#### 2.3 TCP 状态机

```
CLOSED → LISTEN → SYN_RCVD → ESTABLISHED → FIN_WAIT_1 → FIN_WAIT_2 → TIME_WAIT → CLOSED
                                           \→ CLOSE_WAIT → LAST_ACK → CLOSED
```

常见异常状态诊断：
- 大量 `SYN_RCVD` → 可能遭受 SYN Flood 攻击
- 大量 `CLOSE_WAIT` → 服务端代码忘记调用 `close()`，文件描述符泄漏
- 大量 `TIME_WAIT` → 高并发短连接

#### 2.4 滑动窗口与流量控制

TCP 使用滑动窗口实现流量控制——接收方在 ACK 中告知自己的接收窗口大小（`rwnd`），发送方保证在途数据量不超过 `min(cwnd, rwnd)`。

窗口为 0 时，发送方停止发送并启动"零窗口探测定时器"，定期发送探测报文检查接收方窗口是否重新开放。

**与 Java 的关系：** `Socket.setReceiveBufferSize(int)` 影响接收窗口的初始大小。默认值通常是 64KB-128KB。大带宽高延迟链路（如跨洲传输），建议增大缓冲区以利用带宽：`buffer_size = bandwidth * RTT`（带宽延迟积）。

#### 2.5 拥塞控制

TCP 拥塞控制经历了多个版本的演进：

| 算法 | 阶段 | 特点 |
|---|---|---|
| Tahoe | 慢启动 → 拥塞避免 → 丢包→慢启动重来 | 简单但丢包后窗口骤降 |
| Reno | 在 Tahoe 基础上增加快速恢复（Fast Recovery） | 3 个重复 ACK 触发快速重传而非超时 |
| CUBIC | Linux 默认算法 | 窗口增长函数为三次函数，不依赖 RTT |
| BBR | Google 开发 | 基于瓶颈带宽和 RTT 建模，不把丢包作为唯一的拥塞信号 |

慢启动：`cwnd` 从 1 个 MSS 开始，每收到一个 ACK 翻倍（指数增长），直到达到慢启动阈值（`ssthresh`）。拥塞避免阶段：`cwnd` 线性增长（每 RTT 增加 1 个 MSS）。

**Java 端的观察：** 应用层无法直接控制 TCP 拥塞算法，但可以观察到其影响——例如下载大文件时速度从慢到快再到稳定，就是慢启动到拥塞避免的过程。

#### 2.6 TCP Keep-Alive

TCP Keep-Alive 用于检测对端是否仍在。Linux 默认参数：
- `tcp_keepalive_time = 7200`（2 小时后才发第一个探测包）
- `tcp_keepalive_intvl = 75`（探测间隔 75 秒）
- `tcp_keepalive_probes = 9`（最多探测 9 次）

默认 2 小时太久，对于大多数后端应用，应在应用层实现心跳（如定时发心跳包），或使用 `Socket.setKeepAlive(true)` 并调整 OS 参数。

### 三、HTTP 协议演进

#### 3.1 HTTP/1.1

HTTP/1.1 是最广泛使用的 HTTP 版本。核心特性：
- **持久连接**（Connection: keep-alive）：默认不复用连接，减少 TCP 握手开销
- **管线化**（Pipelining）：同一连接上可以连续发送多个请求不必等待响应，但由于队头阻塞（Head-of-Line Blocking）问题，大多数浏览器禁用
- **分块传输编码**（Chunked Transfer Encoding）：适用于不知道响应体大小的场景，如 SSE 流式输出

**队头阻塞问题：** 在一个 TCP 连接上，前一个请求/响应拖慢会阻塞后续所有请求。HTTP/1.1 的解法是开启多个 TCP 连接（浏览器通常 6 个/域名），但这增加了连接管理的复杂性。

#### 3.2 HTTP/2

HTTP/2（RFC 7540）引入了三个革命性的改进：

**二进制分帧层：** HTTP/1.1 是纯文本协议，HTTP/2 将请求/响应拆分为二进制帧（Frame），在一条 TCP 连接上交错传输多个流（Stream）的帧。

**多路复用：** 多个请求/响应可以在同一 TCP 连接上并发传输，互不阻塞。Stream ID 标识每个流，奇数 ID 表示客户端发起，偶数 ID 表示服务端发起。

**头部压缩（HPACK）：** HTTP 请求头中有大量冗余（如每次请求都带 Cookie），HPACK 使用静态/动态表 + Huffman 编码压缩头部，减少带宽消耗 85-90%。

**Server Push：** 服务端可以主动推送资源（如 HTML 中的 CSS/JS），让浏览器在请求之前就开始下载。但实际部署中 Server Push 应用有限，部分浏览器已开始弃用。

HTTP/2 的局限：由于底层仍是 TCP，TCP 层的丢包重传会阻塞所有流（TCP 队头阻塞）。这是 HTTP/3 要解决的核心问题。

#### 3.3 HTTP/3 (QUIC)

HTTP/3 基于 QUIC 协议（最初由 Google 设计），底层使用 UDP 代替 TCP。

**核心优势：**
- **0-RTT 握手：** 之前连接过的客户端可以 0-RTT 直接发送数据（基于保存的 TLS 密钥）
- **无队头阻塞：** QUIC 的流在 UDP 层独立，一个流的丢包不影响其他流
- **连接迁移：** 连接由 Connection ID 标识，IP 地址变化（如 WiFi 切 4G）不影响连接

**Java 支持：** JDK 内置的 `HttpClient`（JDK 11+）目前还不支持 HTTP/3。需要引入第三方库（如 `netty-incubator-codec-http3`）或通过反向代理（如 Nginx + QUIC）实现。

### 四、DNS

#### 4.1 解析过程

```
浏览器 → 系统 DNS 解析器 → 本地 DNS 服务器（运营商/路由器）
  → 根 DNS 服务器（返回 .com NS 记录）
  → 顶级域 DNS 服务器（返回 example.com NS 记录）
  → 权威 DNS 服务器（返回 example.com 的 A 记录）
```

TTL 控制缓存时间。CDN 的核心原理是基于 DNS 解析返回离用户最近的边缘节点 IP。

#### 4.2 Java 中的 DNS

```java
InetAddress addr = InetAddress.getByName("www.example.com");
// JVM 默认缓存 DNS 结果，可通过以下参数调整：
// -Dsun.net.inetaddr.ttl=30        (秒，-1 表示永久缓存)
// -Dsun.net.inetaddr.negative.ttl=10  (失败缓存的 TTL)
```

**注意：** JVM 默认永久缓存 DNS 结果（如果 SecurityManager 未安装），这在容器化/K8s 环境中可能导致调用已经销毁的旧 Pod IP。务必显式设置 `sun.net.inetaddr.ttl`。

### 五、TLS 1.3

TLS 1.3（RFC 8446）是对 TLS 1.2 的重大简化。

#### 5.1 握手过程

```
Client → Server: ClientHello (支持的密码套件 + 密钥共享)
Server → Client: ServerHello (选择的密码套件 + 密钥共享)
                 + {EncryptedExtensions}
                 + {Certificate}
                 + {CertificateVerify}
                 + {Finished}
Client → Server: {Finished}
```

**1-RTT 握手：** TLS 1.3 握手只需 1 个 Round-Trip Time（TLS 1.2 需要 2 个 RTT）。客户端在第一个 ClientHello 中就包含了密钥共享（如 ECDHE 的公钥），减少了往返次数。

**PFS（Perfect Forward Secrecy）：** TLS 1.3 强制使用支持 PFS 的密码套件（ECDHE），即使服务器的长期私钥泄漏，已建立的会话密钥也不会泄漏。TLS 1.3 移除了 RSA 密钥交换和静态 DH 等不支持 PFS 的算法。

#### 5.2 证书链

```
Root CA（预装，自签名）→ Intermediate CA → Server Certificate（叶子证书）
```

客户端验证链条：用 Root CA 公钥验证 Intermediate CA 签名 → 用 Intermediate CA 公钥验证 Server 证书签名。

#### 5.3 Java 中的 TLS

```java
// JDK 25 HttpClient 默认使用 TLS 1.3
var client = HttpClient.newBuilder()
    .sslContext(sslContext)     // 自定义 SSLContext
    .sslParameters(params)      // 自定义密码套件等
    .version(HttpClient.Version.HTTP_2)
    .build();
```

mTLS（双向 TLS）：服务端不仅提供证书，也要求客户端提供证书。适合内部服务间通信的身份认证。

### 六、Socket 编程

#### 6.1 传统阻塞 Socket

```java
try (var serverSocket = new ServerSocket(8080)) {
    while (true) {
        var clientSocket = serverSocket.accept();  // 阻塞等待连接
        new Thread(() -> {  // 传统做法：一个连接一个线程
            try (clientSocket;
                 var in = new BufferedReader(
                     new InputStreamReader(clientSocket.getInputStream()));
                 var out = new PrintWriter(clientSocket.getOutputStream(), true)) {
                String line;
                while ((line = in.readLine()) != null) {
                    out.println("Echo: " + line);
                }
            } catch (IOException e) {
                e.printStackTrace();
            }
        }).start();
    }
}
```

线程-per-connection 模型的致命缺陷：当连接数达到数千时，线程数爆炸，大量时间花在上下文切换上。

#### 6.2 NIO Selector 模式

```java
try (var selector = Selector.open();
     var serverChannel = ServerSocketChannel.open()) {
    serverChannel.bind(new InetSocketAddress(8080));
    serverChannel.configureBlocking(false);
    serverChannel.register(selector, SelectionKey.OP_ACCEPT);

    while (true) {
        selector.select(); // epoll_wait
        var keys = selector.selectedKeys().iterator();
        while (keys.hasNext()) {
            var key = keys.next();
            keys.remove();
            if (key.isAcceptable()) {
                // 接受新连接
                var client = ((ServerSocketChannel) key.channel()).accept();
                client.configureBlocking(false);
                client.register(selector, SelectionKey.OP_READ);
            } else if (key.isReadable()) {
                // 读取数据
                var client = (SocketChannel) key.channel();
                var buffer = ByteBuffer.allocate(1024);
                int read = client.read(buffer);
                if (read == -1) {
                    client.close();
                } else {
                    buffer.flip();
                    client.write(buffer);
                }
            }
        }
    }
}
```

这个模型是 Netty 的基础。单个线程通过 Selector（底层 epoll）管理数千个连接。

### 七、负载均衡

| 类型 | 工作层 | 代表 | 适用场景 |
|---|---|---|---|
| L4（传输层） | TCP/UDP | LVS、Nginx stream | 基于 IP+Port 分发，性能最高 |
| L7（应用层） | HTTP/HTTPS | Nginx http、Spring Cloud Gateway | 基于 URL/Header/Cookie 分发，灵活 |

**常见算法：**
- 轮询（Round Robin）：均匀分配
- 最少连接（Least Connections）：发给连接数最少的后端
- 一致性哈希（Consistent Hashing）：同一请求总是发到同一后端（会话保持、缓存命中率）
- 加权轮询（Weighted Round Robin）：按权重比例分配

### 八、常见网络问题诊断

| 工具 | 用途 | 典型命令 |
|---|---|---|
| `ss` | 查看 Socket 统计（替代 netstat） | `ss -tlnp`（查看监听端口）|

## 代码示例 — 使用 JDK HttpClient

```java
// JDK 25 HttpClient — 支持 HTTP/2, SSE, Virtual Threads
void http2Example() throws Exception {
    try (var client = HttpClient.newBuilder()
            .version(HttpClient.Version.HTTP_2)
            .connectTimeout(Duration.ofSeconds(10))
            .build()) {

        var request = HttpRequest.newBuilder()
            .uri(URI.create("https://http2.golang.org/reqinfo"))
            .header("Accept", "application/json")
            .GET()
            .build();

        var response = client.send(request,
            HttpResponse.BodyHandlers.ofString());

        System.out.println("Status: " + response.statusCode());
        System.out.println("Version: " + response.version()); // HTTP_2
        System.out.println("Body: " + response.body());
    }
}

// SSE 流式接收（配合 Virtual Threads）
void sseWithVirtualThreads() {
    var request = HttpRequest.newBuilder()
        .uri(URI.create("https://api.example.com/events"))
        .GET()
        .build();

    var client = HttpClient.newBuilder().build();
    client.sendAsync(request, HttpResponse.BodyHandlers.ofLines())
        .thenAccept(response -> {
            response.body().forEach(line -> {
                if (line.startsWith("data:")) {
                    System.out.println("Event: " + line);
                }
            });
        });
}
```

## 常见问题 / 面试题

**Q1: TCP 三次握手中，第二次握手（SYN+ACK）丢失了会怎样？**
客户端由于没有收到 SYN+ACK，会重传 SYN（默认重传 5 次，间隔 1s、2s、4s、8s、16s）。服务器端由于没有收到 ACK，也会重传 SYN+ACK。两侧的重传机制独立运作。

**Q2: HTTP/2 的多路复用与 HTTP/1.1 的 Keep-Alive 管线化有什么本质区别？**
HTTP/1.1 管线化是串行响应（必须按请求顺序返回响应），队头响应慢会阻塞后续所有响应。HTTP/2 多路复用将请求拆分为二进制帧，不同流的帧可以交错传输，接收方按 Stream ID 重组——真正的并行。

**Q3: TLS 1.3 为什么比 TLS 1.2 快？**
TLS 1.3 的握手从 2-RTT 减少到 1-RTT（0-RTT 重连更快），因为 ClientHello 直接包含密钥共享。另外，TLS 1.3 移除了 100 多种不安全的密码套件，简化了协商过程。

**Q4: TCP 的 Keep-Alive 和 HTTP 的 Keep-Alive 是一回事吗？**
完全不同。TCP Keep-Alive 是 TCP 层的探活机制（默认 2 小时）；HTTP Keep-Alive 是 HTTP/1.1 的长连接特性，复用 TCP 连接发送多个 HTTP 请求。两者名字相似但层不同。

**Q5: 如何排查 Java 应用的连接池耗尽问题？**
1. `ss -tnp | grep <pid>` 查看当前 TCP 连接数和状态分布
2. 检查是不是大量 TIME_WAIT 或 CLOSE_WAIT
3. `-Djavax.net.debug=all` 输出 Socket 级别的连接详情
4. 通过 JFR 的 Socket Read/Write Events 分析 I/O 时间分布
5. Thread dump（`jstack <pid>`）查看阻塞在 `Socket.connect()` 或 `SocketInputStream.read()` 上的线程
